# AI 거버넌스·컴플라이언스 검토 보고서

작성: AI 거버넌스·컴플라이언스 책임자 / 작성일 2026-11-13 / 근거: 공용 브리핑, 제주빅데이터센터 데이터 반출 정책 원문(2026.09.01 개정, 직접 내려받아 읽음), 대회 제공 데이터 목록 xlsx(데이터 이름만 인용)

## 결론 5줄

1. 넘으면 안 되는 첫 번째 선은 "센터 CSV에서 나온 값은 어떤 형태로든 외부 LLM으로 보내지 않는다"이다. 원본·조회 결과는 운영진이 불가라고 했고, 집계값은 허용 범위를 확정해 주지 않았으며, 질문 문장에 섞인 값도 외부 전송으로 본다고 했다. 그래서 "10 미만을 가린 집계표를 외부 LLM에 보내는" 구조는 대회 제출은 가능하더라도 센터 탑재가 불확실하다.
2. 규정 위험이 가장 낮으면서 AI 역할도 살리는 구조는, 외부 LLM에게는 공개 명세서·허브 공개 데이터·값을 걸러 낸 질문만 주어 계획과 도구 호출을 맡기고, 센터 CSV는 로컬 코드(필요하면 로컬 LLM)만 다루게 하며, 이 경계를 프롬프트가 아니라 코드와 자동 테스트로 강제하는 구조다.
3. 반출 정책 원문은 로그인 없이 확인했다. 브리핑에 없던 중요한 조항은 산출물 4가지 유형의 정의(발췌·단순집계·응용집계·시각화), 응용집계는 수치를 포함해 반출 가능, 시각화는 png·jpg 그림만 인정(SVG·HTML은 캡처 필요), 소스코드에 data.head() 같은 데이터 출력이 남아 있으면 반출 불가, 10 미만 처리 방법 3가지(범주·삭제·비식별), 원본 제공 불가 데이터는 제공 단위 그대로의 합계·평균도 원칙적으로 반출 불가, 버스·교통량·와이파이·날씨·쓰레기 계열 센터 데이터는 원본까지 반출 가능, 영리 목적 사용은 제공기관 협의 필요라는 것이다.
4. 기획서에 외부 전송 명세표, 외부 접속 주소 목록, LLM을 끈 상태의 동작 범위, 결과 삭제 ON/OFF, 반출 규칙 적용 방식, 출처 표기, 라이선스·AI 사용 내역을 넣으면 결과 신뢰성과 실용성 점수에 직접 도움이 된다. 기획서 PDF는 상호평가에서 다른 참가자에게 공개되므로 API 키나 비공개 정보를 절대 넣지 않는다.
5. 아이디어는 세 가지다. 반출 심사 통과형 보고서 Agent는 겹칠 가능성이 높지만 역산 방지·제공 단위 규칙·코드 출력 제거까지 다뤄 차별화할 수 있고, 공개 쌍둥이 리허설 Agent는 겹칠 가능성이 중간이며 LLM이 센터 데이터를 한 번도 보지 않는다는 것을 시연으로 증명할 수 있고, 기업 데이터 지배기업 보호 Agent는 겹칠 가능성이 낮지만 센터 기업 데이터의 컬럼 구조를 아직 확인하지 못했다는 위험이 있다.

## 1. 넘으면 안 되는 선 목록

각 항목은 "선", "근거", "설계에 주는 의미" 순으로 적었다. 근거에서 "운영진 답변"은 브리핑 4절, "반출 정책"은 2026.09.01 개정 원문 PDF를 뜻한다.

### 1-1. 센터 데이터 외부 전송 금지

- 선: 센터 CSV의 원본 행, 조회 결과, 그로부터 계산한 집계값, 그리고 그 값이 섞인 질문 문장을 외부 LLM이나 외부 서버로 보내지 않는다.
- 근거: 운영진 답변 "센터 데이터 원본·조회 결과를 외부 LLM으로 보내면 불가", "집계값 전송은 센터 심의 대상이라 허용 범위를 사전에 확정해 주지 않음(11/7, 11/10)", "질문 문장에 센터 데이터 값이 들어가 외부로 가도 외부 전송으로 본다", "센터 데이터가 통신으로 외부에 나가는 구조는 불가".
- 의미: 집계값 전송은 "금지"라고 하지 않았지만 "허용"도 확정하지 않았다. 대회 결과물이 센터에 탑재되려면 심의를 통과해야 하므로, 집계값을 보내는 구조는 탑재 단계에서 막힐 수 있다. 사용자가 화면에서 본 숫자를 질문에 그대로 쳐 넣는 경우도 막아야 하므로, 외부로 나가는 문장을 코드로 검사하는 장치가 필요하다.
- 예외: 제주데이터허브 공개 데이터는 이 제한이 없다(운영진 답변 "공개 데이터"). 센터 데이터 명세서는 외부에 공개된 자료이고(브리핑 6-1), 반출 정책도 "데이터명세서, 반출정책: 외부 홈페이지에도 공개하고 있으므로 반출가능"이라고 적고 있다. 따라서 컬럼 이름과 명세서 내용은 외부 LLM에 보내도 된다. 업종코드표와 메뉴코드표는 반출 정책 표에서 원본까지 반출 가능(O)으로 되어 있다.

### 1-2. 센터 DB·API 직접 연결 금지

- 선: Agent가 센터 DB나 API에 직접 붙지 않는다. 이용자가 센터 조회 화면에서 CSV를 내려받고, Agent는 그 파일을 파일 선택이나 경로 지정으로 읽는다.
- 근거: 운영진 답변 "Agent가 센터 DB·API에 직접 연결 불가 … CSV를 Agent에서 파일 선택·경로 지정으로 불러오는 구조여야 한다".
- 의미: 센터 조회 화면을 브라우저 자동화로 대신 눌러 CSV를 받는 기능도 같은 취지에 어긋날 가능성이 크므로 넣지 않는다(추론). 대신 "어느 데이터를, 어느 달을, 어떤 조건으로 조회하라"는 안내까지만 Agent가 한다.

### 1-3. DLP와 외부 통신 차단

- 선: 외부 통신이 차단돼도 Agent가 멈추지 않아야 한다.
- 근거: 운영진 답변 "DLP 보안정책이 있어 데이터가 외부로 나가는 통신은 차단될 수 있다".
- 의미: 외부 LLM 호출이 실패하면 로컬 LLM이나 규칙 기반 안내로 넘어가는 "LLM 꺼짐 모드"를 설계에 넣는다. 외부 LLM이 없으면 핵심 기능이 아예 안 되는 구조는 탑재 위험이 크다.

### 1-4. 접속 차단 키워드

- 선: Agent가 접속하는 모든 외부 주소(LLM API, 허브 Open API, 패키지 저장소, 로컬 모델 다운로드 주소, 지도 타일·CDN)가 차단 키워드에 걸리지 않는지 점검하고, 기획서에 전부 적어 허용 목록 등록을 받는다.
- 근거: 운영진 답변 "행안부 불법광고 차단 키워드 133개가 들어간 주소는 자동 차단될 수 있다"(코인, 아이스, 케이, 마약, 카지노, 픽업, 정산, 운반, 드랍, 실험용, 회원모집, 자동수집, 그룹방, 떨 등), "기획서에 적은 외부 주소는 허용 목록 등록 가능".
- 의미: 133개 전체 목록은 브리핑에 없다. 영문 표기(예를 들어 coin, ice, drop, pickup)까지 걸리는지도 알 수 없으므로, 영문 대응어가 들어간 주소도 피하거나 기획서에 명시한다(추론). 기획서에 적지 않은 주소는 쓰지 않는다.

### 1-5. 반출 기준

- 선: Agent가 "반출용"으로 만드는 결과물은 반출 정책을 만족해야 한다. 최소한 다음을 지킨다.
  - 10 미만 단순집계 값은 범주처리, 삭제처리, 비식별처리(같은 값 처리 등) 중 하나로 처리한다(반출 정책 표 비고와 "각 제공처별 반출 기준").
  - 합계 등으로 가린 값을 거꾸로 계산할 수 있으면 반려된다(브리핑 5절 반려 사유 "역산 가능").
  - 텍스트(csv, txt)와 스프레드시트(엑셀)는 원칙적으로 반출 불가이고, 보고서와 그림 파일을 권장한다(브리핑 5절, 반출 정책 "각 제공처별 반출 기준").
  - 그림은 png·jpg만 인정한다. SVG·VML·HTML 벡터 시각화는 화면 캡처 그림으로만 가능하다(반출 정책 "시각화" 정의).
  - 소스코드에 데이터 샘플 출력이 들어 있으면 반출 불가다(반출 정책 "반출 시 유의사항", 예시: Python data.head(), R head(data)).
  - 반출 신청 시 파일마다 출처(원본 데이터 명칭)와 활용 사유를 자세히 적어야 한다. 출처 표기 예시는 "제주빅데이터센터, 데이터셋(이름, 기간)"이다.
- 의미: Agent의 내보내기 기능은 기본값을 PDF 보고서와 png 그림으로 하고, CSV·엑셀 내보내기는 센터 안 작업용으로만 두며 "반출 불가 원칙" 경고를 붙인다. 생성 코드나 노트북을 내보낼 때는 출력 셀을 지운다.

### 1-6. 대회 제공 xlsx 배포 금지

- 선: 대회 제공 「제주데이터허브 데이터목록_20261105.xlsx」를 ZIP에 넣거나, 기획서·Agent 안에 목록 전체를 옮겨 싣지 않는다.
- 근거: 브리핑 6-2 "Daker 홈페이지 외 배포 금지".
- 의미: 데이터 안내 기능이 필요하면 Agent가 사용하는 데이터만 직접 정리해 넣거나, 실행 시 허브 공개 화면·Open API에서 받아 온다. 허브 공개 데이터 원본·전처리본은 ZIP에 넣어도 된다(브리핑 6-2)는 것과 혼동하지 않는다. 목록 파일 자체가 금지 대상이다.

### 1-7. 외부 데이터 이용 조건

- 선: 허브 데이터와 외부 공개 데이터는 데이터마다 이용 조건을 확인하고 출처를 명시한다. 상업적 이용 금지나 변경 금지 조건이 붙은 데이터는 가공·탑재 용도에 맞는지 따로 확인한다.
- 근거: 브리핑 6-2 "외부 공개 데이터도 적법하면 사용 가능(출처 명시)", 반출 정책 "영리목적 사용 시 제공기관과 협의 필요"(비씨카드, 탐나는전, KT, SKT, 나이스지니데이타, 데이터웨이, 제주특별자치도, 티머니 등 전 제공처).
- 의미: 센터가 결과물을 비독점 이용하고 참가자도 대회 뒤 계속 개발할 수 있으므로, 나중에 상업화하려면 센터 데이터 제공기관과 협의가 필요하다는 점을 기획서 한계 항목에 적는다. 허브 데이터별 이용허락 유형(예: 공공누리 유형)은 이번에 확인하지 못했다.

### 1-8. 개인정보

- 선: Agent가 개인을 식별할 수 있는 정보를 수집·저장·외부 전송하지 않는다. 이용자가 직접 반입한 CSV(예: 자기 가게 매출)도 센터 세션 안에서는 외부로 보내지 않는다.
- 근거: 센터 카드 데이터는 비씨카드 실소유자 기준 집계이고 작은 값(10 미만)이 가려지지 않은 원본이라는 참가자 전언이 있다(브리핑 6-1, 4절). 작은 칸은 특정 개인이나 사업장을 짐작하게 할 수 있다. 이용자 반입 자료에 대한 운영진 답변은 브리핑에 없다.
- 의미: 이용자 반입 자료의 외부 전송 허용 여부는 확인되지 않았으므로 센터 데이터와 같은 기준으로 다루는 것이 안전하다(추론). 대화 기록과 실행 로그도 로컬에만 두고 결과 삭제 대상에 포함한다.

### 1-9. API 키 처리

- 선: 키를 코드에 직접 쓰지 않는다. 운영 키는 센터 담당자가 환경변수로 넣고, 평가용 키는 참가자가 준비해 ZIP 매뉴얼에 넣는다. 기획서 PDF에는 키를 넣지 않는다.
- 근거: 운영진 답변 "운영 시 키는 센터 담당자가 환경변수로 설정", "평가용 외부 AI 키는 참가자가 준비해 ZIP 매뉴얼에 넣어 제출(한도 설정 가능, 비용 참가자 부담)", 브리핑 3절 "상호평가에는 기획서 PDF만 공개".
- 의미: 평가용 키는 이 대회 전용으로 새로 만들고 사용 한도를 걸며, 전문가 평가가 끝나는 11/27 23:59 이후 폐기한다. 허브 Open API 프로젝트 키도 같은 방식으로 다룬다.

### 1-10. 결과물 권리

- 선: 결과물은 수상과 상관없이 센터가 비독점 이용한다. 센터가 쓸 수 없는 조건의 구성 요소(예: 상업적 이용 금지 모델, 재배포 금지 데이터)를 핵심에 두지 않는다.
- 근거: 브리핑 1절 "센터가 비독점 이용(저작권 양도 아님). 센터 안에서만 탑재, 기획서·코드는 이용자에게 비공개".
- 의미: 오픈소스·로컬 모델·데이터의 라이선스 표를 ZIP에 넣는다. 로컬 모델 중에는 사용 조건이 붙은 것이 있으므로 AI 엔지니어가 모델을 고를 때 라이선스를 함께 확인한다.

### 1-11. 대회 기간 중 코드의 개인적 제3자 공유 금지

- 선: 11/20 마감 전후 대회 기간에는 코드를 팀 밖 사람에게 개인적으로 공유하지 않는다. 저장소는 비공개로 유지한다.
- 근거: 과제 지시문에 적힌 "동의사항 8-A". 이번 작업에서 원문은 확인하지 못했다.
- 의미: GitHub 링크 제출은 선택 사항이므로(브리핑 2절) 공개 저장소를 만들지 않는 것이 안전하다. 개발에 외부 AI 코딩 도구를 쓰는 것이 이 조항의 "제3자 공유"에 해당하는지는 원문 확인이 필요하다.

### 1-12. AI 사용 내역 명시 의무

- 선: 사용한 AI 모델, AI 활용 범위, 외부 API, 외부 데이터, 오픈소스를 기획서와 ZIP에 모두 적는다.
- 근거: 브리핑 2절 "사용한 AI 모델, AI 활용 범위, 외부 API, 외부 데이터, 오픈소스를 명시해야 한다".
- 의미: 실행 중에 쓰는 모델은 모델 이름과 버전, 어느 단계에서 쓰는지, 그 모델이 무엇을 보는지까지 적는다. 이 표가 그대로 "외부 전송 명세표" 역할을 해서 규정 준수 근거가 된다. 개발 과정에서 AI 도구를 쓴 범위도 "AI 활용 범위"에 들어갈 수 있으므로 함께 적는 것이 안전하다(추론).

### 1-13. 퇴실 시 삭제와 결과 삭제 기능

- 선: Agent가 만든 모든 작업 파일의 위치를 Agent가 알고 있어야 하고, 결과 삭제 기능을 켜고 끌 수 있어야 한다. 센터 데이터에서 나온 값을 세션을 넘어 보관하는 기능(대화 기억, 캐시 DB 등)은 기본으로 꺼 둔다.
- 근거: 운영진 답변 "퇴실 시 반출 승인 자료 외 삭제. 집계값 보존이 필요하면 매뉴얼에 명시. Agent에 결과 삭제 기능 ON/OFF 권장(없으면 탑재 어려울 수 있음)".
- 의미: 삭제 대상에는 생성한 그림·보고서뿐 아니라 임시 파일, DuckDB 같은 캐시, 대화 기록, 실행 로그, 웹 화면을 쓴다면 브라우저 저장소까지 포함한다. 로컬 LLM 실행 도구가 프롬프트를 로그로 남기는지는 AI 엔지니어 확인이 필요하다.

### 1-14. 설치 범위

- 선: 기획서에 미리 적은 소프트웨어만 설치한다.
- 근거: 운영진 답변 "Python 등 설치 가능(기획서에 미리 적은 것만)".
- 의미: Python 버전, 패키지 목록과 버전, 로컬 모델 이름과 공식 배포처를 기획서 기술 환경 항목에 고정해 적는다.

## 2. 반출 정책 원문 확인 결과

### 2-1. 확인 방법

- 공지 48번 페이지(https://jejudatahub.net/community/notice/view/48)는 화면을 자바스크립트로 그리는 방식이라 HTML에는 본문이 없다. 웹 수집 도구로 접근했을 때는 해외 IP라는 이유로 방화벽에 막혔고, 이 PC에서 직접 요청했을 때는 열렸다.
- 사이트가 공개로 쓰는 API(https://jejudatahub.net/api/community/notice/view?id=48)로 공지를 읽었다. 공지 본문은 "2026년 9월 1일 개정에 따라 게시"라는 한 줄뿐이고, 실제 정책은 첨부 파일 「제주빅데이터센터 데이터 반출 기준.pdf」(10쪽)와 같은 내용의 hwp 파일에 있다. 게시일 2026.10.30, 조회 320회, PDF 내려받기 203회였다.
- 첨부 PDF는 로그인 없이 내려받아 전문을 읽었다. 문서 제목은 「제주빅데이터센터 데이터 반출 정책」, 제정 2020.08.31, 개정 2026.09.01(반출 기준의 정책화 및 절차의 구체화)이다.

### 2-2. 브리핑에 없던 중요한 조항

1. 산출물 4가지 유형의 정의. 분석 산출물을 발췌, 단순집계, 응용집계, 시각화로 나눈다.
   - 발췌: 원본 형태 그대로 일부를 추출한 것.
   - 단순집계: 원본보다 크거나 다른 시간·공간 단위로 속성값이 드러나게 통계 처리한 것. 합계, 평균, 최소, 최대, 중앙값, 단순집계에 가중치를 곱한 것, 영역 안의 위치 개수가 해당한다.
   - 응용집계: 원본보다 크거나 다른 단위로 역변환할 수 없게 통계 처리한 것. 차이, 증감률, 비율, 순위, 범주, 복합 지수, 모델링 결과, 통계 검정값이 해당한다.
   - 시각화: 그래프·지도 등을 png·jpg 그림 파일로 만든 것.
2. 응용집계는 수치를 포함해 반출할 수 있다. 비씨카드·KT·SKT·나이스지니데이타 등 제공처 기준에서 "블록보다 큰 단위로 처리한 응용집계(차액, 지수, 비율, 순위, 범주, 회귀분석 등)의 경우 반출 가능", 그림 파일 안에서도 "응용집계의 경우 수치 포함 반출 가능"이라고 적혀 있다. 반면 단순집계는 그림 안에서 10 미만 수치가 없을 때만 반출 가능하다. 결과를 비율·증감률·순위 형태로 설계하면 반출이 쉬워진다는 뜻이다.
3. 10 미만 처리 방법이 3가지다. 범주처리, 삭제처리, 비식별처리(같은 값 처리 등). 브리핑에는 범주처리만 있었다.
4. 시각화는 png·jpg만 인정한다. SVG, VML, HTML 같은 벡터 방식은 화면을 캡처한 그림으로만 가능하고, 캡처가 안 되면 운영 담당자에게 문의하라고 되어 있다. 웹 차트 라이브러리로 그린 결과는 png로 저장하는 기능이 필요하다.
5. 소스코드에 데이터 샘플 출력이 있으면 반출 불가다. Python의 data.head()나 data 출력, R의 head(data) 출력이 예시로 적혀 있다.
6. 원본 제공이 불가한 데이터는 제공 단위(블록, 집계구, 동, 구 등) 그대로의 총합·평균 같은 통계 처리 데이터도 반출 불가가 원칙이고, 분석결과보고서와 그림 파일 반출을 장려한다. 단순집계 정의가 "원본보다 크거나 다른 단위"라는 점과 함께 보면, 읍면동 단위로 제공된 데이터를 읍면동별 합계표로 내보내는 것은 거절될 가능성이 크다(해석이며, 운영진 확인이 필요하다).
7. 해석이 애매한 경우 "반출 정책을 보완할 사항이며, 반출 심사는 변화 없이 처리됨"이라고 되어 있다. 애매한 경우를 이용자에게 유리하게 해석해 주지 않는다는 뜻으로 읽힌다(해석).
8. 위치(점) 데이터는 위치 자체를 속성값으로 본다. 영역 안의 위치 개수도 단순집계라서 10 미만 규칙이 적용된다.
9. 데이터별 반출 등급표가 있다.
   - 원본·발췌는 불가, 단순집계·응용집계는 가능, 시각화는 조건부인 데이터: 카드 이용 계열(1-01부터 1-16, 1-30, 1-31), 제주도 내 업종별 매장 수(1-17), 외식업 포스 계열(1-18부터 1-31), 탐나는전 이용 현황(1-32), 한국기업데이터 계열(2-01 거래처정보_구매부터 2-08 휴폐업까지 8종), 유동인구 계열(4-07부터 4-15), 품목별 농산물 거래 규모 기상 융합 데이터(5-07).
   - 원본·발췌까지 모두 반출 가능한 데이터: 버스 계열(티머니, 3-01부터 3-06), 도로 구간·노드 정보와 교통량(교통정보센터, 3-07부터 3-10), 와이파이 계열(제주특별자치도, 4-01부터 4-06), 날씨 관측소 정보와 일일 날씨 정보(5-01, 5-02), 종량제봉투판매실적(5-03), 대형폐기물 현황(5-04), 음식물쓰레기 배출현황 제주시·서귀포(5-05, 5-06), 업종코드표와 메뉴코드표.
   - 주의: 반출이 가능하다는 것과 외부 LLM으로 보내도 된다는 것은 다른 문제다. 운영진은 외부 LLM 규칙을 데이터 등급별로 나누지 않았으므로, 반출 가능 등급 데이터라도 센터에서 받은 CSV는 외부 LLM으로 보내지 않는다.
   - 원문 표의 번호에 1-31이 두 번(외식업 포스 메뉴 매출(세분류)과 온라인 카드 이용 현황(제주기업)) 나오고 1-28이 없다. 기획서에서 번호를 인용할 때는 데이터 이름을 함께 적는다.
10. 심사 절차. 반출 신청 뒤 내부 심사자가 심사하고, 경우에 따라 2차로 제공처 심사를 한다. 결과는 승인, 부분승인, 반려 중 하나이고 최대 5일(평균 3일) 안에 이메일과 문자로 통보된다.
11. 일반 요건. 가공한 데이터의 책임은 이용자 본인에게 있고, 공식 통계값은 해당 주관 부서에서 확인해야 한다. Agent 결과 화면과 보고서에 "공식 통계가 아님" 문구를 넣을 근거가 된다.
12. 센터 안에서 분석을 완료하는 것을 권장한다.
13. 원본 파일 서버의 참고 자료 중 데이터명세서와 반출정책은 반출 가능하지만, 데이터안심구역 지침과 파일설명서는 반출 불가다. Agent가 파일설명서 내용을 학습 자료나 프롬프트로 쓰려면 그 내용이 외부에 공개된 것인지 먼저 확인해야 한다.
14. 정책 문서의 용어 정의에 따르면 센터는 65종의 데이터를 제공한다.

## 3. 에이전트 구조 유형별 위험도

위험도는 두 가지로 나눴다. "대회 제출 위험"은 실격이나 감점으로 이어질 가능성이고, "센터 탑재 위험"은 대회 뒤 센터가 실제로 올릴 수 있느냐에 대한 위험이다. 평가 항목 중 실용성(실제 서비스 활용 가능성)은 탑재 위험과 직접 연결된다.

| 구조 | 대회 제출 위험 | 센터 탑재 위험 | 근거가 되는 운영진 답변 |
|---|---|---|---|
| 외부 LLM에 센터 원본 행이나 조회 결과를 보냄 | 높음 | 높음 | "센터 데이터 원본·조회 결과를 외부 LLM으로 보내면 불가" |
| 외부 LLM에 마스킹한 집계표를 보냄 | 중간 | 높음 | "집계값 전송은 센터 심의 대상이라 허용 범위를 사전에 확정해 주지 않음" |
| 외부 LLM에 스키마·공개 명세서·값을 걸러 낸 질문만 보냄 | 낮음 | 낮음~중간 | "질문 문장에 센터 데이터 값이 들어가 외부로 가도 외부 전송으로 본다", 명세서는 외부 공개 자료 |
| 공개 데이터는 외부 LLM, 센터 CSV는 로컬 코드만 쓰는 혼합 구조 | 낮음 | 낮음 | "제주데이터허브 공개 데이터는 이런 제한이 없다", "센터 데이터가 통신으로 외부에 나가는 구조는 불가" |
| 로컬 LLM만 씀 | 낮음 | 낮음 | 로컬 LLM 모델 다운로드 가능, "GTX 1060 3GB라 큰 모델은 어렵다(팀이 판단할 사항)" |
| LLM 없이 코드로 집계·시각화만 함 | 낮음(규정), 높음(점수) | 낮음 | "외부 LLM 없이 … 표·차트만 보여 줘도 데이터 활용으로 인정되지만 AI Agent 대회라 AI가 어떤 역할을 하는지가 중요" |
| 허브 공개 데이터와 외부 공개 데이터만 씀 | 낮음 | 낮음 | "제주데이터허브 공개 데이터는 이런 제한이 없다", 허브 Open API는 센터 PC에서 직접 호출 가능 |
| 센터 DB·API 직접 연결 또는 조회 화면 자동 조작 | 높음 | 높음 | "Agent가 센터 DB·API에 직접 연결 불가" |
| 개인 PC 버전에서 반출 승인된 결과물을 외부 LLM에 넣음 | 중간 | 해당 없음 | 운영진 답변 없음. "같은 Agent를 개인 PC에서 따로 실행하게 만드는 것도 가능"만 있음 |

각 구조에 대한 설명은 다음과 같다.

- 마스킹한 집계표를 보내는 구조: 다른 팀들이 많이 택한 구조다(브리핑 7절: 안녕하12, 미노스, Tarkovsky). 운영진이 금지하지는 않았으므로 대회 실격 가능성은 크지 않다고 본다(추론). 하지만 심의 결과에 따라 탑재가 막힐 수 있고, 10 미만만 가린 표는 반출 기준(역산 방지, 제공 단위 규칙)도 다 만족하지 못할 수 있다.
- 스키마만 보내는 구조: 사용자가 질문에 센터 값을 적어 넣으면 바로 위반이 된다. 이 구조를 "낮음"으로 만들려면 외부로 나가는 문장을 코드로 검사해야 한다. 숫자, 불러온 CSV에 있는 값, 법정동 이름과 금액이 함께 나오는 패턴을 찾아 막거나 로컬 모드로 돌리는 방식이다. 프롬프트로 "값을 보내지 마"라고 지시하는 것만으로는 근거가 약하다.
- 혼합 구조: 데이터마다 "공개" 또는 "센터"라는 표시를 붙이고, "센터" 표시가 붙은 데이터나 그로부터 계산된 결과는 외부 통신 함수에 들어갈 수 없게 코드에서 막는다. 그리고 센터 CSV에 일부러 심어 둔 표시값이 외부 요청에 한 번도 나타나지 않는다는 자동 테스트를 둔다. 이 테스트 결과가 기획서의 결과 신뢰성 근거가 된다.
- 로컬 LLM만 쓰는 구조: 규정 위험은 가장 낮지만, VRAM 3GB에서 한국어 서술과 도구 호출 품질이 충분한지가 기술성·완성도 점수 위험이다. 이 판단은 AI 엔지니어 몫이다.
- 개인 PC 버전: 반출 승인을 받은 결과물은 밖에서 쓰도록 허가된 것이지만, 이를 외부 LLM에 넣어도 되는지에 대한 운영진 답변은 없다. 필요하면 운영진에게 물어야 한다.

## 4. 기획서 규정 준수 설계 체크리스트

결과 신뢰성(결과 근거·한계 명확성, 재현 가능)과 편의성·실용성(실제 서비스 활용 가능성) 점수를 노린 항목이다. 기획서 양식 항목 중 어디에 넣을지 함께 적었다.

### 데이터 흐름과 외부 전송 (기획서 "개발·탑재 계획"의 외부 서비스 의존성)

- [ ] 데이터 흐름도: 센터 CSV, 허브 공개 데이터, 사용자 질문이 각각 어디까지 가는지 그림 한 장으로 보여 준다.
- [ ] 외부 전송 명세표: 외부로 나가는 요청마다 "보내는 내용, 받는 곳, 센터 데이터 포함 여부"를 적는다. 센터 데이터 포함 여부는 전부 "없음"이어야 한다.
- [ ] 외부 전송 차단을 코드로 강제하는 방식과 그것을 확인하는 자동 테스트(심어 둔 표시값 검사)를 적고, 테스트 결과를 결과 설명자료에 넣는다.
- [ ] 질문 문장 검사: 질문에 숫자나 센터 CSV 값이 있으면 외부 전송을 막고 이유를 사용자에게 보여 준다.
- [ ] 외부 전송 기록: 실제로 외부에 보낸 내용을 로컬에 남겨 센터 담당자가 열람할 수 있게 한다. 이 기록도 결과 삭제 대상에 넣는다.
- [ ] 외부 접속 주소 전체 목록과 차단 키워드 점검 결과를 적는다.
- [ ] LLM 꺼짐 모드에서 되는 기능과 안 되는 기능을 표로 적는다(DLP 차단 대비).

### 반출과 삭제 (기획서 "서비스 제안"의 편의성, "개발·탑재 계획")

- [ ] 결과 삭제 ON/OFF 설정과 삭제되는 파일 위치 목록을 적는다. 집계값을 보존하는 기능이 있으면 매뉴얼에 명시한다.
- [ ] 반출용 결과물의 기본 형식을 PDF 보고서와 png 그림으로 하고, CSV·엑셀은 반출 불가 원칙 경고를 붙인다.
- [ ] 10 미만 값 처리 방식(범주·삭제·비식별 중 무엇을 기본으로 하는지)과 역산 방지 방식을 적는다.
- [ ] 결과를 가능하면 응용집계(비율, 증감률, 순위, 지수)로 설계한다는 원칙과 그 근거 조항을 적는다.
- [ ] 생성 코드를 내보낼 때 데이터 출력을 지우는 기능을 적는다.
- [ ] 반출 신청서의 출처와 활용 사유 문안을 자동으로 만들어 주는지 적는다. 활용 사유는 "(툴/분석방법)으로 분석 후 (가공처리)로 가공하여 (내용)의 보고서 작성 및 (어디)에 활용" 수준이어야 한다(브리핑 5절).

### 결과 근거와 한계 (기획서 "Agent 개발 구성", 결과 설명자료의 검증 방법·한계)

- [ ] 모든 표와 그림에 "제주빅데이터센터, 데이터셋(이름, 기간)" 형식의 출처를 자동으로 붙인다.
- [ ] 각 결과가 어떤 파일, 어떤 조건, 어떤 계산으로 나왔는지 화면에서 확인할 수 있게 한다.
- [ ] 데이터 한계 문구를 고정으로 넣는다: 카드 데이터는 비씨카드 한정·실소유자 기준이고, 가공 결과의 책임은 이용자에게 있으며, 공식 통계는 주관 부서에서 확인해야 한다(반출 정책 일반 요건).
- [ ] "판단 및 자율 수행 범위"에 LLM이 하지 못하게 막은 일을 명시한다. 예를 들어 센터 데이터 값 열람, 사용자 확인 없는 파일 삭제, 반출 가능 여부의 최종 판정(최종 판정은 센터 심사자가 한다는 문구)이다.
- [ ] 센터 CSV 형식 검사(영문 헤더, NA 결측, 큰따옴표, UTF-8 BOM 없음, 파일명 Results_YYYYMMDD_HHMMSS.csv)와 비개발자용 오류 메시지를 적는다.

### 설치와 비용, 라이선스 (기획서 "개발·탑재 계획"의 기술 환경)

- [ ] 설치할 소프트웨어와 버전, 로컬 모델 이름과 공식 배포처를 고정해 적는다.
- [ ] 평가용 데이터는 명세서 구조를 따른 가상 데이터임을 밝히고, 실제 센터 데이터는 포함하지 않았다고 적는다.
- [ ] 허브 공개 데이터 스냅숏을 ZIP에 넣어 허브 API 장애나 차단과 상관없이 재현되게 한다.
- [ ] API 키는 환경변수로만 받고, 기획서 PDF에는 키가 없으며, 평가용 키는 한도를 걸었다고 적는다.
- [ ] 외부 LLM 호출 횟수와 길이의 상한, 캐시 사용 여부를 적어 센터 비용 부담을 보여 준다.
- [ ] 라이선스 표: 오픈소스, 모델, 데이터별 이용 조건과 출처. 센터 데이터의 영리 목적 사용은 제공기관 협의가 필요하다는 점을 한계에 적는다.
- [ ] AI 사용 내역 표: 실행 중 쓰는 모델(이름, 버전, 단계, 그 모델이 보는 데이터)과 개발 과정의 AI 활용 범위.

## 5. 규정 준수가 차별점이 되는 AI Agent 아이디어

### 아이디어 1: 반출 심사 통과형 보고서 Agent

- 한 줄 요약: 질문을 받으면 처음부터 반출 정책을 만족하는 형태(응용집계 위주, 10 미만 처리, 역산 방지, png 그림, PDF 보고서)로 분석을 설계해 보고서와 반출 신청 문안까지 만들어 주는 Agent.
- 누가 쓰나: 센터를 방문한 기관·기업 이용자. 예를 들어 관광 관련 기관 연구원이 "애월읍·한림읍의 관광객 카드 소비 업종 구성"을 현황자료에 넣으려고 센터에서 카드 데이터를 조회한 상황.
- 해결하는 문제: 센터 데이터로 분석은 했는데 반출 신청에서 반려되면 다시 방문해야 한다. 반려 사유는 10 미만 값, 역산 가능성, 활용 사유 부족, 형식 문제로 다양하고(브리핑 5절), 원문에는 제공 단위 그대로의 합계 금지나 코드 출력 금지처럼 이용자가 놓치기 쉬운 조항도 있다. 심사는 최대 5일이 걸린다.
- 쓰는 데이터:
  - 센터 데이터: 카드 이용 현황(읍면동)_v02(헤더가 확인된 데이터), 필요 시 외식업 포스 이용 현황(읍면동).
  - 허브 데이터: 읍면동 단위 내국인 유동인구(API, 일 갱신), 제주특별자치도 상가(상권) 정보(File, 2025-09-18).
- AI가 맡는 일:
  - LLM: 사용자의 질문을 분석 계획으로 바꾼다. 어떤 지표가 질문에 답하면서 반출이 쉬운지(합계 대신 비율·증감률·순위, 읍면동 대신 7권역이나 행정시) 고르고, 집계·처리·그림·보고서 도구를 순서대로 호출한다. 반려 위험이 남으면 대안 지표를 제안한다.
  - 일반 코드: CSV 형식 검사, 집계, 10 미만 탐지와 처리(범주·삭제·비식별), 가린 값을 합계로 되살릴 수 있는지 검사해 추가로 가리는 처리(상보 억제), 결과물의 유형 판정(발췌·단순집계·응용집계·시각화), png 저장, PDF 생성, 코드 출력 제거, 반출 신청서 출처·활용 사유 문안 채우기, 정책 조항을 인용한 "심사 근거표" 작성.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙을 지키는 방법: 외부 LLM은 공개 명세서의 컬럼 정의, 업종코드표, 값을 걸러 낸 질문만 보고 계획을 세운다. 데이터를 읽은 뒤의 설명(어느 칸을 왜 가렸는지 등)은 로컬 코드의 고정 문장이나 로컬 LLM이 만든다. 센터 데이터가 들어간 결과는 외부 통신 함수에 넘길 수 없게 코드로 막는다.
- 시연 방법: 명세서 구조로 만든 가상 Results_YYYYMMDD_HHMMSS.csv(일부 칸이 10 미만이고 합계 행이 있는 파일)를 불러와 "애월읍·한림읍 업종별 관광객 카드 이용 현황 보고서를 만들어 줘"라고 입력한다. Agent가 10 미만 칸을 처리하고, 합계 때문에 되살릴 수 있는 칸을 하나 더 가리는 장면, 읍면동 합계표 대신 비율 그림을 제안하는 장면, PDF 보고서와 png 그림과 반출 신청 문안이 나오는 장면, 결과 삭제 ON으로 작업 파일이 지워지는 장면을 보여 준다.
- 다른 팀과 겹칠 가능성: 높음. 반출 점검(beebird, sanhapark, 강태우)과 현황보고서 자동 생성(river.kim)에 경쟁이 몰려 있다(브리핑 7절).
- 그래도 이길 수 있는 이유: 다른 팀들은 게시판 질문으로 보아 "10 미만 점검" 중심일 가능성이 있다(추론). 이 아이디어는 첫째, 결과물을 다 만든 뒤 검사하는 대신 처음부터 반출 가능한 지표를 고르게 해 LLM의 판단이 실제로 쓰이고, 둘째, 원문 조항(산출물 4유형 정의, 응용집계 수치 반출 가능, 제공 단위 규칙, png만 인정, 코드 출력 금지, 처리 3방법)을 모두 규칙으로 구현하며, 셋째, 역산 방지(상보 억제)까지 다루고, 넷째, 원문에서 뽑은 반려 사례를 자동 테스트로 만들어 결과 신뢰성 근거로 낸다. 다만 경쟁 팀이 같은 깊이로 구현하면 차이는 줄어든다.
- 가장 큰 위험:
  - 상보 억제는 한 표 안의 합계만 다룬다. 여러 표를 비교해 값을 되살리는 경우까지는 막지 못하므로 한계로 적어야 한다.
  - 제공 단위 규칙의 해석이 운영진 확인 전이라, 너무 보수적으로 잡으면 결과가 지나치게 거칠어져 사용자가 불편할 수 있다.

### 아이디어 2: 공개 쌍둥이 리허설 Agent

- 한 줄 요약: 외부 LLM은 센터 데이터와 구조가 비슷한 허브 공개 데이터(공개 쌍둥이)로 분석 절차를 직접 실행해 보며 완성하고, 센터 CSV에는 그 검증된 절차를 로컬에서만 적용해, LLM이 센터 데이터를 한 번도 보지 않는다는 것을 증명하는 Agent.
- 누가 쓰나: 논문이나 사업계획서를 쓰는 기관 연구원. 센터 방문 전에 개인 PC에서 분석을 미리 짜 보거나, 센터 PC에서 분석을 시작하는 상황. 운영진은 같은 Agent를 개인 PC에서 따로 실행하는 것도 가능하다고 했다.
- 해결하는 문제: 센터 안에서는 센터 데이터에 외부 LLM을 쓸 수 없으니 이용자는 AI 도움 없이 분석해야 하고, 어떤 데이터를 어떤 조건으로 조회할지 모른 채 방문 시간을 쓴다. 조회는 한 번에 1개월씩이라(브리핑 4절) 무엇을 받을지 미리 아는 것이 중요하다.
- 쓰는 데이터:
  - 허브 데이터(공개 쌍둥이와 보조 자료): 메뉴별 외식업 매출액(File, 2019~2024), 업종별 성별 외식업 이용 정보(File, 2019~2024), 업종별 성별 카드 이용 정보(File, 2018~2025-06), 읍면동 단위 내국인 유동인구(API, 일 갱신).
  - 센터 데이터: 외식업 포스 메뉴 매출(중분류), 외식업 포스 이용 현황(읍면동), 카드 이용 현황(읍면동)_v02.
- AI가 맡는 일:
  - LLM: 질문을 받아 공개 쌍둥이 데이터와 대응하는 센터 데이터를 고른다(공개 명세서 기준). 허용된 도구(필터, 묶어서 집계, 비율, 순위, 그림)만으로 분석 절차를 짜서 공개 데이터에 실행해 보고, 결과를 보며 오류를 고친다. 설명 문장은 값 자리를 비워 둔 틀(예: "{업종 1위}의 비중이 {비중}%로 {증감 방향}했다")과 조건 분기로 미리 써 둔다. 센터에서 무엇을 어느 달·어떤 조건으로 조회할지 "조회 조건 안내"를 만든다.
  - 일반 코드: 공개 데이터와 센터 데이터의 컬럼 대응표 적용, 센터 CSV 형식 검사, 검증된 절차를 센터 CSV에 그대로 실행, 설명 틀의 빈자리를 로컬에서 채우기, 공개 데이터 결과와 센터 데이터 결과의 방향이 크게 다르면 경고, 반출 규칙 적용.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙을 지키는 방법: 작업이 "공개 데이터 단계"와 "센터 데이터 단계"로 나뉜다. 센터 CSV를 불러오는 순간 외부 LLM 호출 기능이 코드에서 잠기고, 외부 전송 기록 화면에 그 뒤 외부 요청이 0건인 것이 보인다. LLM이 쓴 설명 틀은 값을 모른 채 쓰였으므로, 값을 채운 문장은 밖으로 나가지 않는다. 필요하면 로컬 LLM이 문장을 다듬는다(네트워크 사용 없음).
- 시연 방법: 허브 「메뉴별 외식업 매출액」 실제 공개 파일로 "업종별 매출 비중 변화"를 묻고, LLM이 절차를 짜서 실행하고 고치는 과정을 보여 준다. 이어서 명세서 구조로 만든 가상 외식업 포스 메뉴 매출(중분류) CSV를 불러오면 외부 호출이 잠기고, 같은 절차가 로컬에서 실행되어 보고서가 나오며, 외부 전송 기록이 0건으로 남는 장면을 보여 준다. 표시값을 심은 가상 CSV로 외부 요청에 그 값이 없음을 확인하는 자동 테스트도 함께 실행한다.
- 다른 팀과 겹칠 가능성: 중간. "CSV를 넣으면 분석해 주는 범용 분석기"와 데이터 안내 기능(안녕하12, 너굴맨이처리했다구)은 겹친다(브리핑 7절). 하지만 공개 쌍둥이로 절차를 검증한 뒤 센터 데이터에는 값 없이 적용하는 구조는 게시판 질문 목록에 보이지 않는다(브리핑 7절 기준, 다른 팀의 실제 구현은 모른다).
- 가장 큰 위험:
  - 공개 쌍둥이와 센터 데이터의 단위·컬럼이 다를 수 있다. 예를 들어 허브 외식업 파일에 읍면동 구분이 없으면 절차를 그대로 옮길 수 없다. 데이터 분석가의 대응표 확인이 먼저 필요하다.
  - 값을 모르고 쓴 설명 틀은 센터 데이터에서만 나타나는 특이값에 반응하지 못한다. 로컬 코드의 이상값 경고로 보완해야 한다.

### 아이디어 3: 기업 데이터 지배기업 보호 Agent

- 한 줄 요약: 센터의 한국기업데이터(거래처·기업·재무·휴폐업)로 제주 기업의 도내·도외 거래 비중과 업종별 휴폐업 추이를 분석하되, 한두 기업이 칸을 지배해 개별 기업 정보가 드러나는 것을 정책 문자보다 엄격한 기준으로 막는 Agent.
- 누가 쓰나: 제주 산업정책 담당자나 기업지원기관 연구원이 사업계획서나 현황자료에 "제주 제조업체의 도외 구매 비중" 같은 지표를 넣으려는 상황. 센터 이용 목적(논문·현황자료·사업계획서, 브리핑 4절)과 맞는다.
- 해결하는 문제: 기업 단위 데이터는 업종과 지역을 잘게 나누면 한 칸에 기업이 몇 개 없어서, 금액이 10 이상이라 10 미만 규칙은 통과해도 특정 기업의 재무나 거래 규모가 드러날 수 있다. 반출 정책은 경우에 따라 제공처 2차 심사를 한다고 적고 있어 이런 결과는 반려될 가능성이 크다(추론). 이용자는 어느 단위까지 묶어야 안전한지 모른다.
- 쓰는 데이터:
  - 센터 데이터: 거래처정보_구매(2-01), 거래처정보_판매(2-02), 기업정보(2-03), 재무정보_결산(2-05), 휴폐업(2-08). 반출 정책 원문 표에 있는 이름이다.
  - 허브 데이터: 읍면동별 사업체 생멸 통계(File, 2018~2023), 산업 중분류별 사업체 생멸 통계(File, 2018~2023), 제주 경제 통계_산업별 지역 내 총 생산(GRDP)(File, 1985~2019).
- AI가 맡는 일:
  - LLM: 질문에 맞는 지표(도내 거래 비율, 휴폐업률, 업종별 순위처럼 응용집계 위주)와 묶음 단위(산업 대분류·중분류, 권역)를 고르고, 허브 공개 통계와 비교할 항목을 정해 도구를 호출한다. 보호 규칙 때문에 칸이 많이 가려지면 더 큰 묶음을 다시 제안한다.
  - 일반 코드: 칸마다 기업 수를 세어 10개 미만이면 가리기(반출 정책의 10 미만 규칙을 기업 수에도 적용하는 팀 자체 기준), 상위 1~2개 기업이 칸 합계의 큰 몫을 차지하면 가리기(팀 자체 기준), 역산 방지, 기업명·사업자 식별 컬럼이 결과에 절대 나오지 않게 제거, 허브 통계와의 비교 그림, PDF 보고서.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙을 지키는 방법: 외부 LLM은 공개 명세서의 컬럼 정의, 공개 산업분류 이름, 허브 공개 통계만 본다. 센터 기업 데이터는 로컬 코드만 다루고, 기업 데이터 모드에서는 외부 호출을 잠근다. 기업 데이터는 민감도가 높으므로 이 아이디어는 외부 LLM 없이 로컬 LLM만으로 돌리는 선택지도 함께 검토한다.
- 시연 방법: 명세서 구조로 만든 가상 거래처정보_구매 CSV(일부 업종은 기업 3개, 일부 업종은 한 기업이 거래액 대부분을 차지하도록 만든 파일)를 불러와 "제주 제조업 중분류별 도외 구매 비중을 보여 줘"라고 묻는다. Agent가 위험한 칸을 가리고 "이 칸은 기업 수가 적어 개별 기업이 드러날 수 있음"이라고 설명한 뒤, 대분류로 묶은 결과를 제안해 그림과 보고서를 만드는 장면을 보여 준다.
- 다른 팀과 겹칠 가능성: 낮음. 게시판 질문으로 드러난 다른 팀의 구상에 기업 데이터는 없다(브리핑 7절).
- 가장 큰 위험:
  - 한국기업데이터 계열이 현재 명세서(v13, 2026.11.04)에 있는지, 컬럼이 무엇인지 이번에 확인하지 못했다. 반출 정책(2026.09.01)에는 있지만, 브리핑의 센터 조회 화면 캡처 목록에는 보이지 않는다. 컬럼을 모르면 가상 데이터를 명세서 구조대로 만들 수 없다.
  - 거래처 데이터에 상대 기업 이름 같은 식별 정보가 들어 있다면 다루기가 훨씬 까다롭고, 지배기업 기준은 정책에 없는 팀 자체 기준이라 심사자가 받아들이는 기준과 다를 수 있다.
