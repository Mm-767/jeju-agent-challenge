# 사용자 리서처 보고서: 센터·허브 이용자는 누구이고 어디서 막히는가

작성: 사용자 리서처(UX Researcher), 2026-11-13. 근거는 공용 브리핑, 제주데이터허브 데이터목록 xlsx(필요한 이름과 조회수만 인용), 웹 보도 5건이다. 이용자 후기나 인터뷰 자료는 웹에서 찾지 못했기 때문에, 막히는 지점은 브리핑에 정리된 운영 규칙과 게시판 질문에서 거꾸로 도출했다. 이 한계를 전제로 읽어 주기 바란다.

## 결론 5줄

1. 센터는 2019년 개소 때 기업·대학·공공기관·전문 연구자를 대상으로 했고, 2026년 4월 "데이터 프리존" 전환으로 연구계획서 없이 도민·소상공인·예비창업자도 쓰게 됐다. 다만 지금 실제 방문자는 대부분 기관·기업이고 목적은 논문·현황자료·사업계획서다(운영진 답변).
2. 가장 심각하고 자주 막히는 지점은 "어떤 데이터를 어떤 조건으로 받아야 할지 모른다"와 "분석 결과가 반출 심사에서 반려된다"이다. 둘 다 작업을 아예 멈추게 하거나 재방문을 만든다.
3. 그다음은 한 번에 1개월만 조회되어 생기는 파일 여러 개를 합치는 일, 영문 컬럼명과 코드값 해독, SQL·통계 지식 부족이다. 이것들은 시간을 잡아먹는 유형이고 도민·소상공인에게 특히 크다(추론).
4. 이 결과에서 아이디어 세 개를 냈다. 「방문 설계도 Agent」는 집에서 만든 분석 계획을 센터에서 LLM 없이 그대로 실행하고, 「반출 통과 보고서 Agent」는 반출 기준에 맞춰 재집계한 보고서를 만들며, 「공개 데이터 결합 해석 Agent」는 센터 CSV에 허브 공개 데이터를 붙여 맥락을 보여 준다.
5. 다른 팀과 겹칠 가능성은 반출 통과 보고서가 높음, 방문 설계도가 중간, 공개 데이터 결합 해석이 낮음에서 중간이다. 사용자 문제의 크기로는 앞의 두 개가 크고, 겹침을 피하는 쪽으로는 방문 설계도의 "센터에서 LLM 없이 재실행" 부분과 결합 해석이 차별점이 된다(추론).

## 1. 사용자 분석

### 1-1. 확인된 사실

- 2019년 7월 23일 개소 당시 센터는 "이용제한 없는 일반분석실"과 "연구계획 제출시 이용가능한 분야별 데이터랩(관광/모빌리티/거버넌스)실"로 운영됐고, 6개 분야 21개 데이터셋(통신사 생활인구, 신용카드 매출 등)을 제공했다. 대상으로 중소기업, 대학, 공공기관, 전문 연구자가 언급됐다(제주의소리, 인베스트코리아 전재 연합뉴스).
- 2026년 4월 28일 제주테크노파크는 센터를 "데이터 프리존"으로 전환한다고 밝혔다. 연구계획서를 내야 볼 수 있던 내국인 카드 이용 현황, 기업 거래처 정보, 버스 노선별 이용 데이터 등 65종을 간소화된 절차로 쓸 수 있고, 제주데이터허브에서 온라인으로 신청한 뒤 원하는 날 방문하면 바로 쓸 수 있다(헤드라인제주, 파이낸셜뉴스).
- 같은 보도에서 대상은 "데이터에 관심은 있지만 장비와 분석 환경, 전문 지식 부족으로 접근이 어려웠던" 도민과 기업이다. 중소기업·소상공인·예비창업자에게 전문가 컨설팅과 탐색적 데이터 분석(EDA) 수준의 분석을 지원하며, 지난해 실적은 컨설팅 7건과 분석 지원 5건이었다(파이낸셜뉴스, 헤드라인제주).
- 2026년 6월 12일 컨설팅 모집 공고의 대상은 도내 기업(예비창업자 포함), 제주지역 공공기관·연구소, 창업을 준비하는 개인이다. 지원 내용은 기업 요청 기반 데이터 분석 제공과 수집·가공·분석 기술 컨설팅이다(기업마당).
- 브리핑의 운영진 답변: 이용자는 SQL을 쓰지 않고 메뉴로 조회한다. 조회는 한 번에 1개월이고 결과는 영문 헤더 CSV로 내려받는다. 반입은 CSV만 된다. 퇴실 시 반출 승인 자료 외에는 삭제된다.
- 허브 데이터목록 xlsx에서 창업·상권 관련 매쉬업 결과의 조회수가 높은 편이다. 「제주특별자치도_주제3_상권분석을 위한 유동인구에 따른 카드 매출액 변화 데이터 활용_매쉬업결과」 3,319회, 「제주특별자치도_주제1_제주 예비창업자를 위한 업종별 카드 매출과 매장수 데이터 활용_매쉬업 결과」 2,431회, 「제주특별자치도_주제8_유동인구 비율 대비 지역별 인기있는 업종 추천 데이터_매쉬업 결과」 2,221회다. 「일별 기상 정보」(API)는 4,862회다.
- 게시판에서 소상공인이 자기 가게 매출과 센터 데이터를 비교하려는 질문(한콩이아빠)이 있었다(브리핑 7절).

### 1-2. 해석

- 공식 대상은 넓어졌지만 실제 방문자는 아직 기관·기업 중심이다. 지난해 사람이 직접 도운 분석 지원이 컨설팅과 분석을 합쳐 12건이라는 점은, 데이터 활용을 도와줄 손이 부족하다는 신호로 읽을 수 있다(추론). 이 숫자를 "수요가 적다"는 뜻으로 읽어 아이디어를 거르지는 않았다.
- 2026년 전환으로 앞으로 처음 오는 이용자, 특히 데이터 경험이 적은 도민의 비율이 늘 가능성이 있다(추론). 대회가 "IT 비전문가 도민"을 명시한 것도 같은 방향이다(사실: 브리핑 1절).

### 1-3. 사용자 유형

| 유형 | 근거 | 주 목적 | 데이터 역량(추론) |
|---|---|---|---|
| 기관 실무자 (공공기관·연구소·도 산하기관) | 운영진 답변 "대부분 기관", 컨설팅 공고 대상 | 현황자료, 정기 보고서 | 엑셀 중급, SQL 없음 |
| 연구자·대학원생 | 개소 보도 "대학, 전문 연구자", 운영진 답변 "논문" | 논문용 표·그림 | 통계 지식 있음, 데이터 정리 시간 부담 |
| 기업 실무자 (중소기업 기획·마케팅) | 개소·전환 보도, 컨설팅 공고 | 사업계획서, 시장 파악 | 편차 큼 |
| 소상공인·예비창업자·일반 도민 | 2026 전환 보도, 대회 조건, 게시판 질문 | 창업 입지·업종 판단, 사업계획서 | 낮음 |

페르소나는 이용 목적이 가장 다른 세 유형으로 만들었다. 기업 실무자는 사업계획서라는 목적이 소상공인과, 보고서라는 산출물이 기관 실무자와 겹쳐서 따로 세우지 않았다.

## 2. 페르소나

### 소상공인 A (제주시 읍 지역에서 카페 창업을 준비하는 예비창업자)

- 목표: 가게를 낼 동네와 손님이 몰리는 시간대를 정하고, 사업계획서에 "데이터로 본 상권" 한 쪽을 넣는다.
- 역량(추론): 스마트폰과 엑셀 기초는 다룬다. SQL과 통계는 모른다. 일상에서 생성형 AI 대화 서비스는 써 봤다.
- 방문 전: 허브에서 이용을 신청한다. 센터 데이터 65종과 허브 데이터 1,259건 가운데 무엇을 봐야 할지 모른다. 명세서를 열어도 컬럼명이 base_year_month, bjd, biz_cd, user_type처럼 영문이라 뜻을 짐작해야 한다.
- 방문 중: 조회 화면에서 데이터 선택, 기간 1개월, 조건(같다·같지않다, And·Or)을 고른다. 1년 추세를 보려면 같은 조회를 12번 반복한다. 파일명이 Results_YYYYMMDD_HHMMSS.csv라서 어느 파일이 몇 월인지 헷갈린다. 엑셀에서 피벗으로 묶는 법을 모른다. 평소 쓰던 외부 AI 서비스에 표를 붙여 넣고 해석을 물으면 규칙 위반이다.
- 방문 후: 그래프를 가져가려고 반출을 신청한다. 읍면동, 업종, 연령을 동시에 나눈 칸 일부가 10 미만이라 반려될 수 있고, 활용 사유도 "(툴/분석방법)으로 분석 후 (가공처리)로 가공하여 (내용)의 보고서 작성 및 (어디)에 활용" 수준으로 써야 한다. 반려되면 퇴실 때 파일이 지워졌으니 다시 와서 처음부터 한다.
- 가장 크게 막히는 곳: 데이터 선택, 도구 지식 부족, 반출.

### 기관 실무자 B (도 산하기관 관광 담당, 분기마다 소비 현황자료 작성)

- 목표: 분기마다 내국인·중국인 관광객 카드 소비 현황 보고서를 새 달 데이터로 갱신한다. 표와 그림 구성은 지난번과 같다.
- 역량(추론): 엑셀 피벗과 차트는 능숙하다. SQL과 통계 모형은 쓰지 않는다.
- 방문 전: 지난 분기 보고서 틀은 있다. 하지만 지난번에 어떤 데이터를 어떤 조건으로 받았는지는 기억이나 메모에 의존한다(추론).
- 방문 중: 3개월에 데이터 2~3종이면 조회와 다운로드를 6~9번 한다. 지난번과 같은 조건으로 받았는지 확인하기 어렵다(추론). 합계 행을 넣으면 작은 칸이 역산될 수 있다.
- 방문 후: 텍스트·스프레드시트는 원칙적으로 반출이 안 되니, 센터 안에서 PDF 보고서까지 완성해야 한다. 사무실에서 엑셀로 다시 다듬을 수 없다.
- 가장 크게 막히는 곳: 반출, 월별 파일 관리, 매번 같은 작업의 반복.

### 연구자 C (대학원생, 관광 소비와 유동인구·날씨의 관계를 다루는 논문)

- 목표: 여러 해의 월별 패널 자료를 만들어 회귀분석을 하고, 논문에 넣을 표와 그림을 가져간다.
- 역량(추론): R이나 Python으로 통계 분석은 하지만 데이터 정리에 시간을 많이 쓴다.
- 방문 전: 허브 공개 데이터(「읍면동 단위 내국인 유동인구」 API, 「일별 기상 정보」 API)는 집에서 받는다. 허브의 카드 데이터 API는 대부분 2016~2018년 자료라 최신 소비는 센터 데이터를 써야 한다(사실: 브리핑 6-2절).
- 방문 중: 센터 카드 데이터 수십 개월을 월별로 받거나 운영자에게 요청한다(바탕화면 "요청파일" 폴더). 센터 카드 데이터의 지역은 법정동(bjd, 73개)인데, 허브 유동인구는 "읍면동 단위"라서 두 단위가 같은 체계인지 확인해야 한다(체계 차이 여부는 확인 필요).
- 방문 후: 회귀 결과표를 반출할 때 원자료가 역산되지 않는지 심사받는다. 퇴실 시 정리한 패널 자료가 지워지면 다음 방문에 다시 만든다.
- 가장 크게 막히는 곳: 월별 파일 합치기, 공개·센터 데이터의 지역 단위와 기간 맞추기, 반출.

## 3. 막히는 지점 순위

판정 기준을 세 페르소나 모두에 같게 적용했다. 심각도는 "작업이 멈추거나 재방문이 필요함"을 높음, "시간이 크게 듦"을 중간, "불편함"을 낮음으로 했다. 빈도는 세 페르소나 중 몇 명이 겪는지와 매 방문마다 생기는지로 판정했다.

| 순위 | 막히는 지점 | 심각도 | 빈도 | 사실 근거 | 추론 부분 |
|---|---|---|---|---|---|
| 1 | 어떤 데이터·조회 조건을 골라야 할지 모름 | 높음 | 높음 (A·C, 첫 방문마다) | 센터 65종·허브 1,259건, 게시판의 데이터 안내·받을 파일 목록 기능 질문, 컨설팅 사업 존재 | 프리존 전환으로 첫 방문자가 늘 것 |
| 2 | 반출 반려(10 미만 미처리, 역산 가능, 활용 사유 부족, 스프레드시트 불가) | 높음 | 높음 (A·B·C 모두 결과를 밖에서 써야 함) | 반출 규칙과 반려 사유(브리핑 5절), 반출 점검 질문 3팀, CSV가 작은 값을 가리지 않은 원본이라는 참가자 전언 | 이용자가 기준을 미리 모른 채 신청할 것 |
| 3 | 한 번에 1개월 조회, 타임스탬프 파일명, 여러 파일 합치기 | 중간 | 높음 (B·C는 매번, A도 추세를 보려면) | 브리핑 4절 | 파일 혼동이 실제로 잦을 것 |
| 4 | SQL·통계·도구 지식 부족 | A에게 높음, 전체 중간 | 중간 (A 크게, B 일부) | 메뉴 조회 방식, 대회의 IT 비전문가 조건, 보도의 "전문 지식 부족" | A 같은 이용자 비율 |
| 5 | 영문 컬럼명과 코드값(bjd, biz_mid_cd의 Q06, user_type, tour_type, user_cnt와 use_cnt 구분) | 중간 (잘못 해석할 위험) | 높음 (모두) | CSV 헤더 영문, 컬럼 목록(브리핑 6-1절) | 명세서 한글 설명의 충실도는 미확인 |
| 6 | 퇴실 시 삭제로 중간 결과가 남지 않음 | 중간 | 중간 (B·C처럼 여러 번 오는 이용자) | 브리핑 4절 | 재방문 시 같은 정리를 반복할 것 |
| 7 | 외부 생성형 AI를 센터 데이터에 쓸 수 없음 | 중간 | 중간 | 외부 LLM 규칙(브리핑 4절) | 평소 AI로 해석을 받던 이용자가 도움을 잃을 것 |
| 8 | 공개 데이터와 센터 데이터의 지역 단위·기간 불일치 | C에게 높음 | 낮음 (결합 분석 이용자) | 센터 카드는 법정동 73개, 허브 카드 API는 2016~2018년 | 법정동과 허브 읍면동이 다른 체계인지 |
| 9 | 방문 자체의 부담 | 중간 | 높음 | 비공개 데이터는 방문해야 받음, 보도의 "위치 정보 등록, 접근성 개선" | Agent로 직접 풀기 어려워 아이디어에서 제외 |

1위와 2위는 근거가 가장 단단하다. 운영 규칙이 그렇게 되어 있다는 사실과 다른 참가자들이 같은 문제를 게시판에서 물었다는 사실이 함께 있기 때문이다. 3위부터 5위는 규칙상 반드시 생기는 일이지만 이용자가 얼마나 괴로워하는지는 추론이다.

## 4. AI Agent 아이디어 3개

세 아이디어를 같은 기준으로 먼저 비교한다. 평가 기준은 어떤 막히는 지점을 푸는지, 다른 팀과 겹칠 가능성, 가상 데이터로 평가 환경에서 돌아가는지(시연 가능성), 5일 안 구현 부담이다. 구현 부담은 AI 엔지니어의 확인이 필요한 추론이다.

| 아이디어 | 푸는 막히는 지점(순위) | 겹칠 가능성 | 시연 가능성 | 구현 부담(추론) |
|---|---|---|---|---|
| 방문 설계도 Agent | 1, 3, 5, 7 | 중간 | 높음 (실행 단계는 인터넷 없이 돎) | 중간 |
| 반출 통과 보고서 Agent | 2, 4, 6 | 높음 | 높음 (거의 전부 로컬) | 중간 |
| 공개 데이터 결합 해석 Agent | 8, 3, 4 | 낮음~중간 | 중간 (허브 API 키와 응답에 의존) | 중간~높음 |

### 아이디어 1: 방문 설계도 Agent

- 한 줄 요약: 이용자가 목적을 한국어로 말하면 받아야 할 센터 데이터, 조회 조건, 월별 다운로드 체크리스트, 분석 순서를 "설계도 파일"로 만들어 주고, 센터에서는 내려받은 CSV 폴더만 지정하면 일반 코드가 설계도대로 분석을 끝낸다.
- 누가 쓰나: 소상공인 A가 첫 방문 전날 집에서 설계도를 만들고, 다음 날 센터 PC에서 실행한다. 연구자 C가 연구 설계 단계에서 필요한 월과 조건을 빠짐없이 정리할 때도 쓴다.
- 해결하는 문제: 무엇을 받아야 할지 몰라 센터에서 시간을 허비하는 문제, 12개월치를 받고 합치는 수작업, 영문 컬럼 해독, 센터 안에서 AI 도움을 못 받는 문제.
- 쓰는 데이터: 센터 데이터는 「카드 이용 현황(읍면동)_v02」, 「카드 이용 현황(시간대)」(정확한 판 표기는 명세서 확인 필요), 「제주도 내 업종별 매장 수」. 허브 데이터는 「읍면동 단위 내국인 유동인구」(API, 일 갱신)와 「제주특별자치도 상가(상권) 정보」(File)다.
- AI가 맡는 일: LLM은 목적 문장을 해석하고, 공개 명세서와 허브 목록에서 후보 데이터를 검색해 고르고, 조회 조건과 기간을 계획하고, 허브 API를 도구로 호출해 공개 데이터로 미리보기를 만든 뒤 설계도를 쓴다. 일반 코드는 설계도 형식 검증, CSV 헤더로 데이터 종류 판별, 파일명 대신 base_year_month로 월 판별과 누락 월 경고, 월별 파일 합치기, NA 처리, 설계도에 적힌 집계와 차트, 컬럼 한글 라벨 붙이기를 맡는다.
- 외부 LLM 규칙 준수: 설계 모드와 실행 모드를 나눈다. 설계 모드에서 LLM이 보는 것은 이용자의 목적 문장, 공개 명세서, 허브 공개 데이터뿐이다. 실행 모드는 LLM 호출 코드를 아예 불러오지 않고 네트워크 호출도 하지 않으며, 설계도에 정해진 계산만 한다. 그래서 센터 CSV 값이 외부로 나갈 경로가 구조적으로 없다.
- 시연 방법: 평가자가 설계 모드에서 "읍 지역 카페 창업, 최근 1년 시간대별 손님 흐름"을 입력하면 체크리스트가 나온다. 이어서 명세서 구조대로 만든 가상 Results_*.csv 12개가 든 폴더를 실행 모드에 지정하면, 합친 표와 시간대 차트, 컬럼 한글 설명이 나온다. 인터넷을 끊은 상태에서도 실행 모드가 도는 장면을 함께 보여 준다.
- 다른 팀과 겹칠 가능성: 중간. 앞부분인 데이터 안내는 안녕하12(데이터 안내와 로컬 LLM), 너굴맨이처리했다구(받을 파일 목록 안내)와 겹친다. 설계도를 센터에서 LLM 없이 그대로 재실행하는 연결은 게시판에 드러난 구상에 없다(추론).
- 가장 큰 위험: 공개 명세서의 컬럼 설명이 빈약하면 LLM의 계획이 틀린다. 설계도가 다룰 수 있는 데이터와 분석 종류를 넓히면 5일 안에 끝나지 않으므로, 지원 데이터를 3~4종으로 좁혀야 한다.

### 아이디어 2: 반출 통과 보고서 Agent

- 한 줄 요약: 센터 CSV로 만든 집계표를 반출 기준(10 미만 범주처리, 역산 방지)에 맞게 자동 재집계하고, 그림이 들어간 PDF 보고서와 반출 신청서의 활용 사유 문장 초안까지 만든다.
- 누가 쓰나: 기관 실무자 B가 분기 보고서를 센터 안에서 완성해 반출 신청할 때. 소상공인 A가 사업계획서에 넣을 그림을 가져갈 때.
- 해결하는 문제: 반려로 인한 재방문, 퇴실 시 삭제 때문에 센터 안에서 끝내야 하는 압박, 반출 가능한 형식(PDF, 그림)으로 직접 만들 도구 지식 부족.
- 쓰는 데이터: 센터 데이터는 「내국인·중국인 카드 이용 현황과 이용 금액(관광업종)」과 「외식업 포스 이용 현황」. 허브 데이터는 비교 맥락용 「방문목적별 입도객 현황」(API, 2025-07까지)이다.
- AI가 맡는 일: LLM은 이용자의 목적 문장과 공개 명세서의 컬럼 정의만 보고 집계 축, 차트 종류, 작은 칸이 생길 때 묶을 상위 단위의 순서(예: 법정동 대신 지역구분 7권역, 세부 연령 대신 넓은 연령대)를 정책으로 정한다. 활용 사유 문장도 브리핑에 나온 형식에 맞춰 목적 문장과 실행 단계 기록(숫자 제외)으로 초안을 쓴다. 일반 코드는 실제 칸 값 검사, 정책에 따른 반복 재집계, 합계와 차이로 역산되는지 검사, 해석 문장의 숫자 채우기(템플릿), PDF 생성, 결과 삭제 기능 켜기·끄기를 맡는다.
- 외부 LLM 규칙 준수: 어떤 칸이 10 미만인지는 값에서 나온 정보이므로 LLM에 보내지 않는다. 집계값 전송은 센터 심의 대상이라 아예 보내지 않는다. 숫자가 들어가는 문장은 전부 코드가 템플릿으로 만든다.
- 시연 방법: 일부러 10 미만 칸을 섞은 가상 CSV를 넣으면 검사 결과에 작은 칸 목록이 나오고, 권역 단위로 재집계한 뒤 작은 칸이 없어진 표, PDF 보고서, 활용 사유 초안이 차례로 나온다.
- 다른 팀과 겹칠 가능성: 높음. 반출 점검은 beebird, sanhapark, 강태우("반출 점검 메모")가 게시판에서 직접 물었고, 현황보고서 Agent(river.kim)와도 겹친다.
- 가장 큰 위험: 센터가 허용 범위를 사전에 확정해 주지 않으므로 Agent의 "통과" 판정과 실제 심사가 다를 수 있다. "통과 보장"이 아니라 "사전 점검"으로 표현하지 않으면 결과 신뢰성 항목에서 불리하다(추론). 경쟁 쏠림이 커서 상호평가에서 비슷한 기획서와 나란히 비교될 가능성이 높다(추론).

### 아이디어 3: 공개 데이터 결합 해석 Agent

- 한 줄 요약: 이용자가 센터 CSV와 조회 조건을 넣으면, Agent가 같은 기간·지역의 허브 공개 데이터(날씨, 유동인구, 버스 승객, 입도객)를 API로 찾아 붙이고, 센터 수치와 나란히 볼 맥락 지표와 차트를 만든다.
- 누가 쓰나: 연구자 C가 논문 변수를 한 표로 합칠 때. 기관 실무자 B가 "이번 달 소비가 왜 달라 보이는가"에 날씨·입도객 맥락을 덧붙일 때.
- 해결하는 문제: 출처마다 지역 단위와 기간이 달라 직접 맞추기 어려운 문제, 결합과 비교에 필요한 통계·코딩 지식 부족. 허브가 2021년 무렵 사람 손으로 만든 매쉬업 결과(예: 상권분석을 위한 유동인구에 따른 카드 매출액 변화)를 이용자가 원하는 기간으로 자동 재현하는 셈이다.
- 쓰는 데이터: 센터 데이터는 「카드 이용 현황(읍면동)_v02」와 「외식업 포스 이용 현황」. 허브 데이터는 「일별 기상 정보」(API, 일 갱신), 「읍면동 단위 내국인 유동인구」(API, 일 갱신), 「버스 일일 승객수 데이터」(API, 일 갱신), 「방문목적별 입도객 현황」(API)이다.
- AI가 맡는 일: LLM은 공개 명세서의 컬럼 정의와 이용자가 화면에서 고른 조회 조건을 보고 붙일 허브 데이터와 결합 키를 계획하고, 허브 API를 도구로 호출한다. 허브 데이터 자체는 공개 데이터라 LLM이 자유롭게 요약·해석한다. 일반 코드는 지역 코드 매핑, 월 단위 결합, 전년 같은 달 비교와 상관 계산, 차트, 센터 값이 들어간 문장의 템플릿 생성을 맡는다.
- 외부 LLM 규칙 준수: LLM에는 CSV 안의 값을 보내지 않는다. 기간과 지역은 이용자가 화면에서 고른 조건을 쓴다. 센터 수치와 공개 데이터를 함께 해석하는 문장은 코드 템플릿으로만 만든다. 조회 조건 자체를 보내도 되는지는 컴플라이언스 확인이 필요하다.
- 시연 방법: 가상 카드 CSV 3개월치를 넣으면 Agent가 실제 허브 API에서 같은 기간의 날씨와 입도객을 가져와 붙이고, 비 온 날 수와 카드 이용 건수를 나란히 놓은 차트와 "상관은 인과가 아니다"라는 한계 문구가 나온다.
- 다른 팀과 겹칠 가능성: 낮음에서 중간. 게시판에서 센터 데이터와 허브 공개 데이터의 결합을 직접 밝힌 팀은 없다. 다만 "CSV를 넣으면 분석해 주는 범용 분석기" 묶음으로 보일 수 있다(추론).
- 가장 큰 위험: 센터 카드 데이터의 법정동과 허브의 읍면동이 다른 체계라면 매핑이 틀릴 때 결합 결과 전체가 틀린다. 평가 실행이 허브 API 키와 응답에 의존하므로, 키 문제나 장애가 나면 핵심 장면이 안 나온다. 허브 데이터를 ZIP에 미리 넣어 두는 대비가 필요하다(브리핑상 허용됨).

## 5. 다른 팀원이 확인해 주면 좋을 질문

- 제주 도메인 전문가에게: 소상공인·예비창업자가 사업계획서에 데이터를 넣어야 하는 실제 상황(창업 지원 사업, 정책자금 서식 등)이 제주에 있는가. 데이터 프리존 전환 뒤 도민 방문이 실제로 늘었는가.
- 데이터 분석가에게: 센터 명세서(v13) 엑셀에 컬럼별 한글 설명과 코드표가 들어 있는가. 방문 설계도 Agent는 이것이 핵심 전제다. 센터 카드 데이터의 bjd(법정동 73개)와 허브 「읍면동 단위 내국인 유동인구」의 지역 단위가 같은 체계인지, 매핑표를 구할 수 있는지. 같은 데이터의 v01과 v02 컬럼이 달라 월별 합치기에 문제가 생기는지.
- AI 엔지니어에게: 설계 모드(외부 LLM)와 실행 모드(LLM 없음)를 나누는 구조를 5일 안에 만들 수 있는지. 설계 모드를 로컬 소형 모델로 대신할 때 GTX 1060 3GB나 CPU로 쓸 만한 속도와 품질이 나오는지.
- 경쟁 분석가에게: 반출 점검과 데이터 안내 쪽 팀이 게시판 밖에서도 얼마나 될지, 센터·허브 데이터 결합을 구상하는 팀 신호가 있는지.
