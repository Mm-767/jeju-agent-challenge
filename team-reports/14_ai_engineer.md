# AI 엔지니어 보고서: 센터 값을 외부로 보내지 않으면서 AI가 실질적인 역할을 하는 에이전트 구조

작성 2026-11-13, AI 엔지니어(LLM·에이전트 설계 담당). 근거는 공용 브리핑(00_brief.md), 제주데이터허브 데이터 목록 xlsx(필요한 데이터 이름만 인용), 이번에 직접 확인한 웹 페이지(맨 끝 출처 목록)다. 확인하지 못한 수치에는 "추정", 근거 없는 판단에는 "추론"을 붙였다.

## 결론 5줄

1. 추천 구조는 "스키마 계획형"이다. 외부 LLM은 사용자 질문과 공개 명세(컬럼명·코드표)만 보고 분석 계획을 쓴다. 계산은 센터 PC 안의 코드가 하고, 숫자는 LLM을 거치지 않은 채 코드가 표·차트·문장 빈칸에 채운다.
2. AI 역할을 키우는 핵심 장치는 "가상 데이터 리허설"이다. 명세대로 만든 가상 데이터로 계획을 먼저 돌려 보고, 그 오류를 LLM에 돌려줘 고치게 한다. 센터 값을 한 개도 보내지 않으면서 계획, 실행, 검증, 재시도 고리가 실제로 돈다.
3. 로컬 소형 LLM은 핵심 경로에 넣지 않는다. Ollama는 GTX 1060을 지원하지만 드라이버 570 이상이 필요하다. 3GB VRAM에 다 들어가는 한국어 모델은 2B 안팎뿐이다. 개발자에게 같은 하드웨어가 없어서 속도도 측정할 수 없다.
4. 아이디어는 세 개다. 「반출 기준을 스스로 맞추는 현황보고서 분석 비서」는 겹칠 가능성이 높다. 「축제·행사 효과 측정 에이전트」와 공개 데이터만 쓰는 「농산물 시세 브리핑 에이전트」는 낮다. 셋 다 같은 엔진(계획, 리허설, 로컬 실행, 빈칸 채움 보고서)을 공유한다.
5. 가장 큰 기술 함정은 "마스킹한 집계표를 외부 LLM에 보내 해석 문장을 받는 구조"다. 다른 팀이 몰린 방향이고(브리핑 7절), 센터가 집계값 전송의 허용 범위를 미리 확정해 주지 않았다(브리핑 4절, 11/7·11/10 답변).

## 1. 에이전트 구조 비교

### 1-1. 비교한 네 가지 구조

- **스키마 계획형**: 외부 LLM(Claude 등)이 질문과 공개 명세만 보고 분석 계획(정해진 형식의 JSON)을 만든다. 센터 PC의 로컬 코드가 그 계획을 DuckDB SQL로 바꿔 실행하고, 검사하고, 표·차트·보고서를 만든다. 계획은 실행 전에 "가상 데이터 리허설"로 미리 검증한다.
- **로컬 소형 LLM 단독형**: 센터 PC에서 Ollama로 2B 안팎 모델을 돌린다. 외부 통신 없이 LLM이 값을 직접 보고 해석까지 한다.
- **혼합형**: 스키마 계획형에 로컬 소형 LLM을 더한다. 계획은 외부 LLM이 하고, 센터 값을 봐야 하는 해설 문장은 로컬 LLM이 쓴다. 로컬 LLM이 쓴 숫자는 코드가 계산 결과와 대조한다.
- **공개 데이터 전면형**: 외부 LLM은 제주데이터허브 공개 데이터(값을 보내도 되는 데이터)만 다루며 자유롭게 계획, 도구 호출, 해석을 한다. 센터 CSV 분석은 미리 정해 둔 분석 메뉴를 코드가 실행한다.

### 1-2. 비교표

| 구조 | AI 역할 크기 | 설치 난이도(비개발자 매뉴얼) | 운영 비용 | 주요 실패 모드 | 숫자 환각 방지 | 구현 난이도(1명·5일) |
|---|---|---|---|---|---|---|
| 스키마 계획형 | 큼 | 쉬움 | 질문당 수 원~백 원 수준(추정) | 외부 API 차단, 계획 오류 | 구조적으로 차단 | 중간, 5일 가능 |
| 로컬 소형 LLM 단독형 | 중간~작음 | 어려움 | 0원 | 느림, JSON 깨짐, 드라이버 | 약함, 검증기 필요 | 높음, 시험 환경 없음 |
| 혼합형 | 가장 큼 | 가장 어려움 | 낮음 | 두 구조의 실패 모두 | 검증기에 의존 | 가장 높음, 5일 빠듯 |
| 공개 데이터 전면형 | 공개 데이터 부분만 큼 | 쉬움 | 낮음 | 센터 데이터 부분이 단순 메뉴로 보임 | 공개 데이터는 검증기, 센터는 코드 | 낮음 |

### 1-3. 구조별 설명

**스키마 계획형 (추천).** 외부 LLM이 맡는 일은 질문 이해, 필요한 센터·허브 데이터 찾기, 분석 계획 작성, 리허설 결과를 보고 계획 고치기, 보고서 문장 쓰기(숫자 자리는 빈칸)다. 설치는 Python과 pip 패키지, API 키 환경변수 하나라 배치 파일 두 개(설치용, 실행용)로 끝낼 수 있다. 비용은 1-4절에 정리했다.

가장 큰 실패 모드는 평가 환경이나 센터의 DLP가 외부 API 주소를 막는 경우다. 막히면 LLM 단계 전체가 멈추므로, 외부 LLM 없이 미리 정해 둔 분석 메뉴로 돌아가는 강등 모드를 반드시 둔다. 외부 주소는 기획서에 적으면 허용 목록에 등록할 수 있다(브리핑 4절). 두 번째 실패 모드는 LLM이 명세에 없는 컬럼을 쓰거나 형식이 틀린 계획을 내는 경우다. 로컬 정적 검사기와 리허설이 잡아낸 뒤 다시 고치게 한다.

숫자 환각은 구조상 생기지 않는다. LLM이 센터 값을 본 적이 없고, 보고서 숫자는 전부 코드가 계산 결과에서 채우기 때문이다. 5일 일정은 1-5절에 적었다.

**로컬 소형 LLM 단독형.** 외부 통신이 없어서 규정 측면에서는 가장 깔끔하다. 대신 AI 역할이 작아진다. 2B 안팎 모델은 여러 단계 계획과 도구 선택을 안정적으로 하기 어렵다(추론). 그래서 실제로 맡길 수 있는 일은 "질문을 정해진 분석 유형과 조건으로 바꾸기" 정도다.

설치 매뉴얼에는 NVIDIA 드라이버 570 이상 업데이트, Ollama 설치, 모델 내려받기(1~3GB)가 추가된다. 어느 단계든 실패하면 평가자가 전체를 실행하지 못할 수 있다. 값을 직접 보는 모델이 해설 문장에 숫자를 쓰므로 환각 위험도 가장 크다.

결정적인 약점은 개발자에게 GTX 1060 3GB와 같은 시험 환경이 없다는 점이다. 평가는 "센터 운영환경과 최대한 비슷한 환경"에서 하므로(브리핑 3절), 측정해 보지 않은 속도가 그대로 감점 요인이 될 수 있다.

**혼합형.** 기술 점수만 보면 가장 화려하다. 로컬 LLM이 값을 보고 "애월읍은 전년 같은 달보다 줄었다" 같은 해석을 쓸 수 있기 때문이다. 하지만 두 구조의 실패 모드를 모두 떠안고, 로컬 LLM이 쓴 문장 속 숫자와 방향을 하나하나 대조하는 검증기까지 만들어야 한다. 5일 안에는 빠듯하다. 스키마 계획형을 다 만든 뒤 시간이 남을 때 "선택 기능(기본 꺼짐)"으로만 붙이는 것이 맞다.

**공개 데이터 전면형.** 허브 공개 데이터는 외부 전송 제한이 없어서(브리핑 4절) LLM이 값을 보고 자유롭게 일할 수 있다. 에이전트다움을 보여 주기 가장 쉽다. 단, 센터 데이터 부분이 "정해진 메뉴 실행"에 머물면 운영진이 말한 "AI가 어떤 역할을 하는지"에서 센터 데이터 분석의 AI 역할이 약해 보인다(추론). 아이디어 3처럼 공개 데이터만으로 주제를 완결하거나, 스키마 계획형과 합쳐 쓰는 편이 낫다.

### 1-4. 외부 LLM 비용 추정

Claude API 개발 참고 자료(2026-11-03 기준 가격표)에 따르면 다음과 같다.

| 모델 | 모델 ID | 입력 100만 토큰당 | 출력 100만 토큰당 | 비고 |
|---|---|---|---|---|
| Claude Haiku 5.5 | `claude-haiku-5-5` | 0.10달러 | 0.50달러 | 프롬프트 10만 토큰 이하 기준 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | 2달러 | 10달러 | |

캐시에서 읽는 입력은 정가의 약 0.1배다.

질문 하나에 입력 2만 토큰(명세·도구 정의·리허설 왕복 누적), 출력 3천 토큰이 든다고 가정하면 다음과 같다. 이 사용량은 가정이다.
- Haiku 5.5: 입력 0.002달러와 출력 0.0015달러를 더해 질문당 약 0.0035달러다. 1달러를 1,400원으로 가정하면 약 5원이다.
- Sonnet 5.5: 입력 0.04달러와 출력 0.03달러를 더해 질문당 약 0.07달러, 약 100원이다.
- 명세와 도구 정의는 질문마다 같으므로 프롬프트 캐시를 쓰면 입력 비용이 더 내려간다.

어느 모델을 쓸지는 시험 질문 30개쯤으로 "계획이 한 번에 검사를 통과하는 비율"과 "리허설 재시도 횟수"를 측정한 뒤 정하자. Haiku 5.5는 거절했을 때 서버 쪽 대체 모델이 없다는 점도 참고 자료에 적혀 있다. 평가용 키의 사용 한도는 대회가 설정을 허용했다(브리핑 4절). Anthropic Console 쪽 지출 한도 기능은 참고 자료에 "미리보기 단계"로 적혀 있어서 실제로 설정할 수 있는지 확인이 필요하다.

### 1-5. 스키마 계획형 5일 구현 범위 (개발자 1명 기준 추정)

- 1일차: 센터 데이터 명세 엑셀 파싱, 명세 기반 가상 데이터 생성기, 분석 계획 JSON 형식 정의, 계획을 DuckDB SQL로 바꾸는 변환기.
- 2일차: LLM 계획 작성, 리허설, 수정 고리. 질문 검문기와 외부 전송 기록.
- 3일차: 10 미만 검사, 재집계 사다리, 합계 검산, 역산 가능성 검사.
- 4일차: 차트(한글 폰트), 빈칸 채움 보고서, PDF 출력, 화면(Streamlit 같은 로컬 웹 화면).
- 5일차: Windows 설치·실행 배치 파일, 비개발자 매뉴얼, 강등 모드, 평가 시나리오 통째 실행 시험.

가상 데이터 생성기는 개발용, 평가 제출용 더미 데이터, 실행 중 리허설에 모두 쓰이는 한 부품이다. 그래서 가장 먼저 만든다.

## 2. 외부로 보내는 것과 보내지 않는 것 (설계 규칙)

센터 데이터 규칙(브리핑 4절)을 코드로 강제하는 방법이다. 기술적 차별점이기도 해서 기획서에 표로 넣기를 권한다.

| 구분 | 내용 | 처리 |
|---|---|---|
| 외부로 보내도 되는 것 | 사용자 질문(검문 통과 후), 센터 데이터 명세의 공개 내용(컬럼명, 코드표, 설명), 허브 공개 데이터 값, LLM이 만든 계획, 데이터 없이 판단한 계획 문법 오류, 가상 데이터 리허설의 실행 결과 | 그대로 전송, 전부 기록 |
| 기본값으로 보내지 않는 것 | 센터 CSV의 셀 값, 행 수, 집계값, 데이터에서 나온 오류 메시지 원문, 10 미만 칸의 위치 | 코드에서 차단 |
| 센터 판단이 필요한 회색 영역 | 실제 데이터에 대한 "검사 통과/실패" 한 비트 신호, 컬럼별 결측 여부 | 설정으로 켜고 끌 수 있게 하고 기본은 끔. 끈 상태에서는 로컬 규칙이 다음 단계를 정함 |

구현 장치는 세 가지다.
- **질문 검문기**: 외부로 나가는 모든 문자열을 검사한다. 불러온 CSV의 숫자 값과 공개 코드표에 없는 문자열 값이 들어 있으면 막는다. 질문 속 날짜·기간이 아닌 숫자는 "[숫자1]" 같은 자리표시자로 바꿔 보낸다. 브리핑 4절에 "질문 문장에 센터 데이터 값이 들어가 외부로 가도 외부 전송"이라고 했기 때문에 필요하다.
- **오류 메시지 정화**: 실제 데이터 실행에서 난 오류는 "오류 종류와 관련 컬럼명"만 남긴다. pandas·DuckDB 오류 원문에는 셀 값이 섞일 수 있다.
- **외부 전송 기록 화면**: 외부 LLM에 보낸 내용을 호출마다 원문 그대로 남긴다. 센터 담당자와 평가자가 "값이 안 나갔다"는 것을 직접 확인할 수 있다. 결과 신뢰성 점수(15점)의 근거 자료가 된다.

## 3. 로컬 소형 LLM 조사

### 3-1. 실행 도구

- **Ollama**: 공식 문서에 "compute capability 5.0 이상, 드라이버 550 이상" 지원이라고 적혀 있다. GTX 1060은 6.1 행에 들어 있다. 다만 "5.0~6.2는 드라이버 570 이상"이 필요하다. Windows에서는 Vulkan 백엔드도 기본으로 켜진다고 적혀 있다(출처 1). 센터 PC의 현재 드라이버 버전은 모른다. 설치 매뉴얼에 드라이버 업데이트 단계가 들어가야 할 수 있다.
- **llama.cpp**: GitHub 배포본(Windows용 CUDA·Vulkan 빌드)과 GGUF 파일을 따로 내려받는 방식이다. 비개발자 매뉴얼로는 Ollama보다 단계가 많다(추론). Python 바인딩(llama-cpp-python)은 Windows에서 빌드 도구가 필요할 수 있어 피하는 게 좋다(기억 기반, 이번에 확인 안 함).

### 3-2. 후보 모델

| 모델 | 크기(Ollama 다운로드 기준) | 3GB VRAM에 다 들어가나 | 한국어 | 라이선스 | 확인 수준 |
|---|---|---|---|---|---|
| qwen3:1.7b | 1.4GB | 들어감(추정) | 다국어 지원(이번에 확인 안 함) | 이번에 확인 못 함 | 크기는 확인(출처 2) |
| qwen3:4b | 2.5GB | 빠듯함. 화면 출력과 KV 캐시 몫 때문에 일부가 CPU로 넘어갈 가능성 큼(추정) | 위와 같음 | 이번에 확인 못 함 | 크기는 확인(출처 2) |

라이선스로 보면 Apache 2.0이 확인된 Kanana 1.5 2.1B와 Qwen3.5 계열이 안전하다. 센터가 결과물을 운영에 탑재하는 것(브리핑 1절)이 "상업적 이용"에 해당하는지는 컴플라이언스 확인이 필요하다. 비상업 조건 모델(EXAONE NC, Qwen2.5-3B)은 그 답이 나오기 전까지 쓰지 않는 게 좋다.

### 3-3. 속도 (전부 추정)

GTX 1060에서 실제로 측정한 llama.cpp 벤치마크는 찾지 못했다. 찾은 자료(willitrunai)는 스스로 추정치라고 밝혔고, 1B가 3B보다 느리게 나오는 등 앞뒤가 맞지 않아 쓰지 않았다(출처 9).

대신 "생성 속도는 메모리 대역폭을 모델 파일 크기로 나눈 값에 비례한다"는 일반 원리로 계산했다. 가정은 다음과 같다(이번에 출처로 확인 안 함).
- GTX 1060 3GB 메모리 대역폭은 약 192GB/s다(제품 사양 기억).
- i7-8700과 DDR4-2666 듀얼 채널 조합은 약 42.7GB/s다(사양 계산).
- 효율은 0.5로 가정했다.

| 경우 | 생성 속도(추정) |
|---|---|
| qwen3:1.7b, GPU에 전부 적재 | 초당 약 70토큰 |
| qwen3:1.7b, CPU만 | 초당 약 15토큰 |
| qwen3:4b, CPU만 | 초당 약 8토큰 |
| qwen3:4b, GPU 일부 적재 | 위 두 값 사이 |

입력 처리 단계도 CPU만으로는 느리다. 명세 3천 토큰을 넣으면 수십 초가 걸릴 수 있다(추정). 실제 숫자는 같은 사양 PC에서 `ollama run 모델명 --verbose`나 llama.cpp의 llama-bench로 측정해야 하는데, 지금 팀에는 그 PC가 없다.

### 3-4. 로컬 LLM을 쓴다면 맡길 범위

- 맡길 일: 질문을 정해진 분석 유형(추이, 비교, 순위, 구성비)과 조건(지역, 기간, 업종, 연령)으로 바꾸는 분류·추출. Ollama 구조화 출력(JSON 스키마 지정)으로 출력 형식을 강제한다. 이 기능 지원 여부는 기억 기반이라 확인이 필요하다.
- 맡기지 말 일: 여러 단계 계획, 숫자가 들어간 해설 문장. 꼭 쓰게 한다면 문장 속 숫자를 계산 결과와 하나씩 대조하는 검증기를 통과한 문장만 보여 준다.
- 위치: "외부 연결이 막혔을 때 쓰는 선택 기능"으로만 두고 기본은 끈다. 설치 실패가 평가 전체 실패로 번지지 않게 하기 위해서다.

## 4. 도구(tool) 설계

### 4-1. 도구 목록

| 도구 | 하는 일 | 실행 위치 | LLM에게 돌아가는 것 |
|---|---|---|---|
| 명세 검색 | 센터 데이터 명세 엑셀과 허브 데이터 목록에서 필요한 데이터·컬럼·코드표를 찾는다(로컬 키워드 검색) | 로컬 | 공개 명세 내용 |
| CSV 판독 | 불러온 Results_YYYYMMDD_HHMMSS.csv의 헤더를 명세의 컬럼 집합과 대조해 어떤 센터 데이터인지 알아낸다. 파일 안 기간이 요청 기간과 맞는지도 본다 | 로컬 | 데이터 이름과 컬럼명만, 값과 행 수는 안 돌려줌 |
| 계획 검사 | LLM이 낸 계획 JSON을 데이터 없이 검사한다: 명세에 있는 컬럼인지, 집계 함수와 컬럼 형식이 맞는지, 기간 조건이 한 달 단위 파일 구조와 맞는지 | 로컬 | 문법·명세 오류 목록 |
| 가상 데이터 리허설 | 명세로 만든 가상 데이터(일부러 10 미만 칸과 결측 NA 포함)에 계획을 실행한다 | 로컬 | 실행 결과 전체. 가상 데이터라 보내도 됨 |
| 집계 실행 | 검사를 통과한 계획을 실제 CSV에 DuckDB로 실행한다 | 로컬 | 결과 번호(핸들)만 |
| 10 미만 검사와 재집계 | 결과 표의 모든 칸이 10 이상인지, 합계로 가려진 칸을 역산할 수 있는지 검사한다. 실패하면 계획에 적힌 재집계 사다리를 순서대로 적용한다 | 로컬 | 기본값: 아무것도 안 돌려줌. 회색 영역 설정을 켜면 통과/실패만 |
| 합계 검산 | 부분합과 전체합 일치, 단위, 기간 누락 월을 확인한다 | 로컬 | 위와 같음 |
| 허브 Open API 호출 | 읍면동 단위 내국인 유동인구, 일별 기상 정보 같은 공개 데이터를 가져온다. 평가 환경 장애에 대비해 스냅샷을 ZIP에 넣는다(브리핑 6-2절에서 허용) | 로컬에서 허브로 호출 | 공개 데이터 값 |
| 차트 생성 | 계획에 적힌 차트 종류로 그림을 만든다(한글 폰트로 Windows 맑은 고딕 지정) | 로컬 | 성공 여부 |
| 보고서 작성 | LLM이 미리 쓴 문장 틀의 빈칸을 계산 결과로 채워 HTML과 PDF를 만든다. 방법·한계 절도 넣는다. 반출 신청용 활용 사유 문장도 만든다 | 로컬 | 성공 여부 |
| 사용자에게 묻기 | 필요한 달의 파일이 없을 때 센터 조회 화면에서 받을 조건이나 "요청파일" 폴더 안내를 보여 준다. 축제 날짜처럼 LLM이 짐작한 사실은 사용자 확인을 받는다 | 화면 | 사용자 응답 |
| 결과 삭제 | 퇴실 전 결과 파일 삭제를 켜고 끈다(브리핑 4절 권장) | 로컬 | 없음 |

### 4-2. 숫자 환각을 막는 보고서 방식: 빈칸 채움

LLM은 보고서 문장을 쓸 때 숫자 대신 계산 결과를 가리키는 빈칸만 쓴다. 예를 들면 다음과 같다.

> "{{표1.1위.지역}}의 카드 이용 금액은 전년 같은 달보다 {{표1.1위.증감방향}}했고 변화율은 {{표1.1위.변화율}}다."

로컬 코드가 빈칸을 채우고, "증가"나 "감소" 같은 방향 단어도 코드가 계산해 넣는다. 검사 규칙은 다음과 같다.
- LLM 문장에 빈칸이 아닌 숫자가 들어 있으면 그 문장을 버린다.
- 모든 숫자 옆에 "계산식 보기"를 붙인다. 쓴 파일 이름, 조건, SQL, 재집계 단계를 보여 준다.
- 계획 JSON, SQL, 입력 파일 해시를 저장해 같은 결과를 다시 만드는 재실행 버튼을 둔다.

결과 신뢰성·재현성(15점)에서 말하는 "결과 근거"와 "코드로 재현 가능"을 직접 보여 주는 장치다. 연구 방법 절(어떤 데이터를 어떤 조건으로 어떻게 집계했는지)은 값이 필요 없어서 LLM이 통째로 쓸 수 있다. 논문·현황자료 작성자(브리핑 4절의 주 이용자)에게 실제로 쓸모 있는 부분이다(추론).

### 4-3. 무엇이 "에이전트다움"을 보여 주나

| 행동 | 이 설계에서 실제로 일어나는 장면 |
|---|---|
| 스스로 계획 | 질문 하나를 "명세 검색, 데이터 확정, 계획 작성, 리허설, 실행, 보고" 순서로 직접 쪼갠다. 재집계 사다리처럼 실패할 때의 대안까지 미리 계획에 적는다 |
| 도구 고르기 | 질문에 따라 센터 CSV 집계만 할지, 허브 API로 공개 맥락(기상, 유동인구)을 더할지, 어떤 차트를 쓸지 고른다 |
| 결과 검증 | 계획 검사, 가상 데이터 리허설, 10 미만 검사, 합계 검산을 거친다 |
| 다시 시도 | 리허설 오류를 보고 계획을 고친다(최대 횟수 제한). 실제 데이터 검사에 실패하면 사다리 다음 단계로 넘어간다 |
| 모를 때 묻기 | 파일이 없거나 기간이 모자라면 무엇을 받아 와야 하는지 안내한다. LLM이 짐작한 사실은 확인을 받는다 |

화면에 "에이전트 작업 기록"(어떤 도구를 왜 불렀고 무엇이 실패해 어떻게 고쳤는지)을 보여 주고, 같은 화면 캡처를 기획서에 넣기를 권한다. 상호평가 30%는 기획서 PDF만 보고 투표하므로(브리핑 3절), 동작 장면이 PDF 안에 있어야 AI 역할이 전달된다(추론).

기획서 필수 항목인 "판단 및 자율 수행 범위"는 이렇게 쓰면 된다.
- 에이전트가 혼자 정하는 것: 데이터 선택, 계획, 차트 종류, 재시도(횟수 제한 안).
- 사람에게 묻는 것: 파일 불러오기, 모자란 기간, 외부 사실 확인.
- 절대 하지 않는 것: 센터 값 외부 전송, 사용자 설정 없는 파일 삭제.

## 5. 아이디어 3개

세 아이디어 모두 같은 엔진(질문 검문, 계획, 리허설, 로컬 실행, 10 미만 재집계, 빈칸 채움 보고서)을 쓴다. 엔진을 먼저 만들고 주제를 얹는 방식이라 주제를 늦게 정해도 개발이 막히지 않는다.

### 아이디어 1: 반출 기준을 스스로 맞추는 현황보고서 분석 비서

- **한 줄 요약**: 질문을 넣으면 센터 CSV를 로컬에서 집계하고, 10 미만 칸이 없어질 때까지 재집계 단위를 스스로 올린 뒤, 반출 가능한 PDF 현황보고서를 만들어 주는 에이전트.
- **누가 쓰나**: 센터에 방문한 기관·기업 이용자. 예를 들어 사업계획서에 "읍면동별 관광업종 카드 이용 추이" 표가 필요한 연구원이 조회 화면에서 받은 CSV를 들고 와 SQL 없이 결과물을 만들려는 상황이다.
- **해결하는 문제**: 이용자는 SQL을 쓰지 않고 메뉴로만 조회한다(브리핑 4절). 받은 CSV를 엑셀로 집계하다 10 미만 칸이나 역산 가능 문제로 반출이 반려된다(브리핑 5절). 활용 사유 문장도 따로 써야 한다.
- **쓰는 데이터**: 센터 「카드 이용 현황(읍면동)_v02」(필수), 「외식업 포스 이용 현황」. 허브 「읍면동 단위 내국인 유동인구」(API, 일 갱신)를 보조 맥락으로 쓴다.
- **AI가 맡는 일**: LLM은 질문 해석, 명세 검색, 계획 작성, 재집계 사다리 설계(예: 연령 세분류를 10세 단위로, 다시 3구간으로, 법정동을 행정시나 7권역으로), 리허설 오류 수정, 보고서 문장 틀과 방법·한계 절, 반출 활용 사유 문장 초안을 맡는다. 일반 코드는 CSV 판독, DuckDB 집계, 10 미만·역산 검사, 사다리 적용, 차트, 빈칸 채움, PDF를 맡는다.
- **센터 데이터를 외부 LLM에 보내지 않는 방법**: LLM은 공개 명세와 가상 데이터 리허설 결과만 본다. 실제 CSV 처리는 전부 로컬에서 한다. 질문 검문기와 외부 전송 기록 화면을 둔다.
- **시연 방법**: 명세 구조대로 만든 가상 CSV(Results_20261115_103000.csv)를 불러오고 "2025년 8월 관광업종 이용 금액을 읍면동·연령별로 보여 줘"라고 묻는다. 작업 기록에 "리허설에서 컬럼명 오류, 계획 수정, 실제 실행, 10 미만 칸 발견, 연령을 10세 단위로 재집계, 통과"가 차례로 찍힌다. 그다음 PDF와 외부 전송 기록이 나온다.
- **다른 팀과 겹칠 가능성**: 높음. "반출 점검", "현황보고서 자동 생성", "CSV 넣으면 분석해 주는 범용 분석기"에 경쟁이 몰려 있다(브리핑 7절). 차별점은 값을 한 개도 보내지 않는 점, 재집계 단위를 스스로 고르는 점, 빈칸 채움으로 숫자 환각을 차단하는 점인데, 기획서만 보는 상호평가에서 이 차이가 드러날지는 불확실하다(추론).
- **가장 큰 위험**: 첫째, 겹치는 팀이 많아 주제의 참신성(15점)에서 밀릴 수 있다. 둘째, 자유 질문 범위가 넓어 계획 형식이 모든 질문을 담지 못하면 "주요 기능의 안정적 수행"이 흔들린다. 시연은 지원하는 질문 유형 4~5개로 좁혀야 한다.

### 아이디어 2: 축제·행사 효과 측정 에이전트

- **한 줄 요약**: 축제 이름과 기간을 넣으면 공개 유동인구로 방문 증가를 확인하고, 비교 지역을 스스로 골라 센터 카드 데이터로 "축제 지역과 비교 지역의 매출 변화 차이"를 계산해 성과보고서를 만드는 에이전트.
- **누가 쓰나**: 축제·행사를 주최하거나 지원하는 기관 담당자. 행사 결과보고서나 다음 해 예산 근거를 쓰면서 "행사 덕분에 지역 소비가 얼마나 늘었나"를 숫자로 보여야 하는 상황이다. 브리핑 4절의 센터 이용 목적(현황자료, 사업계획서)과 맞는다(추론).
- **해결하는 문제**: 전년 같은 달과 단순 비교하면 관광 경기나 날씨 효과가 섞인다. 비교 지역을 정하고 기간 전후 차이를 비교하는 이중차분 방식은 비전문가가 직접 설계하기 어렵다(추론).
- **쓰는 데이터**: 센터 「카드 이용 현황(읍면동)_v02」(필수, 월 단위). 허브 「제주관광공사_제주관광정보시스템(VISIT JEJU)_축제행사콘텐츠」(File, 2025-09-18 수집. 개최 날짜·장소 컬럼이 있는지는 확인 못 함), 「읍면동 단위 내국인 유동인구」(API, 일 갱신), 「일별 기상 정보」(API, 일 갱신).
- **AI가 맡는 일**: LLM이 축제 정보에서 개최 읍면동과 기간을 찾는다. 공개 유동인구 일별 값을 직접 보고 행사 기간에 방문이 실제로 늘었는지 판단한다(공개 데이터라 가능). 행사 전 유동인구 흐름이 비슷한 읍면동을 비교 지역 후보로 순위를 매긴다. 그다음 센터 데이터 계산 계획(대상과 비교 지역, 행사 달과 기준 달, 업종 범위)과 "행사 전 추세가 비슷한지" 검사에 실패하면 쓸 다음 후보 순서까지 적는다. 일반 코드는 이중차분 계산, 사전 추세 검사, 10 미만 재집계, 차트, 빈칸 채움 보고서를 맡는다.
- **센터 데이터를 외부 LLM에 보내지 않는 방법**: LLM이 값을 보는 것은 허브 공개 데이터뿐이다. 센터 카드 데이터 계산과 사전 추세 검사는 로컬에서 하고, 후보 교체도 LLM이 미리 정한 순서를 코드가 따른다. LLM이 축제 날짜를 짐작했다면 사용자 확인을 받은 뒤에만 쓴다.
- **시연 방법**: 가상 카드 CSV(행사 달에 특정 읍면동 매출을 일부러 올려 둔 것)와 허브 유동인구 스냅샷을 쓴다. 축제 하나를 고르면 작업 기록에 "유동인구로 행사 기간 방문 증가 확인, 비교 지역 후보 3곳 선정, 1순위 사전 추세 불일치, 2순위로 교체, 차이 계산, 10 미만 없음"이 찍히고, "비교 지역 대비 차이"를 담은 PDF가 나온다.
- **다른 팀과 겹칠 가능성**: 낮음. 게시판 질문에서 축제·행사 효과를 언급한 팀은 없다(브리핑 7절 기준 추론). 상권분석과 데이터 일부가 겹칠 수는 있다.
- **가장 큰 위험**: 첫째, 센터 카드 데이터가 월 단위라 며칠짜리 작은 행사의 효과는 다른 요인에 묻힌다. 보고서는 "인과 효과"가 아니라 "비교 지역 대비 차이"로 쓰고 한계 절에 이 점을 자동으로 넣어야 한다. 둘째, 축제행사콘텐츠 파일에 날짜·장소가 없으면 사용자가 직접 입력해야 해서 편의성이 떨어진다. 데이터 분석가 확인이 필요하다.

### 아이디어 3: 농산물 시세 브리핑 에이전트 (공개 데이터 전면형)

- **한 줄 요약**: "월동무 지금 출하해도 될까?" 같은 질문에 허브 농산물 일일 거래·이동평균과 기상 API를 스스로 조회하고 비교해, 숫자 근거를 단 브리핑을 주는 에이전트.
- **누가 쓰나**: 출하 시기나 다음 작기를 고민하는 농가, 작목반·농협 출하 담당자. 같은 에이전트를 개인 PC에서 실행해도 된다(브리핑 4절).
- **해결하는 문제**: 시세, 이동평균, 날씨가 각각 다른 곳에 흩어져 있다. IT 비전문가가 여러 달을 비교하거나 "작년 이맘때보다 높은지"를 판단하려면 직접 찾아 정리해야 한다(추론. 사용자 리서처 확인 필요).
- **쓰는 데이터**: 허브 「농산물 품종별 일일 거래 정보」, 「농산물 품종별 일일 거래 통계」, 「농산물 품종별 거래 이동평균」(모두 API, 일 갱신), 「일별 기상 정보」(API, 일 갱신). 허브 데이터도 필수 데이터로 인정된다(브리핑 6-2절). 센터 데이터는 쓰지 않는다. 억지로 붙일 만큼 자연스러운 연결고리를 찾지 못했다.
- **AI가 맡는 일**: 제한이 없어서 AI 역할이 셋 중 가장 크다. LLM이 품목·기간을 정하고, 어떤 API를 어떤 순서로 부를지 계획하고, 받은 값을 보며 추가 조회(예: 작년 같은 기간, 한파 일수)를 할지 판단하고, 근거를 붙인 브리핑을 쓴다. 일반 코드는 API 호출과 캐시, 이동평균·증감률 계산, 차트를 맡는다. 숫자는 여기서도 코드가 계산한다. LLM 문장의 숫자는 도구 결과값과 대조해 일치하지 않으면 다시 쓰게 한다.
- **센터 데이터를 외부 LLM에 보내지 않는 방법**: 센터 데이터를 아예 쓰지 않으므로 해당 사항이 없다. 규정 위험이 가장 낮다.
- **시연 방법**: ZIP에 넣은 허브 API 스냅샷(평가 날 API 장애 대비)으로 "당근 시세가 작년보다 어떤지, 최근 날씨 영향이 있는지"를 묻는다. 작업 기록에 "거래 통계 조회, 이동평균 조회, 작년 같은 기간 추가 조회, 기상 조회, 브리핑 작성, 숫자 대조 통과"가 찍힌다.
- **다른 팀과 겹칠 가능성**: 낮음. 게시판에서 농산물을 언급한 팀은 없다(브리핑 7절 기준 추론). 다만 공개 데이터만 쓰는 주제(클린하우스, 전기차 충전소, 버스)를 고른 팀은 여럿이다.
- **가장 큰 위험**: 첫째, 이 API가 어떤 품목과 시장(제주 지역 시장인지 전국 도매시장인지)을 담는지, 최근까지 실제로 갱신되는지 확인하지 못했다. 데이터 목록상 수정일은 2025-09-12다. 둘째, 센터 데이터를 쓰지 않아 "센터 PC에서 센터 데이터를 다루는 도구"를 기대하는 심사에서 활용 방안이 약해 보일 수 있다(추론). "도민이 직접 실행"이라는 대회 주제와는 잘 맞는다.

## 6. 하지 말아야 할 것 (기술 함정)

1. **마스킹 집계표를 외부 LLM에 보내 해석 문장을 받는 구조.** 센터가 집계값 전송 허용 범위를 미리 확정하지 않았고(11/7·11/10), 다른 팀이 몰린 방향이다(브리핑 7절). 센터 심의에서 막히면 핵심 기능이 통째로 빠진다.
2. **LLM이 쓴 Python 코드를 그대로 실행하는 구조.** 임의 코드 실행은 보안상 위험하다. 결과 재현도 어렵고 정적 검사도 거의 불가능하다. 정해진 형식의 계획 JSON을 로컬에서 SQL로 바꾸는 방식이 안전하고 검증하기 쉽다.
3. **실제 데이터 실행 오류 원문을 LLM에 돌려주기.** pandas·DuckDB 오류 메시지에는 셀 값이 섞일 수 있다. 실제 데이터에서 난 오류는 종류와 컬럼명만 남긴다. 원문이 필요한 디버깅은 가상 데이터 리허설에서 한다.
4. **사용자 질문을 검문 없이 보내기.** 질문에 센터 값이 들어가면 외부 전송으로 본다(브리핑 4절).
5. **LLM이 보고서 문장에 숫자를 직접 쓰게 하기.** 값을 보지 않은 LLM은 숫자를 지어낸다. 빈칸 채움 방식으로만 숫자를 넣는다.
6. **로컬 소형 LLM을 핵심 경로에 두기.** 드라이버 570 이상, 3GB VRAM, 측정하지 않은 속도, 시험 환경 부재가 겹친다. 이미지 입력이 포함된 최신 소형 모델은 생각보다 크다(qwen3.5:2b 2.7~3.1GB, gemma4:e2b 4.6GB 이상).
7. **비상업 라이선스 모델 쓰기.** EXAONE 3.5(NC)와 Qwen2.5-3B(qwen-research)는 센터 탑재 시 문제가 될 수 있다.
8. **설치가 무거운 기술 쓰기.** Docker, WSL, CUDA 툴킷, 소스 빌드가 필요한 패키지(Windows의 llama-cpp-python 등), GTK가 필요한 PDF 라이브러리가 여기에 해당한다. 비개발자가 매뉴얼대로 설치하다 실패하면 평가자는 따로 연락하지 않는다(브리핑 3절).
9. **클라우드 서비스에 상태나 데이터를 두기.** 외부 벡터 DB, Supabase, 서버형 에이전트 서비스는 센터 데이터가 나갈 여지를 만들고 허용 목록 주소도 늘린다. 명세 검색은 로컬 키워드 검색이면 충분하다. 문서 수가 적어서다.
10. **외부 LLM이 없으면 아무것도 안 되는 구조.** 평가 당일 API 장애나 DLP 차단에 대비해 미리 정한 분석 메뉴로 돌아가는 강등 모드를 둔다.
11. **기본 설정 그대로 보내는 외부 통신.** Streamlit은 기본값으로 사용 통계를 외부에 보내는 설정이 있다(기억 기반, 확인 필요). 이 설정을 꺼 두지 않으면 DLP에 걸리거나 "외부 통신 없음" 주장과 어긋난다. pip 설치 주소(pypi.org, files.pythonhosted.org), 허브 API, LLM API 주소는 기획서에 미리 적어 허용 목록에 올린다(브리핑 4절).
12. **한글 폰트를 지정하지 않은 차트와 PDF.** matplotlib 기본 폰트로는 한글이 깨진다. Windows의 맑은 고딕을 지정한다.
13. **LLM이 짐작한 외부 사실(축제 날짜, 품목 출하기)을 확인 없이 쓰기.** 사용자 확인 단계를 거친다.
14. **패키지 버전을 고정하지 않기.** 평가 시점에 새 버전이 깔려 깨질 수 있다. requirements 파일에 버전을 고정한다.
