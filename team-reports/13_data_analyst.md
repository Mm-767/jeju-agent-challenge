함정 정리.

- 법정동과 행정동: 카드·포스(법정동)를 유동인구·종량제봉투(행정동)에 붙이려면 행정안전부가 공개하는 법정동·행정동 코드 연계표 같은 외부 공개 데이터가 필요하고, 한 행정동이 여러 법정동을 품거나 한 법정동이 여러 행정동에 걸치는 경우가 있어 일대일이 아니다. 안전한 선택은 권역 단위로 올려 잇는 것이다.
- 유동인구는 연인원이다: 허브 유동인구 API의 resdPop·workPop·visitPop은 하루 시간대별 인구의 합(브리핑 6-2절)이고, 센터 v02도 01~24시 시간 단위 값이다. 하루치를 더하면 같은 사람이 24번까지 세진다. "하루 방문자 수"로 쓰지 말고 시간 평균이나 특정 시간대 값으로 써야 한다.
- 카드는 비씨카드 실소유자 기준 표본이다: 지역 전체 매출이 아니므로 이용자 가게 매출과 금액을 그대로 비교하면 안 되고 비율·추이로 비교해야 한다.
- 센터 CSV에는 명세서의 `pt_year`, `pt_month` 파티션 컬럼이 없다(브리핑 4절). 명세서대로 가상 데이터를 만들 때 이 두 컬럼은 빼야 실제 파일과 같아진다.
- 센터 조회는 한 번에 1개월이다. 1년 추이 분석은 CSV 12개를 합치는 기능이 필수다.

### 1-5. 공개 데이터만으로 되는 분석과 센터 데이터가 있어야 의미가 생기는 분석

**공개 데이터만으로 되는 분석**

- 정류소·노선별 일일 이용자 추이, 날씨(강수·기온)에 따른 이용 변화, 정류소 위치 기반 지역별 비교(일일 정류소별 버스 이용자 정보, 버스 정류소 기본 정보, 일별 기상 정보, 기상관측소 정보).
- 읍면동별 내국인·외국인 유동인구 추이와 요일·계절 패턴(읍면동 단위 유동인구 API 3종).
- 와이파이 사용량으로 본 관광지 붐빔 정도(읍면동별 와이파이 사용량, AP 정보).
- 농산물 품종별 가격 추이와 이동평균(농산물 거래 API 3종). 단 허브에는 이미 농산물 분석 메뉴(`/analysis/agricultural/...`)가 있다.
- 2025-09 기준 업종별 점포 분포(상가(상권) 정보, 음식점 목록, 주소에서 읍면동을 뽑아야 함).

**센터 데이터가 있어야 의미가 생기는 분석**

- 지역·업종·시간대·요일별 소비 금액과 소비자 구성(카드 v02 3종, 500m격자). 허브 카드 API는 2016~2018년이고, 2025년까지 있는 허브 카드 파일은 지역을 나누지 않은 집계로 보인다.
- 외식업 메뉴·업종별 매출과 표본 점포 수(외식업 포스 12종).
- 시간 단위·성별·연령별 행정동 유동인구(유동인구 v02). 허브 API가 같은 해상도를 주는지는 확인 못 했다.
- 버스 승하차 OD(어디서 타서 어디서 내리는지)와 환승(버스 승객별 이용 현황, 버스 카드 승하차 정보). 허브 API는 정류소·노선 합계만 준다.
- 행정동별 일일 종량제봉투 판매량, 음식물쓰레기 배출량(종량제봉투판매실적, 음식물쓰레기 배출현황). 허브에는 클린하우스 시설 목록 정도만 있다.

### 1-7. 허브 Open API로 실제 호출할 수 있는 데이터와 호출 방식

- 호출 형식(일일 정류소별 버스 이용자 정보 상세 페이지에서 확인): `GET https://open.jejudatahub.net/api/proxy/{데이터마다 정해진 ID}/{your_projectKey}?startDate=YYYYMMDD&endDate=YYYYMMDD&...`. 문서 형식 UTF-8, 이 데이터의 일일 쿼터는 1000이다. 요청변수는 startDate·endDate(필수)와 moveType·priceType·payType(선택), 출력은 baseDate·stationId·stationName·moveType·priceType·payType·userCount. 데이터마다 기술문서(.hwp)가 붙어 있다.
- 키 발급(FAQ에서 확인, 실제 발급은 하지 않음): 로그인, 마이페이지의 프로젝트 관리에서 "프로젝트 만들기", 쓰려는 데이터 상세 페이지에서 "프로젝트 담기"를 누르면 그 프로젝트 키로 담은 데이터를 호출한다. 회원가입과 로그인이 필요하다.
- 시연에 쓸 만한 API: 위 1-3절의 일·월 자동갱신 23건 전부와 2025-09 기준 위치 정보 API들(오름, 전기자동차 충전소, 약국, 관광 숙박업 등).
- 확인하지 못한 것: 상세 페이지의 수집기간이 "2015-01-01 ~ 2015-01-01 (자동갱신 : 일)"로 표시되고 미리보기 값은 2019-02-01이다. API가 실제로 2026년 날짜까지 값을 돌려주는지, 응답이 JSON인지, 쿼터가 데이터별인지 키별인지는 키를 받아 한 번 호출해 봐야 안다. 시연을 공개 API에 걸려면 이 확인이 가장 먼저다.
- 평가 환경 주의: `open.jejudatahub.net`은 기획서의 외부 주소 허용 목록에 적어 둔다. 이 호출에는 날짜·조건만 실려 나가고 센터 데이터는 실리지 않는다.

## 2. 아이디어 비교 (같은 기준을 모든 후보에 적용)

데이터 근거를 기준으로 다섯 후보를 같은 축으로 비교했다. 축은 필수 데이터의 최신성, 결합 키가 깔끔한지, 공개 API로 실제 호출 시연이 되는지, 센터 데이터가 더해 주는 가치, 다른 팀과 겹칠 가능성, 가상 데이터 만들기 난이도다.

| 후보 | 최신성 | 결합 키 | 공개 API 실시연 | 센터 데이터의 추가 가치 | 겹칠 가능성 | 가상 데이터 |
|---|---|---|---|---|---|---|
| 버스 정류소·노선 수요 진단 | 일 단위 API | 정류소 ID, 날짜 | 됨 | OD·환승(반출 가능) | 중간 | 보통 |
| 행정동 생활폐기물 현황·예측 | 일 단위(센터), 일 단위 API(유동인구·기상) | 행정동, 날짜 | 유동인구·기상만 | 핵심(종량제봉투) | 중간 | 쉬움 |
| 상권 시간대·요일 소비 진단 | 월 단위(센터), 2025-09 목록(허브) | 권역·법정동, 연월 | 유동인구만 | 핵심(카드 v02) | 높음 | 쉬움 |
| 농산물 가격 추이 안내 | 일 단위 API | 품종, 날짜 | 됨 | 없음 | 낮음 | 필요 없음 |
| 관광 수요 조기 신호 | 월 단위 파일이 2025-07~08에 멈춤 | 연월 | 일부 | 단기체류 외국인 v02 | 중간 | 쉬움 |

농산물은 공개 API만으로 완결되지만 센터 데이터와 이어지지 않고 허브에 이미 농산물 분석 메뉴가 있어 3위 밖에 두었다. 관광 수요 조기 신호는 핵심 월 단위 데이터가 멈춰 있어 뺐다. 다른 팀원 결과와 합칠 때 다시 볼 수 있도록 남겨 둔다.

## 3. 아이디어 3개

### 아이디어 1: 버스 정류소·노선 수요 진단 Agent

- 한 줄 요약: "지난달 비 온 날 ○○ 정류소 이용이 얼마나 줄었나", "이 노선에서 이용이 가장 많이 빠진 정류소는 어디인가" 같은 질문을 받아 허브 버스·기상 API를 직접 호출해 표·차트·근거 문장으로 된 현황 보고서를 만들어 준다.
- 누가 쓰나: 센터를 찾는 교통 분야 연구자·용역 수행 기관이 현황자료를 쓸 때, 제주도·행정시 교통 담당 공무원이 노선 개편 민원이나 의회 자료를 준비할 때.
- 해결하는 문제: 지금은 허브 API를 날짜 범위별로 따로 호출하고, 정류소 ID를 이름과 맞추고, 날씨 관측소를 정류소 위치에 붙이는 일을 직접 코드로 해야 한다. 센터 이용자는 SQL을 쓰지 않는다(브리핑 4절).
- 쓰는 데이터
  - 허브: 일일 정류소별 버스 이용자 정보(2015-01부터, 일 자동갱신 API), 일일 노선별 버스 이용자 정보(2015-01부터, 일), 버스 정류소 기본 정보·버스 노선 기본 정보(2019-04부터, 일), 일별 기상 정보(2014-01부터, 일), 기상관측소 정보. 장기 추이 보강용으로 일별 시간대별 버스 승차 인원 수 현황(2018-06~2025-10-19, File).
  - 센터(선택): 버스 승객별 이용 현황, 버스 카드 승하차 정보(일 단위 누적, 반출 가능 표시). OD·환승 분석에 쓴다.
- AI가 맡는 일
  - LLM: 질문에서 정류소·노선·기간·조건(비 온 날, 주말)을 뽑고 모호하면 되묻기, 어떤 API를 어떤 날짜 범위로 부를지 계획, 결과가 비거나 이상하면 범위를 바꿔 다시 호출, 최종 표의 숫자만 인용해 해석 문장 작성.
  - 일반 코드: API 호출과 캐시, 정류소 이름 퍼지 매칭, 정류소 좌표와 가장 가까운 기상관측소 매칭, 집계·비교·차트, LLM 문장 속 숫자가 계산표 값과 같은지 자동 대조.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙: 공개 API 결과만 외부 LLM에 보낸다. 센터 OD CSV를 불러온 경우 외부 LLM에는 공개 명세서의 컬럼명과 정류소 이름 목록(허브 공개값)만 주고, OD 집계표와 그 해석 문장은 로컬 코드의 템플릿으로 만든다. 센터 모드에서는 외부 호출 버튼을 끄는 스위치를 둔다.
- 시연 방법: 평가 환경에서 참가자 프로젝트 키로 허브 API를 실제 호출해 "2025년 10월 강수일과 비강수일의 제주버스터미널 인근 정류소 이용자 비교" 보고서를 만드는 장면. 센터 부분은 명세서 구조의 가상 승하차 CSV로 OD 표를 보여 준다.
- 다른 팀과 겹칠 가능성: 중간. 게시판에 버스 수요응답형 분석을 묻는 팀(수연에이전트)이 있고, 허브에는 2021년 전기버스 우선도입노선 매쉬업도 있다. 반면 브리핑 7절의 쏠림 영역(센터 이용 도우미, 반출 점검, 범용 CSV 분석기)과는 다르다.
- 가장 큰 위험: 허브 API가 실제로 최신 날짜 값을 돌려주지 않으면 "최신 값 실시간 호출"이라는 강점이 사라진다(키로 한 번 호출해 확인 필요). 일일 쿼터 1000 안에서 긴 기간을 부르면 호출 수가 모자랄 수 있어 캐시가 필수다.

### 아이디어 2: 행정동 생활폐기물 현황·예측 Agent

- 한 줄 요약: 센터의 종량제봉투 판매 CSV를 넣으면 행정동별·일별 판매 추이를 정리하고, 허브 유동인구·기상 API로 방문 인구와 날씨를 붙여 "사람이 몰린 날과 비 온 날 판매가 어떻게 달라졌나"와 다음 달 예상 범위를 보고서로 만들어 준다.
- 누가 쓰나: 제주시·서귀포시 청소행정 담당자, 행정동 주민센터, 환경 분야 연구기관이 수거 계획이나 연구 보고서를 쓸 때.
- 해결하는 문제: 판매 실적은 센터에, 유동인구·기상은 허브에 나뉘어 있고, 판매 데이터는 한 번에 한 달씩만 받을 수 있어 여러 해 추이를 보려면 CSV 수십 개를 합쳐야 한다.
- 쓰는 데이터
  - 센터: 종량제봉투판매실적(2012-01부터 일 단위 누적, 행정동, 반출 가능 표시), 보조로 대형폐기물 현황_제주시.
  - 허브: 읍면동 단위 내국인 유동인구, 읍면동 단위 외국인 단기체류 유동인구(일 자동갱신 API), 일별 기상 정보, 기상관측소 정보. 시설 참고로 서귀포시 클린하우스현황(Link).
- AI가 맡는 일
  - LLM: 질문을 분석 계획(대상 행정동, 기간, 비교 조건)으로 바꾸고, 필요한 센터 CSV 목록(어느 달 몇 개)을 이용자에게 안내하고, 공개 API 호출을 계획한다.
  - 일반 코드: 월별 CSV 병합과 형식 검사, 행정동 이름 정규화, 유동인구 시간 평균 계산(연인원 함정 처리), 회귀 또는 계절성 모델로 예측 범위 계산, 10 미만 값이 있는 칸을 상위 단위로 합쳐 반출 기준에 맞춘 표 생성.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙: 판매 실적 값과 그 집계는 외부로 보내지 않는다. 외부 LLM에는 질문, 공개 명세서의 컬럼명, 행정동 이름(공개값), 허브 공개 데이터 결과만 보내고, 센터 수치가 들어간 해석 문장은 로컬 템플릿이나 로컬 소형 모델로 만든다. 센터 모드에서 질문 문장에 숫자가 있으면 외부 전송 전에 경고한다.
- 시연 방법: 명세서 구조대로 만든 가상 종량제봉투 CSV 3개월치를 넣고, 허브 유동인구·기상 API를 실제 호출해 행정동 하나의 판매·방문 인구·강수 비교 차트와 다음 달 예상 범위를 만드는 장면.
- 다른 팀과 겹칠 가능성: 중간. 클린하우스 공개데이터 기반 Agent를 묻는 팀(도톨토뤼)이 있고 허브에 2021년 클린하우스 음식물쓰레기 예측 매쉬업이 있다. 다만 센터 종량제봉투 데이터와 행정동 결합을 쓰는 팀 신호는 게시판에 없었다.
- 가장 큰 위험: 봉투 판매량은 배출량이 아니라 구매량이라 사재기·명절 효과가 섞인다(도메인 확인 필요). 허브 유동인구 API의 "읍면동" 이름이 센터 종량제봉투의 행정동 이름과 정확히 같은지 확인하지 못했다.

### 아이디어 3: 상권 시간대·요일 소비 진단 Agent

- 한 줄 요약: 센터 카드 v02(시간대·요일·법정동) CSV를 넣으면 업종·지역별로 "언제, 누가(관광객·도민, 연령) 쓰는지"를 정리하고, 허브 점포 목록과 유동인구를 붙여 점포당 소비와 방문 인구 대비 소비를 권역 단위로 보여 준다.
- 누가 쓰나: 사업계획서·컨설팅 보고서를 쓰러 센터에 오는 기업·기관(브리핑 4절의 주 이용자), 소상공인 지원기관 담당자.
- 해결하는 문제: 센터에서 가장 많이 조회·반출되는 데이터가 카드 시간대·요일 v02와 500m격자인데, 법정동 단위 카드와 행정동 단위 유동인구를 잇는 방법을 이용자가 직접 찾아야 하고, 10 미만 칸 처리 없이 표를 만들면 반출이 반려된다.
- 쓰는 데이터
  - 센터: 카드 이용 현황(시간대)_v02, (요일별)_v02, (읍면동)_v02(2023-08부터 월 단위 누적, 법정동 73개·7개 권역), 선택으로 제주도 내 업종별 매장 수(2017-01부터).
  - 허브: 제주특별자치도 상가(상권) 정보, 제주특별자치도 음식점 목록(2025-09 기준), 읍면동 단위 내국인 유동인구(일 자동갱신 API), 비교용 시간대별 카드 이용금액 현황(2018-01~2025-06).
- AI가 맡는 일
  - LLM: 질문에서 업종·지역·비교 조건을 뽑아 공개 명세서의 범주 값(업종명, 법정동명, 권역명)에 맞춰 분석 계획을 세우고, 필요한 CSV를 안내한다.
  - 일반 코드: 법정동과 행정동이 다른 문제를 권역 단위 집계 또는 외부 공개 연계표로 처리, 업종 대응표 적용, 10 미만 칸을 상위 단위로 합치는 반출용 표 생성, 차트.
- 센터 데이터를 외부 LLM에 보내지 않는 규칙: 카드 값은 원본·집계 모두 외부로 보내지 않는다. 외부 LLM은 계획만 세우고, 센터 수치 해석은 템플릿 문장으로 만든다. 공개 점포 수·유동인구 해석만 외부 LLM이 쓴다.
- 시연 방법: 명세서 구조대로 만든 가상 카드 시간대 v02 CSV를 넣고 "제주시 중부(동) 권역 한식 업종의 관광객 저녁 소비 비중"을 표·차트로 만들고, 허브 유동인구 API를 실제 호출해 같은 권역 저녁 시간 방문 인구와 나란히 보여 주는 장면.
- 다른 팀과 겹칠 가능성: 높음. 소상공인 매출 비교(한콩이아빠), 외식업 포스 기반 개발(sanhapark), CSV를 넣으면 집계하는 분석기(안녕하12, 미노스, Tarkovsky)가 게시판에 보였고, 상권분석은 센터 이용 목적과 겹쳐 많을 것으로 추정된다(브리핑 7절, 추정).
- 가장 큰 위험: 경쟁 쏠림으로 상호평가에서 차별점이 묻힐 수 있다. 카드 시간대(오전·점심·오후·저녁·밤)의 시각 경계와 격자 코드 체계를 명세서에서 찾지 못해, 유동인구 시간과 맞추는 근거가 약하다.

## 4. 다른 팀원이 확인해 주면 좋을 질문

- AI 엔지니어에게: 허브 프로젝트 키로 일일 정류소별 버스 이용자 정보와 읍면동 단위 내국인 유동인구를 한 번씩 호출해, 2026년 날짜 값이 오는지, 응답이 JSON인지, 일일 쿼터 1000이 데이터별인지 키별인지 확인해 줄 수 있는가. GTX 1060 3GB에서 센터 수치 해석 문장용 로컬 소형 모델이 현실적인가.
- 컴플라이언스 책임자에게: 공개 명세서에 있는 범주 값(법정동명, 업종명, 행정동명)과 컬럼명만 외부 LLM에 보내는 것은 센터 데이터 외부 전송에 해당하지 않는다고 봐도 되는가. 명세서에 "반출 가능"으로 표시된 버스·폐기물 데이터에도 10 미만 처리 기준이 그대로 적용되는가. 행정안전부 법정동·행정동 연계표 같은 외부 공개 데이터는 출처 표기만으로 쓸 수 있는가.
- 제주 도메인 전문가에게: 종량제봉투 판매량을 폐기물 배출량 대리지표로 쓰는 것이 실무에서 받아들여지는가. 허브와 센터의 버스 정류소 ID가 같은 체계인가. 7개 권역 구분이 행정 자료에서도 쓰이는가.
- 사용자 리서처에게: 센터 방문 이용자(기관·기업)가 보고서에 넣는 표는 주로 어느 지역 단위(행정동, 법정동, 권역, 시)인가. 교통·청소 담당 공무원이 센터를 쓰는가, 아니면 허브만 쓰는가.
- 경쟁 분석가에게: 버스 수요와 생활폐기물 주제가 공개된 다른 대회·기존 서비스와 얼마나 겹치는가. 허브의 농산물 분석 메뉴가 실제로 어떤 기능을 하는가.
