# AI 에이전트 설계: 「행사 효과 나란히」에서 LLM이 맡는 부분

작성 2026-11-13, AI 에이전트 설계 담당. 근거는 40_plan_brief.md, 14_ai_engineer.md 전체, 30_pm_decision.md 2-1절·4절, 16_compliance_officer.md 1·3·4절, app/spec/card_v02.json, 오늘 직접 센 행사 파일 수치, Claude API 참고 자료(2026-11-03 기준 캐시)와 오늘 직접 연 공식 가격 페이지다. 확인하지 않은 수치에는 "추정", 근거 없는 판단에는 "추론"을 붙였다. 코드는 만들거나 고치지 않았다.

## 결론 5줄

1. LLM 호출은 전부 센터 CSV를 불러오기 전에 끝난다. LLM은 공개 정보만 보고 "계획 묶음"(행사 장소, 방문 증가 판단, 비교 읍면 순위, 계산 계획, 숫자가 빈칸인 문장 틀) 하나를 만들고, CSV를 불러오는 순간 외부 연결이 잠긴 뒤로는 코드가 그 묶음대로 계산하고 빈칸을 채운다.
2. 구조는 코드가 단계를 정하고 각 단계 안에서 LLM이 공개 자료 조회 도구를 골라 쓴 뒤 단계별 제출 도구로 답을 내는 방식이다. 제출 도구는 strict 스키마로 형식을 강제하고, 검사나 가상 데이터 리허설에서 실패하면 오류 목록을 같은 대화에 돌려줘 처음 제출 뒤 최대 3번 고치게 한다.
3. 숫자 환각은 두 겹으로 막는다. LLM이 쓰는 모든 문장에서 빈칸, 입력에 나온 날짜와 행사 이름, 업종 코드를 지운 뒤 숫자가 하나라도 남으면 돌려보내고, 결과 문장은 결과가 나오기 전에 경우별(높음, 낮음, 차이 없음, 계산 불가) 틀로 받아 코드가 결과에 맞는 틀을 골라 채운다.
4. 모델은 Haiku 5.5를 기본으로 두고 시험 행사 12개를 3번씩 돌려 통과율과 사람이 만든 정답표(개최 읍면, 같은 달 다른 행사가 있는 읍면) 정답률로 Sonnet 5.5와 비교해 정한다. 실행 1회 비용은 Haiku 약 11원, Sonnet 약 220원으로 추정해 비용은 고르는 기준에서 뺀다.
5. 키가 없거나 호출이 실패하면 개발 때 실제 에이전트로 만들고 사람이 확인한 계획 묶음 3개로 같은 실행기를 돌리고, 화면 상단 띠와 작업 기록 첫 줄에 "미리 만든 계획"이라고 밝힌다. 로컬 LLM, 결과를 본 뒤의 LLM 해석, 자유 질문 창, 웹 검색 도구는 만들지 않는다.

## 0. 이 문서에서 쓰는 말

- **실행 1회**: 이용자가 행사 하나를 골라 계획 묶음을 만들기까지의 한 번. 14번이 말한 "질문 1개"에 해당한다. 이 주제에는 자유 질문 입력이 없다.
- **계획 묶음**: LLM 단계의 산출물 전부를 담은 JSON 파일 하나(10절에 형태). 계산과 보고서는 이 파일만 보고 돈다. 같은 파일로 다시 돌리면 같은 결과가 나온다.
- **조회 도구**: LLM이 공개 자료를 더 보고 싶을 때 부르는 도구 2개(get_visit_series, find_events). 이 PC에서 공개 스냅샷을 읽는다.
- **제출 도구**: 단계마다 답을 내는 도구 5개(이름이 submit_로 시작). 코드가 받아서 검사한다.
- **리허설**: 센터 형식 그대로 만든 가상 카드 CSV(app/data/dummy/card_effect)에 계획을 실제로 돌려 보는 것. 가상 데이터라 결과 전문을 LLM에 돌려줘도 된다.
- **빈칸**: 문장 안의 `{{키}}` 자리. 코드가 계산 결과나 공개 값으로 채운다.

## 1. LLM이 판단하는 단계 전체 목록

### 1-1. 전체 흐름

1. **장소 추정표 만들기(한 번만).** 행사 파일에서 분석 기간(2023-08-01~2026-08-31)에 시작한 행사 213건의 개최 장소를 LLM이 이름으로 추정해 표로 저장한다. 개발 때 만들어 ZIP에 넣고, 행사 파일이 바뀌면(파일 해시로 판별) 다시 만든다. 이 표는 행사 고르기 화면(읍면 행사만 보여 주기)과 단계 2(같은 달 다른 행사 확인)에 같이 쓴다.
2. **행사 확인(단계 0).** 이용자가 행사를 고르면 표에서 날짜와 장소 추정, 이유를 꺼내 노란색으로 보여 준다. 이용자가 읍면을 확인하거나 고치기 전에는 다음으로 넘어가지 않는다. 이 단계는 실행 때 LLM을 다시 부르지 않는다.
3. **단계 1: 방문 증가 판단.** 공개 유동인구로 행사 기간에 방문이 늘었는지 판단한다.
4. **단계 2: 비교 읍면 고르기.** 1~3순위와 이유, 뺀 읍면과 이유를 낸다. 순위가 곧 사전 추세 검사 실패 때의 교체 순서다.
5. **단계 3: 계산 계획.** 계획 JSON을 내고 코드가 검사와 리허설을 한다.
6. **단계 4: 문장 틀.** 경우별 결과 문장, 방법 문단, 이 행사만의 한계, 활용 사유 문안 틀을 낸다.
7. **계획 묶음 저장.** 여기까지가 LLM 몫이다.
8. **센터 CSV 불러오기.** 외부 연결이 잠기고 상단 띠가 바뀐다(30번 2-1절). 이후 계산, 후보 교체, 10 미만 처리, 틀 고르기, 빈칸 채우기는 모두 코드가 한다. 결과가 LLM에 돌아가는 경로는 없다.

단계 1~4는 한 대화(messages 배열 하나)로 이어 간다. 앞 단계의 판단을 다음 단계가 기억하고, 시스템 프롬프트와 도구 정의가 고정된 앞부분이라 프롬프트 캐시가 잘 맞는다.

### 1-2. 단계별 입력·출력·실패 처리

입력은 전부 공개 정보다. 센터 CSV의 값, 행 수, 집계, 오류 원문, 질문 속 숫자는 어느 단계에도 들어가지 않는다. 이 주제에는 이용자가 타이핑한 글이 외부로 가는 경로 자체가 없다(읍면 확인은 고르기 목록이고, 활용 사유의 기관명·사용 목적은 이 PC에서만 채운다).

### 1-3. 단계별로 LLM이 실제로 판단하는 것

- **장소 추정**: 장소 열이 없어서(브리핑 3절) 이름과 주관·주최만으로 추정한다. 예를 들어 "휴애리 유럽 수국축제"는 남원읍, "이호테우축제"는 동 지역, "3월 여행가는 달, 제주 로컬상품 프로모션"은 도 전역이다(모두 추정, 사람 확인 필요). 행사 종류도 판단한다. 몇 주씩 이어지는 야간개장, 상설 공연, 전시는 "상시·장기 운영"으로 나눠야 비교 후보를 지나치게 많이 빼지 않는다. 오늘 행사 파일을 세어 보니 시험 행사가 걸친 달마다 겹치는 행사가 9~33건이었다(2024-07 27건, 2024-08 32건, 2024-10 33건, 2024-04 22건, 2025-03 9건, 2023-10 28건). 행사마다 따로 추정하면 같은 행사에 실행마다 다른 답이 나올 수 있어 한 번 만든 표를 같이 쓴다.
- **방문 증가**: 행사 기간 평균을 행사 전 네 주, 전년 같은 기간과 비교하고 요일 효과를 감안해 판단한다. 전년 값이 필요하면 조회 도구를 직접 부른다. 이 장면이 "도구 고르기"를 보여 준다.
- **비교 읍면**: 흐름 유사도만으로 고르면 코드로 충분하다. LLM이 맡는 이유는 유사도 표에 없는 사정을 함께 보기 때문이다. 같은 달 다른 축제(예: 한림공원 연꽃축제 2024-07~08과 같은 시기의 휴애리 유럽 수국축제, 남원읍 추정), 섬 지역의 작은 칸 위험(우도면, 추자면), 규모 차이를 이유와 함께 순위에 반영한다.
- **계산 계획**: 행사가 며칠만 걸친 달을 행사 달에 넣을지, 축제 방문객이 돈을 쓸 업종을 어디까지 넣을지(좁히면 10 미만 칸이 늘고 넓히면 효과가 희석된다), 묶는 순서를 정한다. 통계 기준값(사전 추세 판정, 차이 없음 판정)은 코드가 정하고 LLM은 바꾸지 못한다.
- **문장 틀**: LLM은 결과를 끝까지 보지 못하므로 결과마다 쓸 틀을 미리 쓴다. 방법 문단은 값이 필요 없어서 LLM이 통째로 쓴다(14번 4-2절).

## 2. 도구 정의

### 2-1. 공통 규칙

- 도구 7개를 모든 요청에 같은 순서로 넣는다. 도구 목록이 바뀌면 캐시가 깨진다.
- 모든 도구에 `strict: true`를 건다. strict는 객체마다 `additionalProperties: false`와 모든 속성을 `required`에 넣어야 한다. 비워도 되는 칸은 `anyOf`로 null을 허용한다.
- 읍면 12곳, 달 37개(2023-08~2026-08), 업종 42개 목록은 app/spec/card_v02.json에서 코드가 읽어 `$defs`에 한 번만 넣는다. 명세 파일이 이미 있으니 새로 쓰지 않는다. bjd 목록에는 월평동이 두 번 나오지만(제주시·서귀포시 각각으로 추정) 읍면 목록은 eup_myeon 12곳을 쓰므로 영향이 없다.
- strict가 지원하지 않는 제약(배열 길이, 숫자 범위, 문자열 길이)은 쓰지 않고 이 PC의 검사기가 본다(참고 자료의 JSON Schema 제한 목록 확인).
- `tool_choice`는 `auto`로 둔다. Sonnet 5.5는 `any`나 특정 도구 강제를 400으로 거절하고, Haiku 5.5는 강제를 받아 주지만 그때 생각(thinking) 없이 바로 도구를 부른다(참고 자료). 두 모델을 바꿔 가며 측정해야 하므로 같은 설정을 쓴다. `auto`는 호출을 보장하지 않으니 제출 도구를 안 부르면 코드가 다시 요청한다(3절).
- 도구 결과는 JSON 문자열로 돌려준다. 실패는 `is_error: true`로 돌려주고 빼먹지 않는다. 한 응답에 도구 호출이 여러 개면 결과를 한 사용자 메시지에 모두 담는다.
- 공통 `$defs`(아래 스키마에서 `#/$defs/...`로 가리킴):

```json
{
  "emd":   {"type": "string", "enum": ["한림읍","애월읍","구좌읍","조천읍","한경면","추자면","우도면","대정읍","남원읍","성산읍","안덕면","표선면"]},
  "month": {"type": "string", "enum": ["2023-08", "2023-09", "...", "2026-08"]},
  "biz":   {"type": "string", "enum": ["G47119", "G47121", "...", "S96122"]},
  "date":  {"type": "string", "format": "date"}
}
```

### 2-2. 조회 도구 2개

**get_visit_series**


### 2-4. 형식을 강제하는 방법과 결정이 필요한 점

strict 제출 도구를 쓰면 LLM이 제출 도구를 부르는 순간 입력은 스키마를 반드시 지킨다(참고 자료: strict tool use는 tool_use.input이 스키마에 맞음을 보장). 남는 위험은 두 가지다. 첫째, `auto`라서 제출 도구를 안 부르고 글로만 답할 수 있다. 이때 코드가 "이 단계는 submit_plan 도구를 불러 끝내 주세요"를 보내고 제출 1번으로 센다. 둘째, 스키마가 표현하지 못하는 규칙(달이 이어지는지, 목록 길이 등)은 검사기가 본다.

**사용자 결정 필요 1: 형식 강제 방식.** 비교한 두 방식에서 실제로 갈리는 점만 적었다.

| | strict 제출 도구와 tool_choice auto (추천) | 응답 형식 지정(output_config.format) |
|---|---|---|
| 형식 보장 | 제출 도구를 부르면 보장, 안 부르면 코드가 다시 요청 | 최종 답 전체 보장 |
| 조회 도구와 함께 쓰기 | 같은 방식이라 자연스럽다 | 가능하다. 다만 Haiku 5.5는 생각을 끈 상태에서 JSON 형식을 같이 요구하면 필요한 도구 호출을 건너뛸 수 있다고 참고 자료에 적혀 있다 |
| 실패를 돌려주는 길 | 그 도구 호출에 is_error 결과로 돌려준다 | 사용자 메시지로 돌려준다 |
| 작업 기록에 보이는 모습 | "도구 호출과 검사 결과"로 보여 에이전트 동작이 드러난다 | 일반 답변으로 보인다 |

추천은 strict 제출 도구다. 30번 4-2절이 "도구 정의의 스키마로 형식을 강제"를 반드시 넣을 것으로 정했고, 실패를 같은 도구 호출에 돌려주는 흐름이 리허설 고리와 맞는다.

## 3. 계획, 리허설, 검증, 재시도 고리

### 3-1. 의사코드

```python
MAX_SUBMITS = 4          # 처음 제출 1번 + 고침 3번
MAX_READS = 4            # 단계마다 조회 도구 호출 한도
MAX_CALLS_PER_RUN = 16   # 실행 1회 전체 LLM 호출 상한

def run_planning(event, on_log):
    if not llm_available():                      # 키 없음, 센터 데이터 모드 잠김
        return use_prebuilt(event, on_log, reason="키 없음")
    convo = Conversation(system=SYSTEM_PROMPT, tools=ALL_TOOLS)   # 순서 고정, 캐시 대상
    bundle = {"event": event, "origin": "ai", "attempts": {}}
    pending = []                                 # 통과한 제출에 돌려줄 tool_result
    for stage in [VISIT, COMPARE, PLAN, TEXTS]:
        convo.add_user(pending + [text(stage.message(bundle))])   # 공개 값으로만 만든 글
        out = run_stage(convo, stage, bundle, on_log)
        if out.failed:
            if stage is TEXTS:                   # 문장 틀만 실패하면 기본 문장으로
                out = default_texts(); on_log("대체", "문장 틀을 기본 문장으로 바꿨습니다.")
            else:
                return use_prebuilt(event, on_log, reason=out.reason)
        bundle[stage.key] = out.value
        bundle["attempts"][stage.key] = out.submits
        pending = [tool_result(out.call_id, "통과")]
        if stage is VISIT and out.value["judgement"] == "증가 없음":
            if not ask_user_continue(on_log):    # 화면에서 이용자가 고른다
                return stopped("효과를 찾기 어려운 행사")
        if stage is COMPARE and len(out.value["ranked"]) < 2:
            return stopped("비교할 수 있는 읍면이 부족합니다")
    bundle["meta"] = meta(model=MODEL, prompt_hash=PROMPT_HASH)
    save_bundle(bundle)
    return bundle

def run_stage(convo, stage, bundle, on_log):
    submits = reads = 0
    while True:
        resp = outbound.send(convo.request())    # 외부로 나가는 유일한 통로, 원문 기록, 잠금 확인
        if resp.stop_reason in ("refusal", "max_tokens"):
            return Fail(f"응답 중단: {resp.stop_reason}")
        convo.add_assistant(resp.content)        # thinking 블록까지 그대로 다시 넣는다
        calls = [b for b in resp.content if b.type == "tool_use"]
        if not calls:
            submits += 1
            if submits >= MAX_SUBMITS: return Fail("제출 도구를 부르지 않음")
            convo.add_user([text(f"이 단계는 {stage.submit_tool} 도구를 불러 끝내 주세요.")])
            continue
        results, passed = [], None
        for call in calls:
            if call.name in READ_TOOLS:
                reads += 1
                if reads > MAX_READS:
                    results.append(err(call, "이 단계의 조회 한도를 다 썼습니다. 지금 가진 자료로 제출해 주세요."))
                else:
                    on_log("도구", call.input["why"])
                    results.append(ok(call, READ_TOOLS[call.name](call.input)))   # 공개 스냅샷
            elif call.name == stage.submit_tool:
                submits += 1
                errors = stage.validate(call.input, bundle)       # 정적 검사, 숫자 규칙
                if not errors and stage is PLAN:
                    report = analysis.rehearse(merge(bundle, call.input))   # 가상 데이터만
                    errors = report.errors
                    on_log("검사", report.summary_ko)
                if not errors:
                    passed = call
                else:
                    on_log("재시도", summarize(errors))
                    if submits >= MAX_SUBMITS: return Fail(errors)
                    results.append(err(call, retry_message(errors, MAX_SUBMITS - submits)))
            else:
                results.append(err(call, "이 단계에서는 쓸 수 없는 도구입니다."))
        if passed:
            return Ok(passed.input, call_id=passed.id, submits=submits)   # 같은 응답의 조회 결과는 버린다
        convo.add_user(results)                  # 결과는 한 사용자 메시지에 모두
```

- 통과한 제출의 tool_result("통과")는 다음 단계 지시와 같은 사용자 메시지 앞에 붙인다. API는 tool_use 다음 사용자 메시지에 그 결과가 있어야 받는다.
- 실행 1회의 호출 수가 MAX_CALLS_PER_RUN을 넘으면 `outbound.send`가 예외를 내고 대체 경로로 간다. 무한 반복과 비용 폭주를 막는 마지막 장치다.
- 계획 묶음을 저장한 뒤의 재실행은 LLM을 부르지 않는다. Haiku 5.5와 Sonnet 5.5는 temperature 같은 표본 추출 값을 기본값이 아니게 보내면 400을 내서(참고 자료) 같은 입력에도 답이 매번 다르다. 재현성은 "LLM을 다시 부르기"가 아니라 "저장한 계획 묶음으로 다시 계산하기"로 보장한다.

**사용자 결정 필요 2: 고리를 직접 쓸지 SDK의 Tool Runner를 쓸지.** Anthropic Python SDK에는 도구 호출 반복을 대신 돌려 주는 `client.beta.messages.tool_runner`(베타)가 있다. 갈리는 점은 세 가지다. 코드 양은 직접 쓰면 위 의사코드 수준(약 60줄, 추정)이고 Tool Runner는 그보다 짧다(추정). 단계 사이에 이용자 확인을 끼우고 제출 검사 결과를 is_error로 돌려주는 흐름은 직접 쓰는 쪽이 그대로 보인다. 외부 전송 기록은 직접 쓰면 `outbound.send` 한 곳에서 요청 원문을 남기면 되고, Tool Runner는 훅으로 가능하다고 적혀 있지만 이번에 확인하지 않았다. 추천은 직접 쓰기다. 베타 기능 의존이 없고, 외부 전송 경계를 한 함수로 모으는 30번 4-2절 8번과 맞는다.

**사용자 결정 필요 3: 재시도 횟수 해석.** 30번 2-1절은 "최대 3회 고친다", 30번 3-2절 점검 조건은 "3회 안에 통과"라서 해석이 갈린다. 추천은 "처음 제출 1번과 고침 3번, 제출은 최대 4번"이다. 측정에서는 몇 번째 제출에서 통과했는지를 기록하므로 11/14 점검의 "3번 안 통과율"도 같은 기록에서 계산된다.

### 3-3. 리허설의 범위와 한계

- 리허설은 실제 계산 함수(analysis.run)를 가상 데이터 폴더에 돌리는 것이다. 따로 만든 흉내 함수가 아니어야 리허설 통과가 의미를 가진다.
- 리허설 결과 전문(가상 숫자 포함)을 LLM에 돌려줘도 규정상 문제가 없다. 다만 가상 숫자를 실제처럼 문장에 옮기지 않도록 시스템 프롬프트에 금지를 적고, 숫자 규칙 검사가 막는다.
- **확인한 문제: 가상 데이터에는 업종이 12개뿐이다**(브리핑 4절, make_dummy_card.py). 계획이 나머지 30개 업종을 고르면 리허설에서 그 업종 칸이 비어 "후보 부족"으로 잘못 실패할 수 있다. 가상 데이터를 42개 업종으로 넓히거나, 리허설이 "가상 데이터에 없는 업종"을 오류가 아닌 경고로 다뤄야 한다. 분석 설계자·QA 설계자와 맞춰야 한다.
- 리허설은 계획이 실행 가능한지만 본다. 실제 센터 데이터에서 10 미만 칸이 어디서 생길지는 가상 데이터와 다르다. 이 차이는 실행 뒤 코드가 묶는 순서를 적용해 흡수한다.

## 4. 숫자 환각 차단

### 4-1. 원칙

LLM이 쓴 글에는 LLM이 지어낸 숫자가 들어갈 자리가 없다. 숫자는 모두 빈칸이고, 빈칸은 코드가 계산 결과(센터 단계)나 공개 값(단계 1)으로 채운다. 결과의 방향("높았습니다", "낮았습니다")도 LLM이 정하지 않는다. LLM은 경우별 틀을 쓰고 코드가 분석 결과의 outcome 값(higher, lower, no_difference, not_computed)으로 틀을 고른다.

### 4-2. 거름 순서

1. 글에서 `{{키}}`를 찾는다. 키가 그 단계 허용 목록에 없으면 위반이다.
2. 허용 토큰을 긴 것부터 지운다. 허용 토큰은 빈칸, 그 실행 입력에 나온 행사 이름(예: "9.81파크 구팔일 억새바당", "제20회 삼양검은모래축제"), 입력에 나온 날짜와 달(2024-07-19, 2024년 7월, 7월 19일 형태로 정규화해 비교), 업종 코드(예: I56111)다.
3. 남은 글에 아라비아 숫자(전각 숫자 포함)가 있으면 위반이다.
4. 숫자를 말로 쓴 표현 목록(두·세·네·다섯·여섯·일곱·여덟·아홉·열·스무·서른 뒤에 배·곳·개·번·달·주·해·명·건이 오는 경우, 절반, 수십, 수백, 수천, 수만, 퍼센트, %)에 걸리면 위반이다. "한"은 "한 번 더"처럼 흔히 쓰여 일부러 뺐다.
5. 위반이 있으면 위반 문장과 이유를 is_error로 돌려준다. 단계 4에서 4번째 제출까지 위반이 남은 칸은 코드에 둔 기본 문장으로 바꾼다.

말로 쓴 숫자 목록은 모든 표현을 잡지 못한다. 그래도 화면과 PDF의 결과 숫자는 구조상 빈칸에서만 오므로, 목록에서 빠진 표현은 "근거 없는 수량 표현"이 남는 위험이지 계산값이 틀리는 위험은 아니다. 목록이 너무 엄격해서 생기는 오탐은 실패가 아니라 고침 1번으로 끝난다.

### 4-3. 빈칸 채우기 규칙

- 결과 빈칸 키 목록은 분석 설계자가 소유한다(analysis.PLACEHOLDER_KEYS). 단계 4 지시에 이 목록을 그대로 넣고, 검사기도 같은 목록을 쓴다. 제안하는 키는 {{행사명}}, {{행사_읍면}}, {{비교_읍면}}, {{행사_달}}, {{기준_달}}, {{행사_읍면_증가율}}, {{비교_읍면_증가율}}, {{차이}}, {{교체_내용}}, {{묶음_내용}}, {{가짜_시점_결과}}, {{업종_범위}}, {{이용자_범위}}, {{데이터_기간}}, {{계산_못한_이유}}, 이용자가 화면에서 채우는 {{기관명}}, {{사용_목적}}이다.
- 값의 형식은 코드가 정한다. 증가율은 소수 한 자리와 %, 차이는 소수 한 자리와 "퍼센트포인트", 달은 "2024년 7월", 읍면 여러 곳은 쉼표로 잇는다. LLM은 단위를 따로 쓰지 않는다.
- 채우는 함수는 틀의 모든 빈칸에 값이 있어야 채운다. 하나라도 없으면 그 칸 전체를 기본 문장으로 바꾸고 작업 기록에 "기본 문장으로 바꿨습니다"를 남긴다. 빈칸이 그대로 보이는 화면은 나오지 않는다.
- 공통 한계 문구 네 개(인과 효과가 아님, 월 단위, 비씨카드 실소유자 기준, 공식 통계가 아님)는 코드 상수다. LLM은 이 행사만의 한계만 덧붙인다.
- 단계 1의 이유에 쓴 {{visit.키}}는 공개 값으로 채워 화면과 작업 기록에 보인다.

### 4-4. 완료 기준

통과해야 할 문장 10개(빈칸만 있는 문장, 행사 이름에 숫자가 있는 문장, 입력 날짜가 있는 문장 등)와 걸러야 할 문장 10개(숫자, "두 배", "%", 모르는 빈칸, 입력에 없는 날짜 등)를 넣은 assert 시험 하나가 통과한다.

## 5. 프롬프트 초안

모델은 생각(thinking)을 스스로 하므로 "단계별로 생각하라" 같은 지시는 넣지 않는다. 시스템 프롬프트는 실행마다 한 글자도 바뀌지 않게 둔다(캐시 조건). 날짜, 행사, 값처럼 바뀌는 것은 전부 단계 지시에 넣는다.

### 5-1. 시스템 프롬프트

```
너는 「행사 효과 나란히」의 분석 설계를 맡은 에이전트다. 제주 읍면에서 열린 축제가 그 지역 카드 소비에 어떤 차이를 만들었는지, 행사 읍면과 행사 전 흐름이 비슷한 비교 읍면을 나란히 놓고 증가율 차이를 보는 방식(이중차분)으로 계산하기 위한 계획을 세운다. 이용자는 축제를 맡은 공무원이나 관광 관련 기관 실무자다.

# 네가 보는 것과 보지 못하는 것
- 너는 공개 정보만 본다. 제주데이터허브 행사 파일, 허브 「읍면동 단위 내국인 유동인구」 값, 센터 카드 데이터의 공개 명세(컬럼과 코드값), 가상 데이터로 돌린 리허설 결과가 전부다.
- 너는 센터 카드 데이터의 실제 값을 보지 못하고 앞으로도 보지 않는다. 계획을 낸 뒤 실제 계산은 이 PC 안의 코드가 하고, 그때는 외부 연결이 잠긴다. 실제 결과를 짐작하지 마라.
- 리허설 결과의 숫자는 가상 데이터라 실제와 관계가 없다. 그 숫자를 판단 근거로 삼거나 문장에 옮기지 마라.

# 숫자 규칙
- 네가 쓰는 모든 글(이유, 근거, 문장 틀, 방법, 한계, 활용 사유)에 아라비아 숫자를 쓰지 않는다. 숫자가 필요한 자리는 {{키}} 빈칸으로 쓰고, 쓸 수 있는 키는 각 단계 지시에 적힌 것뿐이다.
- 예외는 입력에 나온 날짜와 달, 입력에 나온 행사 이름, 업종 코드다. 이것들은 입력에 적힌 그대로 쓴다.
- "두 배", "절반", "열 곳"처럼 숫자를 말로 풀어 쓴 표현도 쓰지 않는다.
- 코드가 글을 검사해서 규칙을 어긴 글은 돌려보낸다.

# 일하는 방식
- 단계마다 지시에 적힌 제출 도구(submit_로 시작) 하나를 불러 그 단계를 끝낸다. 제출 도구 밖에 쓴 글은 이용자에게 보이지 않는다.
- 공개 자료를 더 봐야 판단할 수 있으면 조회 도구(get_visit_series, find_events)를 부른다. 단계마다 많아야 네 번이다. why 칸에 왜 필요한지 한 문장으로 적는다. 이 문장은 작업 기록에 그대로 보인다.
- 제출이 검사에서 실패하면 고칠 항목이 돌아온다. 고쳐서 같은 제출 도구를 다시 부른다.
- 이유는 이용자가 읽는다. 한국어 완결 문장으로 짧고 구체적으로 쓰고, 줄임말과 화살표 나열을 쓰지 않는다.
- 확신이 없으면 확신도를 낮추고 왜 모르는지 쓴다. 모르는 것을 아는 것처럼 쓰지 않는다.

# 코드가 이미 정한 것 (너는 바꾸지 못한다)
- 결과는 "비교 읍면 대비 차이"이고 인과 효과가 아니다. "입증", "증명", "덕분" 같은 말을 쓰지 않는다.
- 사전 추세 검사(행사 전에 두 읍면이 나란히 움직였는지), 가짜 시점 검사(행사가 없던 달에 같은 계산을 해 차이가 0 근처인지), 판정 기준값은 코드가 정한다.
- 비교 읍면이 사전 추세 검사에 실패하면 코드가 네가 정한 순위대로 다음 후보로 바꾼다. 검사 결과는 너에게 돌아오지 않는다.
- 이용자 수나 이용 건수가 10 미만인 칸은 반출할 수 없다. 그런 칸이 생기면 코드가 네가 정한 묶는 순서를 차례로 적용한다.
```

### 5-5. 단계 3 지시

```
[단계 3: 계산 계획]
앞 단계 결과로 센터 카드 데이터 계산 계획을 세워 submit_plan으로 제출하라. 제출하면 코드가 형식을 검사하고 가상 데이터로 리허설한다. 실패하면 고칠 항목이 돌아오니 고쳐서 다시 제출한다.
- event_months: 행사가 걸친 달 가운데 효과를 볼 달. 달별 행사 일수와 그 달에서 차지하는 비중을 아래에 준다. 며칠만 걸친 달을 넣을지는 네가 판단하고 이유를 쓴다.

- metric: 기본은 use_amt(이용 금액)다. 다른 지표를 고르면 이유를 쓴다.
- biz_codes: 축제 방문객이 돈을 쓸 만한 업종. 너무 좁히면 10 미만 칸이 늘고, 너무 넓히면 효과가 묽어진다.
- tour_types는 관광객인 개별과 단체에서 고른다. user_types를 고를 때는 허브 유동인구가 내국인만 센다는 점을 생각한다.
- small_cell_steps: 10 미만 칸이 생기면 적용할 순서. 마지막은 반드시 "후보 제외"다.
- reasons: 각 선택의 이유. 숫자를 쓰지 않는다(달 표기와 업종 코드는 예외).
달별 행사 일수와 비중(JSON): [{"month": "...", "days": ..., "share": ...}]
행사 읍면에 다른 축제가 있던 달(JSON): [{"month": "...", "event_id": "...", "name": "..."}]
```

### 5-6. 단계 4 지시

```
[단계 4: 결과 문장 틀]
계산 결과는 아직 없고 너는 끝까지 보지 못한다. 결과가 어떻게 나오든 쓸 수 있도록 경우별 문장 틀을 써서 submit_texts로 제출하라. 코드가 실제 결과에 맞는 틀 하나를 고르고 빈칸을 채운다.
- result_sentences: higher(행사 읍면 증가율이 비교 읍면보다 높음), lower(낮음), no_difference(차이가 판정 기준 안), not_computed(계산하지 못함) 네 가지. 각각 두세 문장.
- method: 어떤 데이터를 어떤 조건으로 어떻게 비교했는지 한 문단. 이용자가 보고서 "분석 방법"에 그대로 붙여 넣을 수 있게 쓴다.
- extra_limits: 이 행사에만 해당하는 한계를 많아야 세 개(예: 같은 읍면의 다른 행사, 행사가 두 달에 걸침). 공통 한계 네 개(인과 효과가 아님, 월 단위, 비씨카드 실소유자 기준, 공식 통계가 아님)는 코드가 붙이니 쓰지 않는다.
- export_reason: 센터 반출 신청서의 활용 사유 문안 틀.
- 쓸 수 있는 빈칸: {analysis.PLACEHOLDER_KEYS를 이름과 설명과 함께 코드가 넣는다}
- higher와 lower에는 {{차이}}와 {{비교_읍면}}이 반드시 들어간다. not_computed에는 {{계산_못한_이유}}가 들어간다.
- {{차이}}와 증가율 빈칸은 코드가 숫자와 단위를 함께 채운다. 단위를 따로 쓰지 않는다.
```

### 6-1. API 설정 (참고 자료와 공식 가격 페이지에서 확인한 사실)

| 항목 | 설정 | 근거 |
|---|---|---|
| 모델 ID | `claude-haiku-5-5` 기본, `claude-sonnet-5-5` 대안. 측정 스크립트가 바꿀 수 있게 환경변수 하나로 둔다 | 참고 자료 모델표 |
| thinking | 보내지 않는다(두 모델 모두 생략하면 적응형 생각이 켜짐) | 참고 자료. Haiku 5.5는 생각을 끄면 JSON과 도구를 함께 쓸 때 도구 호출을 건너뛸 수 있다고 적혀 있어 끄지 않는다 |
| effort | `output_config.effort`를 `medium`으로 명시 | Haiku 5.5 기본값은 medium, Sonnet 5.5 기본값은 high라서 같은 조건으로 비교하려면 명시해야 한다 |
| max_tokens | 16000 | 생각 토큰도 max_tokens에 들어가 작게 잡으면 답 전에 끊긴다 |
| tool_choice | auto | Sonnet 5.5는 강제를 400으로 거절. Haiku 5.5는 받지만 강제하면 생각 없이 도구를 부른다 |
| temperature 등 | 보내지 않는다 | 두 모델 모두 기본값이 아닌 값을 400으로 거절 |
| 미리 채운 응답(prefill) | 쓰지 않는다 | 두 모델 모두 400 |
| 프롬프트 캐시 | 요청 맨 위에 `cache_control: {"type": "ephemeral"}`(자동 캐시) | 캐시 최소 길이는 두 모델 512토큰이고 시스템 프롬프트와 도구가 약 4천 토큰(추정)이라 걸린다. 측정 때 `usage.cache_read_input_tokens`로 확인 |
| 대화 이어 붙이기 | 응답 content 전체(thinking 블록 포함)를 그대로 다시 넣는다 | 두 모델은 생각 블록을 보존하며, 앞 차례를 고치면 캐시와 생각 블록이 깨진다 |
| 시간 제한과 재시도 | 요청당 60초, 연결 5초, SDK 기본 재시도 2번(429, 5xx, 연결 오류) | 참고 자료의 SDK 기본값. DLP 차단 때 오래 멈추지 않게 연결 시간을 짧게 둔다(추론) |
| 거절(refusal) | 실패로 보고 대체 경로로 간다 | Haiku 5.5는 서버 쪽 대체 모델이 없고 `fallbacks`를 넣으면 400이다. Sonnet 5.5는 `fallbacks: "default"`가 되지만 다른 모델로 넘어가 AI 사용 내역(16번 1-12)에 적을 모델이 흔들려 쓰지 않는다(추천, 사용자 결정 필요) |
| 도구 입력 읽기 | SDK가 파싱한 `block.input`을 쓴다. 문자열을 직접 맞춰 보지 않는다 | 참고 자료 |

공식 가격 페이지(오늘 확인): Haiku 5.5는 프롬프트 10만 토큰 이하에서 입력 100만 토큰당 0.10달러, 5분 캐시 쓰기 0.125달러, 캐시 읽기 0.01달러, 출력 0.50달러다. Sonnet 5.5는 입력 2달러, 5분 캐시 쓰기 2.50달러, 캐시 읽기 0.10달러, 출력 10달러다. 도구를 쓰면 시스템 프롬프트에 286토큰이 더해진다(tool_choice auto 기준, 두 모델 같음).

### 6-2. 리허설 통과율로 고르는 측정 방법

- **시험 행사 12개.** 브리핑의 시험 행사 5개(휴애리 유럽 수국축제, 한림공원 연꽃축제, 9.81파크 구팔일 억새바당, 가파도청보리축제, 2025 보롬왓 튤립축제), 짧은 행사 1개(추자도 참굴비 대축제 2023-10, 카드 데이터가 2023-08부터라 행사 전 달이 모자라 "계산 불가"가 나와야 정상), 행사 파일에서 고른 6개(2024 금능 원담축제, 한림공원 튤립축제, 제13회 우도소라축제, 2025 제주들불축제, 2024 제주메밀축제, 2024 자청비 와흘메밀문화제)다. 뒤의 6개가 읍면 행사라는 것은 추정이라 사용자가 확인한다.
- **반복.** 표본 추출 값을 고정할 수 없어 같은 입력에도 답이 달라진다. 행사마다 3번, 모델마다 36번 돌린다.
- **사람 정답표.** 사용자가 웹으로 확인해 만든다. 시험 행사 12개의 개최 읍면, 행사 달에 다른 축제가 있는 읍면 목록, 장소 추정표 213건 중 무작위 30건의 개최 장소다. 검사 통과율만 보면 우리가 만든 검사기를 우리 프롬프트가 통과하는지만 보는 셈이라, LLM과 무관한 이 정답표 지표를 반드시 같이 본다.
- **지표.** 기록은 실행마다 계획 묶음의 attempts와 usage에서 자동으로 모은다.
  1. 최종 통과율: 모든 단계가 4번 제출 안에 검사와 리허설을 통과한 실행의 비율.
  2. 3번 안 통과율: 브리핑 시험 행사 5개 기준(30번 3-2절 11/14 점검 조건).
  3. 계획 단계 평균 제출 횟수.
  4. 장소 정답률: 30건 표본과 시험 행사 12건.
  5. 같은 달 축제 읍면 제외 정답률과 잘못 뺀 읍면 수.
  6. 숫자 규칙 위반으로 돌려보낸 횟수(최종 화면에 남은 위반은 구조상 0이어야 하고, 0이 아니면 버그다).
  7. 실행 1회 시간(초)과 비용(usage로 계산).
- **고르는 기준(추천, 사용자 결정 필요).** Haiku 5.5가 다음을 모두 넘으면 Haiku 5.5로 정한다. 최종 통과율 90% 이상(36번 중 33번 이상), 브리핑 시험 행사 5개 중 4개 이상에서 3번 안 통과, 장소 정답률 85% 이상, 동 지역 행사를 읍면으로 잘못 넣은 경우 시험 행사에서 0건, 같은 달 축제 읍면 제외 정답률 90% 이상. 하나라도 못 넘고 Sonnet 5.5가 넘으면 Sonnet 5.5로 정한다. 둘 다 못 넘으면 모델을 키우지 않고 계획 형식을 줄인다(예: 가짜 시점 달을 코드가 정함). 실행 1회 비용 차이는 수 원 대 수백 원(추정)이라 기준에서 뺀다. 실행 1회가 90초를 넘으면 시연 흐름에 지장이 있어 따로 따진다.
- **측정 비용(추정).** 장소 추정표 포함 Haiku 약 0.5달러, Sonnet 약 5~10달러다. 개발 키(캡디2 키)로 실제 돈이 나가므로 측정을 시작하기 전에 사용자에게 확인을 받는다.
- **완료 기준.** 측정표(모델 2개, 지표 7개)가 남고, 선택 결과를 노션 ADR로 기록한다.

### 6-3. 실행 1회 호출 수와 비용 추정

호출 수는 최소 4번(단계마다 1번), 보통 6번(조회 1번과 계획 고침 1번 추정), 상한 16번이다. 장소 추정표는 한 번만 만든다(60건씩 4번).

토큰은 모두 추정이다. 시스템 프롬프트와 도구 정의가 약 4천 토큰이고, 대화가 끝날 때 약 1만 5천 토큰까지 늘어난다고 봤다. 보통 실행은 입력 합계 약 6만 토큰(캐시 읽기 4만, 캐시 아닌 입력 2만, 캐시 쓰기 5천), 출력 약 1만 토큰(생각 포함)이다. 1달러는 1,400원으로 가정했다(14번과 같음).

| 경우 | Haiku 5.5 | Sonnet 5.5 |
|---|---|---|
| 보통 실행(호출 6번) | 약 0.008달러, 약 11원 | 약 0.16달러, 약 220원 |
| 상한 실행(호출 16번) | 약 0.02달러, 약 28원 | 약 0.4달러, 약 550원 |
| 장소 추정표(한 번, 입력과 출력 각 약 1만 2천 토큰) | 약 0.008달러 | 약 0.15달러 |

보통 실행 Haiku 계산: 캐시 아닌 입력 2만 토큰에 0.002달러, 캐시 읽기 4만 토큰에 0.0004달러, 캐시 쓰기 5천 토큰에 0.0006달러, 출력 1만 토큰에 0.005달러를 더했다. Sonnet은 같은 토큰에 0.04, 0.004, 0.0125, 0.1달러다. 출력(생각 포함)이 비용 대부분이라 실제 생각 길이를 측정하면 숫자가 크게 달라질 수 있다. 시간은 호출당 3~8초, 실행 1회 30~60초로 추정하며 측정이 필요하다.

## 7. 키가 없거나 호출이 실패할 때

### 7-1. 대체 경로로 가는 조건

키 환경변수가 비어 있음, 인증 오류, 연결 실패나 시간 초과(DLP 차단 포함), SDK 재시도 2번 뒤에도 계속되는 429·5xx, 거절(refusal), 출력 한도 초과, 단계 1~3이 4번 제출 안에 검사를 못 넘음, 실행 1회 호출 상한 초과다. 단계 4만 실패하면 계획은 살리고 문장만 기본 문장으로 바꾼다.

### 7-2. 미리 만든 계획 3개

- **고를 행사(추천).** 한림공원 연꽃축제(한림읍, 2024-07-19~08-31), 9.81파크 구팔일 억새바당(애월읍, 2024-10-01~11-30), 2025 보롬왓 튤립축제(표선면, 2025-03-15~04-13). 고른 까닭은 세 가지다. 기간이 길거나 개최 달 비중이 커서 월 단위 희석이 덜하다(30번 2-1절 위험 2). 읍면이 서로 다르다. 셋 다 같은 달 다른 축제로 후보를 빼는 장면이 나올 것으로 본다(연꽃축제는 남원읍 휴애리 유럽 수국축제, 억새바당은 2024 자청비 와흘메밀문화제나 2024 제주메밀축제, 보롬왓은 애월읍 2025 제주들불축제. 모두 장소 추정이라 사용자 확인 필요).
- **만드는 방법.** 개발 때 6-2절에서 고른 모델로 실제 에이전트를 돌려 계획 묶음을 만들고, 사람이 내용을 확인한 뒤 app/data/prebuilt/에 저장한다. 묶음 안에는 그때의 작업 기록, 모델 이름, 만든 날짜가 같이 들어 있다. 손으로 쓴 계획이 아니라 에이전트가 실제로 만든 결과를 녹화해 둔 것이다.
- **불러올 때.** 같은 검증 규칙을 다시 돌린다. 명세나 검사 규칙이 바뀌어 오래된 묶음이 맞지 않으면 조용히 쓰지 않고 오류로 드러낸다.

### 7-3. 화면 표시

- 상단 띠: "AI 연결 없음: 미리 만든 계획으로 진행합니다".
- 작업 기록 첫 줄: "AI에 연결하지 못해(이유: 키 없음) 미리 만든 계획으로 진행합니다. 이 계획은 2026-11-14에 claude-haiku-5-5가 만들고 사람이 확인한 것입니다." 이유 칸에는 키 없음, 인증 실패, 연결 실패, 응답 중단, 검사 실패 중 하나가 들어간다. 날짜와 모델은 묶음에 적힌 값이다.
- 녹화된 작업 기록은 회색 글씨와 "기록 재생" 표시로 실제 실행 기록과 구분한다.
- 행사 고르기 화면: 미리 만든 계획이 있는 3개만 고를 수 있고, 나머지는 흐리게 두고 "AI 연결이 있어야 이 행사의 계획을 만들 수 있습니다"를 보여 준다.
- 실행 도중 실패: 그 행사에 미리 만든 계획이 있으면 "미리 만든 계획으로 바꾸기" 버튼을, 없으면 멈춘 단계와 이유, "다시 시도" 버튼을 보여 준다. 검사를 못 넘은 계획으로 계산을 진행하는 경로는 없다.

미리 만든 계획 대신 규칙으로 아무 행사나 계획을 만드는 방식(유사도 상위 3곳, 고정 업종, 기본 문장)도 가능하지만, 30번 4-2절이 정한 범위가 아니라 넣지 않는다.

### 7-4. 완료 기준

키를 지운 상태로 실행하면 3개 행사가 끝까지 결과를 내고 외부 전송 기록이 0건이다. 잘못된 키를 넣으면 같은 결과에 이유가 "인증 실패"로 나온다. 닿지 않는 주소로 연결하게 바꾸면 30초 안에 대체 경로로 넘어간다(연결 5초에 재시도 2번을 더한 추정).

## 8. 에이전트다움을 보여 줄 장면

기획서 PDF만 보고 투표하는 상호평가(브리핑 3절, 14번 4-3절)를 생각해 작업 기록 화면을 캡처해 넣는다. 아래 문장은 코드가 LLM의 제출 칸(이유, why)과 검사 결과로 만드는 작업 기록 예시다. 장소와 행사는 추정이고, 「」 안의 값은 실제 실행에서 채워진다.

1. **스스로 자료를 정리한다.** "행사 파일에서 분석 기간에 시작한 행사 213건의 장소를 이름으로 추정했습니다. 읍면 행사는 「」건, 동 지역은 「」건, 장소를 모르는 행사는 「」건입니다."
2. **짐작한 것은 묻는다.** "「한림공원 연꽃축제」는 한림공원이 있는 한림읍에서 열린 것으로 추정했습니다(확신도 높음). 맞는지 확인해 주세요."
3. **공개 데이터를 직접 보고 판단한다.** "행사 기간 하루 평균 방문 인구가 행사 전 네 주보다 「1.4배」 많아 방문 증가가 뚜렷하다고 판단했습니다."
4. **필요한 도구를 고른다.** "여름 성수기 효과와 나누려고 전년 같은 기간 한림읍 방문 인구를 추가로 조회했습니다."
5. **비교를 흐리는 후보를 뺀다.** "같은 기간 「휴애리 유럽 수국축제」가 열린 남원읍은 비교 후보에서 뺐습니다."
6. **실패에 대비한 순서를 미리 정한다.** "비교 순서를 애월읍, 한경면, 대정읍으로 정했습니다. 1순위가 사전 추세 검사에 실패하면 이 PC의 코드가 2순위로 바꿉니다. AI는 그 검사 결과를 보지 않습니다."
7. **실패하고 스스로 고친다.** "계획 1차 리허설에 실패했습니다. 전년 같은 달 2023-07이 카드 데이터 범위(2023-08부터) 밖입니다. 계획을 고칩니다." 다음 줄 "계획 2차 리허설을 통과했습니다."
8. **숫자를 지어내지 못하게 막힌다.** "결과 문장 틀에 숫자가 직접 들어간 문장 하나를 찾아 다시 쓰게 했습니다."
9. **경계가 코드로 강제된다.** "센터 데이터를 불러와 외부 AI 연결을 잠갔습니다. 이제부터 계산과 문장 채우기는 이 PC 안에서만 합니다."
10. **결과를 모른 채 쓴 틀이 맞게 골라진다.** 효과를 심지 않은 가상 데이터에서 "차이 없음" 틀이 골라지는 장면(30번 2-1절 시연 7).
11. **AI가 없어도 멈추지 않는다.** "AI에 연결하지 못해 미리 만든 계획으로 진행합니다."

기획서 필수 항목 "판단 및 자율 수행 범위"에는 다음처럼 쓴다.

| 구분 | 내용 |
|---|---|
| Agent가 혼자 정함 | 행사 장소 추정, 방문 증가 판단, 비교 읍면 순위와 뺄 읍면, 비교할 달, 업종·이용자 범위, 10 미만 때 묶는 순서, 결과 문장 틀, 조회 도구를 언제 부를지, 검사 실패 뒤 고치기(제출 4번까지) |
| 사람에게 물음 | 개최 읍면 확인, 방문 증가가 없을 때 계속할지, 센터 CSV 불러오기, 결과 삭제 |
| 코드가 정하고 Agent는 바꾸지 못함 | 사전 추세 판정, 차이 없음 판정 기준, 후보 교체 실행, 10 미만 판정, 공통 한계 문구 |
| 절대 하지 않음 | 센터 값 외부 전송, CSV를 불러온 뒤 외부 호출, LLM이 쓴 숫자를 결과로 보여 주기, 확인 없는 파일 삭제 |

## 9. 만들지 않을 것

- **로컬 LLM.** GTX 1060 3GB에서는 드라이버 570 이상이 필요하고, 3GB에 다 들어가는 한국어 모델은 2B 안팎이며, 같은 하드웨어가 없어 속도를 측정할 수 없다(14번 3절). 더 근본적으로 이 설계에서는 LLM이 센터 값을 볼 일이 없어서 로컬 LLM이 맡을 일이 없다.
- **결과를 본 뒤 LLM이 해석 문장을 쓰는 기능.** 집계값 전송은 센터가 허용 범위를 확정하지 않았다(16번 1-1). 경우별 틀로 같은 효과를 낸다.
- **자유 질문 입력 창.** 30번 4-4절에서 뺐고, 넣으면 질문 속 숫자 검문이 새로 필요해진다.
- **LLM이 코드를 쓰고 실행하는 구조.** 보안과 재현성 문제(14번 6절 2번).
- **웹 검색 도구로 장소 확인.** 장소는 이용자가 확인하고, 웹 검색은 비용과 결과 변동을 키워 장소 추정표의 재현이 어려워진다. Haiku 5.5에서 최신 웹 검색 도구 판이 되는지도 확인하지 않았다.
- **서버 쪽 대체 모델(fallbacks).** Haiku 5.5는 지원하지 않고(400), Sonnet 5.5에서는 다른 모델로 넘어가 사용 내역이 흔들린다.
- **스트리밍 응답.** 출력이 짧고, 진행 상황은 단계별 작업 기록으로 충분하다.
- **Managed Agents, Claude Agent SDK, 다중 에이전트.** 클라우드에 상태가 생기고 허용 주소가 늘며, 단계가 짧아 나눠서 얻는 것이 없다.
- **대화 기억, 벡터 DB, 임베딩.** 명세와 행사 목록이 작아 프롬프트에 다 들어간다.
- **결과 숫자를 누르면 계산식이 뜨는 근거 패널.** 30번 4-4절에서 뺐고 PDF 끝 계산 근거표로 대신한다.

## 10. 다른 설계자와 맞출 인터페이스

### 10-1. 함수 제안

외부 API를 부르는 코드는 `outbound.py` 하나에만 둔다. Anthropic SDK를 import하는 파일도 그 하나뿐이어야 한다.

| 함수 | 맡는 사람 | 입력 | 출력 |
|---|---|---|---|
| `agent.build_place_table(events)` | AI 설계 | 행사 목록 | 장소 추정표, app/data/hub/event_places.json에 저장(행사 파일 해시 포함) |
| `agent.propose_event(event_id)` | AI 설계 | 행사 ID | 날짜, 장소 추정, 확신도, 이유. LLM 호출 없음 |
| `agent.run_planning(confirmed_event, on_log)` | AI 설계 | 이용자가 확인한 행사, 작업 기록 콜백 | 계획 묶음 또는 멈춘 이유 |
| `agent.load_prebuilt(event_id)` | AI 설계 | 행사 ID | 계획 묶음 또는 None |
| `texts.fill(texts, result)` | AI 설계(규칙), 보고서 담당이 호출 | 계획 묶음의 문장 틀, 분석 결과 | 채워진 문장(틀 고르기, 기본 문장 바꾸기 포함) |
| `hub.load_events()` | 아키텍트 | 없음 | 행사 목록. ID는 이름과 시작일의 해시로 만들어 파일 순서가 바뀌어도 같게 |
| `hub.visit_daily(emd, start, end)` | 아키텍트 | 읍면, 기간 | 날짜, 요일, 방문 인구 목록(성별·연령대 합산) |
| `analysis.visit_summary(emd, start, end)` | 분석 | 읍면, 행사 기간 | 단계 1 요약값(키 이름이 곧 빈칸 이름) |
| `analysis.similarity_table(treated, pre_end)` | 분석 | 행사 읍면, 행사 전 기간 끝 | 읍면별 흐름 유사도와 규모 비율 |
| `analysis.month_coverage(start, end)` | 분석 | 행사 기간 | 달별 행사 일수와 비중 |
| `analysis.validate_plan(bundle)` | 분석이 규칙 정의, AI 설계가 호출 | 계획 묶음 | 오류 목록(한국어 문장) |
| `analysis.rehearse(bundle)` | 분석 | 계획 묶음 | 리허설 보고(오류 목록, 한국어 요약). 가상 데이터 폴더만 읽는다 |
| `analysis.run(bundle, csv_paths)` | 분석 | 계획 묶음, 센터 CSV 경로 | 결과: outcome(higher, lower, no_difference, not_computed), values(빈칸 키별 값), steps(후보 교체·묶기 기록) |
| `analysis.PLACEHOLDER_KEYS` | 분석 | 없음 | 빈칸 키와 설명 목록 |
| `outbound.send(request)` | 아키텍트, 보안 | Messages API 요청 | 응답. 잠금 상태이거나 호출 상한을 넘으면 예외. 요청 원문과 응답을 외부 전송 기록에 저장 |
| `outbound.is_locked()` | 아키텍트 | 없음 | 센터 데이터 모드 여부 |

작업 기록 한 줄의 형태는 `{"seq", "time", "stage", "kind": "판단|도구|검사|재시도|확인|잠금|대체", "text", "origin": "ai|code|prebuilt"}`다. 화면이 폴링으로 읽을지 서버 전송 이벤트로 읽을지는 ADR-148에서 미정이고, 에이전트는 목록에 추가만 한다.
