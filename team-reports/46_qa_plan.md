# QA·검증 계획: 「행사 효과 나란히」가 심사위원 PC에서 매뉴얼만으로 돌고 맞는 결과를 내는지와 그 증명 방법

작성: QA·검증 설계자, 2026-11-13. 근거는 40_plan_brief.md, 30_pm_decision.md, 22_tech_lead.md, 21_judge_panel.md 전체와 00·14·16·23번 보고서의 관련 절(검색으로 해당 줄만 읽음), 그리고 app/tools/의 build_spec.py, make_dummy_card.py, fetch_population.py다. 코드는 만들거나 고치지 않았다. 다른 설계자 6명의 결과는 보지 못했으므로 모듈 이름은 기능으로 적었다. 확인하지 않은 기술 사실에는 "기억 기반" 또는 "추정"을 붙였다.

## 결론 5줄

1. 검증은 세 층으로 나눈다. 첫째는 맥에서 1분 안에 끝나고 네트워크와 키 없이 도는 표준 라이브러리 unittest 자동 검사(계산, 10 미만, 외부 전송, 삭제, 대체 경로)다. 둘째는 실제 API를 부르는 리허설 통과율 측정 스크립트이고, 셋째는 윈도우 실기 시험 3회(11/15 1차, 11/19 2차, 제출 직전 새로 푼 ZIP 재실행)다. 손으로 보는 것은 화면 흐름과 PDF 모양뿐이다.
2. 11/14 22:00 점검은 시험 행사 5개(남원읍, 한림읍, 애월읍, 대정읍, 표선면)를 미리 정한 실행으로 판정하고, 통과가 나올 때까지 다시 돌리지 않는다. 손계산은 사용자가 스프레드시트 피벗으로 직접 만들어 app/tests/handcalc/에 둔 기대값 파일이며, 계산 함수 결과와 정수 합은 정확히, 비율은 소수 여섯째 자리까지 같아야 한다.
3. 외부 전송 경계는 표시값을 심은 가상 CSV로 전체 흐름을 돌린 뒤, 밖으로 나간 모든 문자열에서 표시값, 표시값의 합계, 최종 결과값이 0건임을 보이는 방식으로 증명한다. 같은 함수를 화면의 자가 점검 버튼과 윈도우 시험에서도 돌린다.
4. ADR-149(Python 본체와 패키지 통째 동봉) 때문에 가장 큰 위험은 윈도우의 바이너리 차단, ZIP 안 경로 길이 260자 초과, 맥용 바이너리 혼입, 폴더를 옮기면 깨지는 Python 묶음이다. 그래서 11/15 1차 시험은 빈 화면 앱이 아니라 쓸 패키지 전부를 넣은 묶음으로 하고, 제출 ZIP은 윈도우에서 시험한 파일과 SHA-256 지문이 같은 것만 낸다.
5. 지금 자료에서 계획 전에 바로잡을 것이 네 가지다. PM 문서 안에서 재시도 횟수가 "최대 3회 고친다"와 "3회 안에 통과"로 갈린다. 가상 데이터에는 1순위 비교 지역 교체 장면을 보장하는 장치가 없다. 시험 행사 3개는 전년 같은 달이 데이터 시작(2023년 8월) 이전이다. 리허설용 가상 데이터와 예시용 "센터" 가상 데이터가 같으면 외부 전송 0건 주장이 흐려진다.

## 0. 전제와 PM 문서에서 달라진 점

- PM 문서 4-2절 1번의 Streamlit 설정과 uv 설치 항목은 ADR-148(FastAPI와 정적 HTML)과 ADR-149(Python 통째 동봉)로 대체됐다. 그래서 "Streamlit 통계 꺼짐" 검사는 빼고, 대신 "서버가 127.0.0.1에만 열림"과 "동봉 Python 묶음이 윈도우에서 그대로 돎"을 검사한다.
- 차트·PDF 라이브러리와 진행 표시 방식은 아직 정해지지 않았다. 아래 검사는 라이브러리 이름 없이 결과로 판정하고, 라이브러리에 기대는 항목(글자 누락 경고 등)은 "고른 라이브러리가 matplotlib일 때"처럼 조건을 붙였다.

### 2-2. 계산(이중차분, 판정, 가짜 시점, 후보 교체)

이중차분은 행사 읍면과 비교 읍면의 행사 전후 변화 차이를 빼는 계산이다.

| 확인 항목 | 방법 | 통과 기준 |
|---|---|---|
| 손계산 대조 | 자동 | 3-3절 기대값 CSV의 모든 행에서 바탕 합계 정수는 정확히 같고, 변화율과 이중차분 값은 차이가 0.000001 미만이다 |
| 효과 판정 | 자동 | 효과 있는 판에서 시험 행사 5개 모두 "효과 있음", 효과 없는 판에서 5개 모두 "차이 없음"이 나온다 |
| 판정 문턱 정하는 순서 | 기록 확인 | 문턱은 효과 있는 판 결과를 보기 전에 효과 없는 판의 가짜 시점 분포로 정하고, 정한 날짜와 값을 기대값 CSV 옆에 적는다. 효과 있는 판이 통과하도록 문턱을 나중에 바꾸면 검증이 스스로를 확인하는 순환이 된다 |
| 가짜 시점 | 자동 | 효과 없는 판에서 행사가 없는 (읍면, 달) 조합 전부에 같은 계산을 돌린 분포(개수, 평균, 최대 절댓값)를 기록한다. 효과 있는 판에서도 행사 달을 비켜 간 가짜 시점은 문턱 안에 든다 |
| 사전 추세 검사와 후보 교체 | 자동(미리 만든 계획) | 6절 시나리오 3에서 1순위가 실패하고 계획에 적힌 순서대로 2순위로 바뀐다. 교체하는 동안 LLM 호출은 0회다 |
| 후보 부족 | 자동 | 쓸 수 있는 비교 후보가 2곳 미만이면 결과를 내지 않고 "비교할 수 있는 읍면이 부족합니다"를 보여 준다 |
| 결정성 | 자동 | 같은 입력으로 두 번 돌리면 숫자가 같다 |

계산 설계자에게 넘길 주의점이 하나 있다. 가상 데이터는 관광객 칸에 (1 + 심은 효과)를 곱하므로, 변화율의 차이로 정의하면 이중차분 값이 심은 효과에 계절 배율이 곱해진 값이 된다. 예를 들어 남원읍 2024년 8월은 계절 배율 1.35가 곱해진다. 그래서 기대값은 "심은 효과와 같다"가 아니라 손계산 값으로 잡는다. 심은 효과는 크기를 가늠하는 참고로만 쓴다.

### 2-3. 10 미만 처리

| 확인 항목 | 방법 | 통과 기준 |
|---|---|---|
| 바탕 칸 검사 | 자동 | 화면·PDF·png에 쓰인 모든 숫자의 바탕 칸(지역·달·업종 범위별 합)에서 user_cnt와 use_cnt의 최솟값이 10 이상이다. 계산 모듈이 바탕 칸 최솟값을 내부 기록으로 남기고 검사가 그것을 확인한다 |
| 묶기 발동 | 자동 | 추자면이나 우도면을 넣은 계획에서 세부 업종이 대분류로 묶이고, 그래도 모자라면 그 후보가 빠지며, 작업 기록에 단계가 찍힌다. 가상 데이터는 원본 행의 약 51%가 10 미만이라 이 장면이 실제로 나온다 |
| 금액 함께 가리기 | 자동 | 인원이나 건수가 10 미만인 칸은 금액도 출력되지 않는다 |
| 역산 불가 | 자동 | 보고서에 들어가는 모든 문자열과 차트 입력값에서, 계산 중간에 만든 정수 합계(지역·달별 user_cnt, use_cnt, use_amt 합)를 하나도 찾을 수 없다. 합계 행·열도 없다 |
| 차트 축 | 자동 | 월별 두 선 그래프의 입력값은 금액이 아니라 지수(예: 행사 전 평균 = 100)나 비율이다. 금액을 그리면 제공 단위 그대로의 단순집계가 되어 반출이 막힐 수 있다(16번 2-2절 해석) |

### 2-4. 외부 전송 경계

| 확인 항목 | 방법 | 통과 기준 |
|---|---|---|
| 표시값 자가 점검 | 자동, 화면 버튼, 윈도우 | user_cnt·use_cnt·use_amt 칸을 서로 겹치지 않는 표시용 숫자로 바꾸고 숫자 칸 하나에 표시용 문자열을 넣은 가상 CSV로 전체 흐름을 돈다. 외부 통신 모듈을 기록 모드로 두고, 나간 요청 전문, 전송 기록 파일, 오류 문구에서 표시값, 표시값의 지역·달 합계, 최종 결과값, CSV 파일 이름을 검색해 0건이다 |
| 잠금 | 자동 | 센터 CSV를 불러온 뒤 외부 호출을 시도하면 막히고, 기록에 "차단" 1건이 남으며, 실제 연결은 0건이다 |
| 통신 모듈 하나 | 자동(정적 검사) | app 코드에서 anthropic, httpx, requests, urllib.request, socket을 불러오는 파일이 외부 통신 모듈 한 파일뿐이다 |
| 오류 정화 | 자동 | 숫자 칸에 표시용 문자열을 넣었을 때 화면과 기록의 오류 문구에 컬럼 이름만 있고 값은 없다 |
| 리허설 데이터 분리 | 자동 | 리허설에 쓰는 가상 데이터 폴더와 예시 모드의 "센터" 가상 데이터 폴더가 다르다(다른 난수 씨앗으로 만든다). 예시 모드 최종 결과값이 전송 기록에 0건이다. 둘이 같으면 리허설 결과로 LLM에 간 숫자가 화면의 결과와 같아져 "센터 값 0건" 시연이 흐려진다 |
| 실행 중 연결 | 윈도우 손 | 센터 데이터 단계에서 명령 창의 `netstat -ano` 결과에 python 프로세스의 연결이 127.0.0.1뿐이다. 이 캡처는 기획서 10쪽 증거로 쓴다 |
| 질문 검문 | 자동(자유 입력 칸이 있을 때만) | 숫자가 든 입력은 보내기 전에 막히고 이유가 보인다 |

### 2-5. LLM 계획

## 3. 11/14 22:00 점검을 판정하는 방법

PM 문서 3-2절의 통과 조건 세 가지(리허설, 손계산, 허브 스냅샷)를 그대로 쓰고, 각 조건을 판정할 수 있게 구체화했다.

### 3-1. 시험 행사 5개

개최 읍면은 브리핑에 "오케스트레이터의 지식 기준, 확인 필요"로 적혀 있다. 점검 전에 사용자가 다섯 곳을 확인하고, 행사 이름과 날짜가 축제 파일 522건에 그대로 있는지 본다.

| 행사 | 읍면 | 기간 | 가상 데이터에 심은 관광객 증가 | 전년 같은 달 | 같은 달 겹치는 시험 행사 |
|---|---|---|---|---|---|
| 휴애리 유럽 수국축제 | 남원읍 | 2024-07-19~09-15 | 7월 15%, 8월 30%, 9월 20% | 2023년 7월 없음, 8·9월 있음 | 한림읍 |
| 한림공원 연꽃축제 | 한림읍 | 2024-07-19~08-31 | 7월 10%, 8월 25% | 2023년 7월 없음, 8월 있음 | 남원읍 |
| 9.81파크 구팔일 억새바당 | 애월읍 | 2024-10-01~11-30 | 10월 25%, 11월 25% | 있음 | 없음 |
| 가파도청보리축제 | 대정읍 | 2024-04-06~04-28 | 4월 30% | 2023년 4월 없음 | 없음 |
| 2025 보롬왓 튤립축제 | 표선면 | 2025-03-15~04-13 | 3월 15%, 4월 20% | 있음 | 없음 |

이 표에서 바로 나오는 점검 위험이 두 가지다.
- 남원읍, 한림읍, 대정읍은 전년 같은 달이 데이터 시작 전이다. LLM에게 주는 공개 명세에 수록 기간 2023-08~2026-08을 넣고, 계획 검사가 범위 밖의 달을 잡아야 한다. 그러지 않으면 이 세 행사에서 리허설이 반복 실패해 점검이 떨어질 수 있다.
- 남원읍과 한림읍은 같은 달에 효과가 심겨 있다. 서로를 비교 후보로 고르면 이중차분 값이 줄어든다. 그래서 "같은 달 행사가 있는 후보 빼기"를 시험하는 자연스러운 사례가 된다.

### 3-2. 조건 1: 리허설 통과

- **준비.** 22:00 전에 프롬프트를 고정하고 파일 지문을 기록한다. 점검 중에는 프롬프트를 고치지 않는다.
- **입력.** 행사마다 행사 이름, 사용자가 확인한 읍면과 날짜(확인 단계를 통과한 상태로 넣는다), 허브 스냅샷, 축제 파일 스냅샷을 넣는다. 모델은 기본 후보인 Claude Haiku 5.5(`claude-haiku-5-5`)다.
- **한 번의 시도.** LLM 계획 1회, 계획 검사(2-5절 규칙), 가상 데이터 리허설을 묶어 한 번으로 센다.
- **행사 하나의 통과.** 첫 시도를 포함해 3회 안에 계획이 형식, 계획 검사, 리허설을 모두 오류 없이 지난다. 계획 검사에는 행사 달이 확인된 날짜와 맞는지, 남원읍과 한림읍이 서로의 비교 후보에서 빠졌는지가 들어 있다.
- **판정 실행 횟수.** 아래 둘 중 하나를 고른다(사용자 결정 필요).

| 방식 | 실행 수 | 장점 | 단점 |
|---|---|---|---|
| 행사마다 미리 정한 1회 | 5회 | PM 기준 문장 그대로, 가장 빠름 | LLM 응답이 매번 달라 운으로 붙거나 떨어질 수 있다 |
| 행사마다 3회 돌려 2회 이상 통과하면 그 행사 통과 | 15회 | 운의 영향이 줄어든다 | 시간과 비용이 3배 |

추천은 3회 중 2회 방식이다. 이 점검으로 주제를 바꿀지가 정해지므로 한 번의 운에 맡기지 않는 편이 낫고, 15회의 비용은 작다(추정, 4절 방법으로 실제 비용을 기록). 어느 방식이든 통과가 나올 때까지 다시 돌리지 않고, 모든 실행을 기록한다.
- **조건 1 통과.** 시험 행사 5개 중 4개 이상이 통과한다.

### 3-3. 조건 2: 손계산 일치

- **위치.** app/tests/handcalc/handcalc_did.xlsx(사용자가 만드는 스프레드시트)와 app/tests/handcalc/expected_did.csv(자동 검사가 읽는 기대값). 스프레드시트는 Numbers로 만들어도 xlsx로 내보내 둔다. 윈도우에서도 열리고 openpyxl이 이미 있다.
- **누가.** 사용자가 스프레드시트 피벗과 수식으로 직접 만든다. Claude가 쓴 스크립트로 기대값을 만들면 계산 코드와 같은 착오를 공유할 수 있어 대조의 의미가 줄어든다.
- **범위.** 시험 행사 5개 × 효과 있는 판·없는 판 = 10행. 업종은 전체로 두어 묶기가 끼어들지 않게 하고, 묶기는 2-3절에서 따로 검사한다.
- **고정 비교 읍면(제안).** 행사 전 6개월을 쓴다고 가정하고(추정, 계산 설계자가 정함) 그 기간에 다른 시험 행사 효과가 없는 읍면을 골랐다. 남원읍은 성산읍, 한림읍은 한경면, 애월읍은 조천읍, 대정읍은 안덕면, 표선면은 구좌읍이다. 피벗을 만들었으면 나머지 읍면 열도 같은 수식으로 채워 둔다. 그러면 시나리오에서 LLM이 다른 후보를 골라도 숫자를 대조할 수 있다.
- **만드는 순서.** 효과 있는 판과 없는 판의 37개 파일을 각각 하나로 합친다(머리글은 한 번만). 터미널에서 `awk 'FNR>1 || NR==1' data/dummy/card_effect/*.csv > ~/effect_all.csv`처럼 하면 된다. 엑셀에서 BOM 없는 UTF-8 CSV를 더블클릭으로 열면 한글이 깨질 수 있으므로(기억 기반) Numbers로 열거나 엑셀의 데이터 가져오기에서 UTF-8을 고른다. 피벗은 행에 bjd, 열에 base_year_month, 필터에 tour_type(개별, 단체), 값에 계산 설계자가 정한 지표의 합을 둔다.
- **expected_did.csv 열.** case_id, variant(effect 또는 none), event_bjd, control_bjd, pre_months, post_months(세미콜론으로 구분한 YYYYMM 목록), metric, treated_pre, treated_post, control_pre, control_post, treated_change, control_change, did, made_by, made_on. 행사 전·후 값이 합인지 월평균인지는 계산 설계자의 정의를 따르고, 그 정의를 파일 첫 주석 줄에 적는다.
- **조건 2 통과.** 10행 모두에서 바탕 값 정수는 정확히 같고, 변화율과 이중차분 값의 차이는 0.000001 미만이다.

app/data/hub/population/에 읍면 12곳 파일이 있고, 2-9절 기준(파일마다 18,032행, 빈 날 없음)을 자동 검사가 통과한다. 수집기가 아직 돌고 있으면 22:00에 "미완"으로 기록한다.

## 4. 리허설 통과율 측정 방법

- **두 집합.** 개발 집합은 3-1절의 시험 행사 5개다. 보류 집합은 프롬프트를 다듬는 동안 한 번도 쓰지 않는 다른 읍면 행사 5개다. 보류 집합은 측정 전에 축제 파일의 2023-08~2026-08 행사 중 사용자가 읍면 개최를 확인한 것에서 난수 씨앗을 정해 고르고, 짧은 행사와 작은 읍면 사례로 추자도 참굴비 대축제(추자면, 2023-10-13~15)를 일부러 하나 넣는다. 개발 집합만으로 측정하면 그 5개에 맞춘 프롬프트의 성적이 되어 기획서 숫자로는 부풀려진다.
- **모델과 횟수.** Haiku 5.5와 Sonnet 5.5(`claude-sonnet-5-5`) 각각 행사마다 5회씩이다. 개발 집합 25회와 보류 집합 25회로 모델마다 50회, 합계 100회다. 보류 집합은 11/18에 고정한 최종 프롬프트로 한 번만 돌린다.
- **고정하는 것.** 프롬프트 파일 지문, 모델 ID, 호출 설정, 리허설 데이터를 실행 단위로 기록하고 측정 중에는 바꾸지 않는다. 프롬프트를 바꾸면 새 판으로 다시 측정하고 이전 판 결과와 섞지 않는다.
- **실행마다 기록할 필드.** 실행 ID, 시각, 모델 ID, 프롬프트 지문, 집합, 행사, 반복 번호, 사용한 시도 수, 최종 통과 여부, 첫 시도 통과 여부, 시도별 실패 종류(형식, 계획 검사 규칙 이름, 리허설 예외 종류), 정답 대조 결과(행사 달, 같은 달 행사 후보 제외), 입력·출력 토큰(응답의 사용량 필드), 걸린 시간.
- **기록 위치.** 원시 기록은 /Users/mh_02/jeju-agent-challenge/qa/bench/rehearsal_YYYYMMDD.jsonl(제출 ZIP 밖)에 한 줄씩 남긴다. 요약과 방법은 노션 「개발 로그」에 측정 방법 원문, 환경, 원시값, 한계와 함께 남긴다.
- **계산할 지표.** 첫 시도 통과율, 3회 안 통과율, 평균 시도 수, 실패 종류 분포, 정답 대조율, 실행당 토큰과 비용, 실행당 시간. 비용은 측정한 날의 공식 가격표를 출처와 날짜와 함께 적어 계산한다.
- **모델 선택 규칙(제안, 사용자 결정 필요).** 측정 전에 규칙을 정한다. 예를 들어 "Haiku의 3회 안 통과율이 Sonnet보다 10퍼센트포인트 이상 낮지 않으면 Haiku"다. 결과를 본 뒤에 규칙을 정하면 원하는 쪽으로 기울기 쉽다.
- **한계.** 표본이 작다. 25회 중 90%가 통과해도 95% 신뢰구간(윌슨 방식으로 계산)은 약 72~97%로 넓다. 기획서에는 비율과 함께 시행 수를 늘 같이 쓴다.

## 6. 평가 시나리오 3개

숫자 기대값은 모두 3-3절 expected_did.csv에서 가져온다. LLM이 비교 읍면을 다르게 고를 수 있으므로 화면 흐름은 손으로, 숫자는 같은 입력의 미리 만든 계획으로 자동 대조한다.

### 시나리오 1: 효과 있음

- **입력.** 첫 화면의 "예시로 해 보기", 기본 행사 휴애리 유럽 수국축제(남원읍, 2024-07-19~09-15, 기간이 가장 길어 제안), 예시 센터 CSV는 효과 있는 판 37개, 허브 스냅샷, 키 있음.
- **기대 출력.**
  1. 행사 확인 화면에 날짜와 출처(축제 파일)가 나오고, 장소 남원읍은 노란색 "AI 제안, 확인 필요"로 표시되며, 확인을 눌러야 다음으로 간다.
  2. 남원읍의 공개 일별 방문 인구 그래프(실제 허브 값, 데이터 기준일 표시)와 방문 증가 판단 문장이 나온다. 이 문장은 실제 값에 달려 있어 기대값을 고정하지 않고 손으로 본다.
  3. 비교 후보 3곳과 이유가 나오고, 작업 기록에 "같은 달 행사가 있는 한림읍은 비교 후보에서 뺐습니다"가 찍힌다. 후보에 남원읍 자신과 동 지역이 없다.
  4. 받아 올 파일 체크리스트의 달 목록이 계획의 달과 같다.
  5. 상단 띠가 "센터 데이터 모드: 외부 AI 연결 잠김"으로 바뀐다.
  6. 결과 문장이 "효과 있음" 쪽이고, 숫자는 expected_did.csv의 (남원읍, effect, 고른 비교 읍면) 행과 같다. 두 선 그래프는 지수로 그려지고, 사전 추세 검사와 가짜 시점 검사는 통과로 나오며, 한계 상자가 있다.
  7. 결과 폴더에 PDF 1개와 png가 생기고 "반출 신청 가능(사전 점검 기준)" 배지와 활용 사유 문안이 나온다.
  8. 외부 전송 기록은 센터 데이터 0건, 공개 정보 n건이다.

### 시나리오 2: 효과 없음

- **입력.** 시나리오 1과 같은 행사와 같은 계획, 예시 센터 CSV만 효과 없는 판 37개.
- **기대 출력.** 1~5번과 7~8번은 시나리오 1과 같다. 결과 문장이 "차이를 찾기 어렵습니다" 쪽이고(정확한 문구는 보고서 설계를 따름), 이중차분 값의 절댓값이 판정 문턱 안이며, 숫자는 expected_did.csv의 (남원읍, none) 행과 같다. 가짜 시점 검사는 통과로 나온다.

### 시나리오 3: 1순위 비교 지역 교체

- **입력.** 2025 보롬왓 튤립축제(표선면, 2025-03-15~04-13), 미리 만든 계획(1순위 남원읍, 2순위 성산읍, 3순위 구좌읍), 효과 있는 판.

## 9. 만들지 않을 테스트와 이유

- **화면 자동 조작 시험(Playwright 등).** 화면이 5단계뿐이고 윈도우 실기 시험에서 사람이 매번 끝까지 누른다. 도구를 묶고 유지하는 비용이 더 크다.
- **GitHub Actions 윈도우 실행기.** 테크 리드 보고서 5-4절대로 윈도우 11도 아니고 화면 조작도 없어 실기 시험을 대신하지 못한다.
- **함수마다 단위 시험, 모의 객체 체계, 커버리지 측정.** 위험이 몰린 지점(계산, 10 미만, 외부 전송, 삭제)만 결과로 검사한다.
- **PDF 화면 비교와 png 글자 인식.** 글자 누락 경고와 글꼴 내장 검사, 그리고 눈으로 보는 확인이면 충분하다.
- **LLM이 LLM 출력을 채점하는 방식.** 같은 계열 모델이 자기 결과를 확인하는 순환이 된다. 계획 검사 규칙과 정답 필드 대조로 대신한다.
- **허브 API 실시간 호출을 자동 검사에 넣기.** 서버가 502를 자주 내서 검사가 이유 없이 흔들린다. 자동 검사는 스냅샷으로 하고 실시간 호출은 손으로 한 번 본다.
- **성능·부하 시험.** 한 사람이 자기 PC에서 쓰는 도구다. 걸린 시간만 기록한다.
- **통계적 검정력 모의실험과 부트스트랩 구간.** MVP 범위 밖이고 가짜 시점 분포로 문턱 근거를 대신한다.
- **맥에서 bat 파일 흉내 내기.** 맥에서 install.bat을 확인할 방법은 실기 시험뿐이다.
- **수집기(fetch_population.py) 자체의 시험.** 한 번 쓰고 마는 수집 도구다. 결과물인 스냅샷의 완전성만 검사한다.
- **여러 브라우저 조합 전부.** 센터 PC에 있는 Chrome과 Edge만 본다.

| 결정 | 선택지 | 추천 |
|---|---|---|
| 테스트 도구 | unittest, pytest, 모듈별 assert 스크립트 | unittest(1-2절) |
| 재시도 횟수 | 첫 시도 포함 3회, 첫 시도 포함 4회 | 3회(2-5절) |
| 11/14 판정 실행 | 행사마다 1회, 행사마다 3회 중 2회 | 3회 중 2회(3-2절) |

| 허브 키 ZIP 포함 | 넣음, 넣지 않고 스냅샷만 | 자르는 순서 2번 적용 여부에 맞춤 |

다른 설계자에게 넘길 요구는 다섯 가지다.
- 계산 설계자: 효과 판정 문턱은 효과 없는 판의 가짜 시점 분포로 먼저 정하고 기록한다. 바탕 칸 최솟값을 내부 기록으로 남긴다. 행사 전 기간 길이를 정해 손계산 파일 첫 줄에 적는다.
- AI 설계자: 공개 명세에 수록 기간 2023-08~2026-08을 넣는다. 리허설용 가상 데이터를 예시용 "센터" 가상 데이터와 다른 난수 씨앗으로 만든다. 재시도 루프는 LLM 호출 함수를 바꿔 끼울 수 있게 해서 가짜 함수로 시험할 수 있게 한다.
- 보고서 설계자: 월별 그래프는 금액이 아니라 지수로 그린다. 결과 폴더에는 .pdf와 .png만 쓴다.
- 설치 설계자: 동봉 Python은 폴더를 옮겨도 도는 형태여야 한다. 차트 라이브러리의 설정·캐시 폴더를 앱 작업 폴더 안으로 지정한다. bat 파일은 CRLF와 영문만 쓴다.
- 가상 데이터: 시나리오 3이 지금 데이터로 성립하지 않으면 한 읍면의 행사 전 흐름을 어긋나게 만드는 장치를 더한다.

이 계획의 검사 작성 비용은 약 0.3~0.4일로 본다(추정). 그중 대부분은 PM 일정의 각 날 확인 조건 안에 들어 있고, 새로 더해지는 것은 표시값 자가 점검 확장, 결과값 역검색, check_zip.py, 리허설 측정 스크립트다.
